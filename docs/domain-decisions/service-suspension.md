# 서비스 운영 중단과 재개

## OPS-001 — 위치기반서비스 관련 절차 정비 전까지 전체 서비스 중단

- 날짜: 2026-08-28
- 상태: 활성
- 관련 구현: `app/_layout.tsx`, `components/ServiceSuspendedScreen.tsx`, `website/src/index.js`, `README.md`

### 배경

모토맵은 지도 주변 검색과 경로 요청 과정에서 이용자의 위치를 사업자 시스템 또는 외부 API에
전송하고, 1.2.0부터는 앱 내 길안내도 제공한다. 위치기반서비스사업 신고 대상 여부와 필요한
운영 요건을 공식 상담으로 확정하고 사업자 등록 등 선행 절차를 정비할 때까지 추가 제공을
계속하지 않기로 했다.

운영 중단은 적용 이후의 제공을 멈추는 조치다. 이미 제공한 기간을 소급해 없애거나 법률 판단을
대체하지 않는다.

### 결정

전체 서비스 중단은 다음 경계를 모두 충족해야 완료로 본다.

1. App Store에서 앱을 판매 중단해 신규 다운로드를 막는다. 앱 레코드는 삭제하지 않는다.
2. OTA를 받을 수 있는 모든 출시 런타임에는 초기화 전 운영 중단 화면을 배포한다. 중단 화면은
   지도, 위치 구독, 길안내 SDK, 인증, 푸시, 분석을 시작하지 않는다.
3. OTA를 지원하지 않거나 아직 OTA를 적용하지 않은 설치본을 위해 백엔드를 중단하고, 클라이언트에
   내장된 지도·검색·길안내 공급자 자격 증명도 비활성화한다.
4. `motomap.kr`의 소개·공유 화면은 503 운영 중단 안내로 대체한다. 이용약관, 개인정보 처리방침,
   위치기반 서비스 이용약관과 계정·데이터 요청 이메일은 계속 접근 가능해야 한다. 공개 저장소의
   `README.md`도 운영 중단과 재개 예정 시점을 알리고 App Store에서 바로 다운로드할 수 있는 것처럼
   안내하지 않는다.
5. 현재 제공 중인 기능의 이용자 데이터는 보존한다. 단, 1.1.0에서만 사용하고 현재 처리 목적이
   없는 전체 GPS 경로 `public.rides`는 RIDE-004에 따라 1.2.8 DB 정비 창에 파기한다. 운영 중단 중
   열람·삭제·처리정지 요청은 `starhn87@gmail.com`으로 접수해 처리한다.

운영 재개에는 최소한 다음 확인이 필요하다.

- 사업자 등록과 위치기반서비스사업 신고 완료. 주변 검색·날씨·유가·AI 추천·길안내 등 현재
  기능만으로 신고가 필요하며, 향후 라이딩 지도 구현 여부는 이 판단을 바꾸지 않는다.
- 위치정보 이용약관·개인정보 처리방침·보호조치와 App Store 고지의 일치
- 공식 상담 또는 전문 검토 결과 기록
- 중단한 백엔드와 외부 공급자 자격 증명의 복구, 앱 런타임별 재개 OTA 검증
- 재개 버전의 보안·릴리스 호환성 검사
- 백엔드·외부 공급자·재개 OTA와 알림 진입 화면의 정상 동작을 확인한 뒤, 보존된 푸시 토큰을
  대상으로 운영 재개 알림을 발송하고 앱 내 공지도 함께 노출

구체적인 재개 순서는 OPS-003을, 사용자 전환 방식은 OPS-002를 따른다. 활성 서비스 OTA나 운영
재개 푸시를 먼저 발행해 사용자가 복구 절차의 중간 상태에 진입하게 해서는 안 된다.

탭했을 때 중단 화면이나 오류 화면이 나타나지 않는지 실기기에서 먼저 확인하고, 발송 결과와 실패

자체 서비스에 사용하는 구조이므로, 현재 확인한 범위에서는 개인위치정보사업 등록이 아니라
위치기반서비스사업 신고를 운영 기준으로 삼는다. 외부 전문 검토에서 분류가 달라지면 근거를
기록한 후 이 결정을 대체한다.

구버전 중단 OTA를 발행할 때만 `MOTOMAP_EMERGENCY_RUNTIME_VERSION`을 대상 앱 버전으로 설정한다.
이 변수는 앱 버전과 `runtimeVersion: { policy: 'appVersion' }`을 함께 맞추는 비상 수단이며, 일반
빌드·OTA에서는 절대 설정하지 않는다. 대상 런타임과 발행 결과를 확인한 뒤 셸에서 해제한다.

운영 중단 자체처럼 안전 경계를 만드는 OTA는 계속 모든 도달 가능한 런타임에 발행한다. 중단
화면의 일정 문구처럼 안전과 무관한 변경은 REL-005에 따라 관측된 활성 런타임만 동기화할 수 있다.

### 검토한 대안과 시행착오

- App Store 판매 중단만으로는 기존 설치자와 구입 목록을 통한 재다운로드를 막지 못한다.
- 현재 런타임 하나에만 OTA를 발행하면 구버전 설치본이 계속 동작할 수 있다.
- Supabase만 중단하면 클라이언트 키로 직접 호출하는 지도·카카오 로컬·경로·길안내가 남는다.
- 원격 버전 정책은 해당 기능이 포함된 앱에서만 읽으므로 모든 출시본에 대한 중단 수단이 아니다.

따라서 스토어, 런타임별 앱, 백엔드, 외부 지도·길안내 공급자를 함께 중단한다.

### 영향과 재검토 조건

서비스 중단 또는 재개를 변경할 때는 이 문서를 가장 먼저 검토한다. 재개 시 이 항목을 삭제하지
않고 `대체됨`으로 표시한 뒤, 재개 조건과 실제 신고·검토 결과를 새 결정으로 연결한다.

운영 중단이 실제로 적용된 시각, 각 런타임 OTA 그룹, 백엔드·공급자·스토어 상태는 배포 기록에
남긴다. 비밀키나 계정 식별 정보는 문서에 기록하지 않는다.

## OPS-002 — 1.2.8 스토어 배포를 주 경로로 단계적으로 운영을 재개한다

- 날짜: 2026-08-29
- 상태: 부분 대체됨(OPS-003 — 격리된 내부 환경·재개 순서; OPS-007 — 심사/active 순서)
- 관련 구현: 구현 전 — `components/ServiceSuspendedScreen.tsx`, `expo-updates`,
  `website/src/index.js`, `lib/push.ts`, `public.broadcast_notice`

### 배경

기본 EAS Update 동작은 앱을 처음 실행할 때 새 OTA를 내려받고 다음 실행에서 적용한다. 현재 운영
중단 번들은 실행 중 업데이트 확인·다운로드·재시작 기능을 포함하지 않으므로, 재개 당일 활성 OTA와
푸시만 발행하면 일부 사용자는 앱을 두 번 직접 종료·실행해야 한다. 운영 중단 중 앱을 한 번도 열지
않아 재개 연결 OTA를 받지 못한 설치본까지 푸시 탭 한 번으로 전환하는 것은 보장할 수 없다.

기존 `push_tokens`와 `public.broadcast_notice`로 운영 재개 알림을 보낼 수 있지만 알림 권한 해제,
앱 삭제, 토큰 만료 때문에 전원 도달을 보장할 수 없다. 현재 전체 공지 함수도 Expo Push ticket과
receipt를 회수해 무효 토큰을 정리하지 않으므로 재개 방송 전에 보완이 필요하다.

### 결정

운영 재개는 1.2.8 App Store 업데이트를 주 경로로 삼고, 구버전 OTA는 사용자를 최신 스토어
버전으로 연결하는 보조 수단으로만 사용한다. 사용자에게 `앱을 두 번 껐다 켜라`고 요구하지 않고,
재개 연결 화면의 버튼 한 번이 설치 상태에 따라 다음 동작을 선택하게 한다.

- 1.2.8 미만: App Store의 모토맵 업데이트 화면을 연다.
- 1.2.8이고 호환되는 OTA가 있음: `checkForUpdateAsync` → `fetchUpdateAsync` → `reloadAsync`로
  내려받은 뒤 앱을 즉시 다시 시작한다.
- 이미 최신 상태: 서비스를 바로 시작한다.
- 확인·다운로드 실패: 중단 화면을 유지하고 재시도와 App Store 폴백을 제공한다.

재개 연결 화면은 지도, 위치 구독, 인증, 길안내 SDK, 푸시 등록과 분석을 초기화하지 않는다.
`motomap.kr`의 최소 공개 상태 엔드포인트에서 `suspended`, `preparing`, `active`, 최소 앱 버전,
스토어 URL과 사용자 문구만 읽는다. 응답 실패, 스키마 오류 또는 알 수 없는 상태는 모두
`suspended`로 닫고, 상태 응답에는 비밀키나 사용자별 정보를 넣지 않는다.

다음 순서를 바꾸지 않는다.

1. 사업자 등록, 위치기반서비스사업 신고, 약관·개인정보 처리방침·보호조치 정비와 공식 상담
   기록을 완료한다.
2. 서비스가 계속 중단된 상태에서 재개 연결 화면과 상태 엔드포인트를 구현한다. 지원 중인 구버전
   런타임에는 서비스 모듈을 열지 않는 연결 OTA를 먼저 배포하고 실기기에서 실패 폐쇄를 검증한다.
3. 1.2.8은 별도 내부 테스트 채널과 격리된 테스트 환경에서 검증한다. 이때
   `external-provider-resilience.md`의 1.2.8 필수 체크리스트를 완료해 네이버·카카오·날씨·미세먼지·
   유가·소셜 로그인의 장애가 무한 로딩, 빈 화면, 공급자 원문 노출 또는 반복 호출로 이어지지
   않는지 장애 주입으로 확인한다. 프로덕션 OTA와 App Store 공개 상태는 이 단계에서 바꾸지 않는다.
4. 1.2.8 App Store 빌드는 원격 상태가 `suspended` 또는 `preparing`이면 중단 화면만 보이도록
   제출한다. 승인·스토어 가용성과 구버전의 스토어 이동을 확인한다.
5. 공개 진입은 계속 막은 채 production Supabase와 네이버·카카오 지도·길안내 설정을 복구한다.
   허용된 테스트 계정으로 인증, 위치 권한, 지도, 검색, 장소 상세, 날씨·미세먼지·유가, 길안내,
   소셜 로그인, 푸시와 계정 삭제를 검증한다. 공급자를 다시 비활성화한 실패 경로도 확인한 뒤
   원래의 준비 상태로 되돌린다.
6. 1.2.8에 필요한 최종 OTA가 있으면 내부 채널에서 확인한 동일 산출물을 production 1.2.8
   런타임에 승격하고, 재개 버튼의 다운로드·재시작과 오류 폴백을 실기기에서 검증한다.
7. 백엔드·공급자·스토어·앱 진입 검증이 모두 끝난 뒤에만 공개 상태를 `active`로 전환한다.
   상태 전환 뒤 새 설치와 구버전 업데이트를 다시 확인한다.
8. 마지막에 `service_resumed` 운영 공지를 앱 내 알림과 푸시로 한 번 발송한다. 알림은 광고 문구를
   섞지 않고 `모토맵 운영을 다시 시작했어요`와 같이 운영 사실 및 앱 실행 방법만 안내한다.
9. Expo Push ticket·receipt, 무효 토큰, 앱 시작·업데이트 적용 실패, Sentry 오류를 확인한다.
   일시 실패만 제한적으로 재시도하고 `DeviceNotRegistered` 토큰은 제거한다. 발송 수·성공·실패와
   상태 전환 시각을 재개 배포 기록에 남긴다.

재개 방송은 캠페인 식별자로 멱등성을 보장해 중복 발송을 막는다. 푸시가 도달하지 않아도 App Store
자동 업데이트, 앱 직접 실행의 재개 연결 화면과 앱 내 공지가 같은 최종 상태로 수렴해야 한다.
향후 `push_tokens`에는 앱 버전·runtime·빌드 번호를 함께 갱신해 버전별 안내와 도달률 검증을
가능하게 한다.

### 검토한 대안과 시행착오

- 활성 OTA를 먼저 발행하고 `완전히 종료한 뒤 두 번 실행`하도록 안내하는 방식은 사용자가 적용
  여부를 알기 어렵고 중간 이탈이 커서 채택하지 않는다.
- 푸시만으로 백그라운드에서 OTA를 미리 적용하는 방식은 iOS 전달과 실행 시점이 보장되지 않고,
  현재 중단 번들에 백그라운드 적용 코드도 없어 재개 조건으로 삼지 않는다.
- 구버전 전체를 기능 OTA로 다시 여는 방식은 네이티브 계약이 다른 런타임을 장기 지원해야 하고
  재개 검증 범위를 넓힌다. 구버전은 연결 화면과 App Store 이동까지만 책임진다.
- 1.2.8 승인과 동시에 공개 상태를 여는 방식은 스토어 전파, 백엔드 및 공급자 복구의 순서가
  어긋났을 때 사용자가 부분 복구 상태를 보게 되므로 채택하지 않는다.

### 영향과 재검토 조건

현재 중단 번들을 적용한 적 없는 오래된 설치본이나 재개 연결 OTA를 받기 전에 장기간 앱을 열지
않은 설치본은 첫 실행 한 번만으로 전환되지 않을 수 있다. 이 한계는 숨기지 않고 1.2.8 스토어
업데이트를 공식 복구 경로로 제공한다. 재개 전에 App Store 자동 업데이트 보급률과 EAS Update
적용률을 확인하되, 보급률을 이유로 신고·보호조치 완료 전 서비스를 먼저 열지 않는다.

기존 바이너리의 업데이트 시작 동작을 네이티브 설정으로 바꾸는 것은 OTA로 소급 적용할 수 없다.
향후 새 중단 기능을 설계할 때에는 활성화와 복구를 한 쌍으로 구현하고, 중단 번들 자체에 안전한
상태 확인과 실행 중 업데이트 적용 수단을 포함한다.

## OPS-003 — 별도 내부 환경 없이 선행 절차 완료 후 운영 환경에서 1.2.8을 검증한다

- 날짜: 2026-09-05
- 상태: 부분 대체됨(OPS-007 — 심사/active 순서). 운영 환경 내부 검증 원칙은 유지.
- 대체 대상: OPS-002의 격리된 Supabase·외부 공급자 내부 테스트 환경과 그에 따른 재개 순서

### 배경

운영용 Supabase와 지도·길안내 공급자를 중단한 상태에서 1.2.8을 미리 실기기 검증하려면 별도
백엔드, 인증 공급자, 지도 공급자 자격 증명, EAS 채널과 테스트 데이터를 장기간 함께 관리해야 한다.
이 분리는 공개 운영을 다시 열지 않고 개발할 수 있다는 장점이 있지만, 모토맵의 현재 운영 규모와
곧 완료할 사업자 등록·위치기반서비스사업 신고 일정을 고려하면 환경 복제 및 동기화 비용이 더 크다.

### 결정

사업자 등록과 위치기반서비스사업 신고 등 OPS-001의 재개 선행 조건을 완료하기 전에는 별도
Supabase 프로젝트·브랜치나 카카오·네이버 테스트 애플리케이션을 만들지 않는다. 운영용 Supabase는
`INACTIVE`, 외부 공급자 자격 증명은 비활성, App Store는 판매 중단, 공개 런타임은 운영 중단 OTA를
유지한다.

중단 기간에는 코드 작성, 타입 검사, 단위 수준 검증과 공급자 호출이 필요 없는 로컬 검증까지만
진행한다. 실제 인증, 운영 데이터, 지도·검색·길안내와 푸시를 사용하는 1.2.8 TestFlight 검증은
선행 조건 완료 뒤 운영 환경을 복구한 다음 수행한다. TestFlight에 올렸다는 사실만으로 App Store를
다시 공개하거나 운영 재개 푸시를 발송하지 않는다.

재개 순서는 다음과 같다.

1. 사업자 등록, 위치기반서비스사업 신고, 약관·개인정보 처리방침·보호조치 정비와 공식 상담 기록을
   완료한다.
2. 1.2.8 코드와 재개 연결 화면을 완성하고 릴리스·외부 공급자 장애 대응 검사를 통과시킨다.
3. App Store 판매 중단과 공개 런타임의 중단 화면을 유지한 채 production Supabase와 네이버·카카오
   지도·검색·길안내 설정을 복구한다.
4. 운영 환경을 사용하는 1.2.8 빌드를 TestFlight 내부 그룹에만 배포하고, 허용된 계정으로 인증,
   위치 권한, 지도, 검색, 장소 상세, 날씨·미세먼지·유가, 길안내, 소셜 로그인, 푸시와 계정 삭제를
   검증한다. 공급자 장애 주입과 실패 폐쇄 동작도 함께 확인한다.
5. 검증된 빌드를 App Store 심사·배포하고 스토어 가용성을 확인한다. 필요한 최종 OTA가 있으면
   production 1.2.8 런타임에 발행해 실기기에서 확인한다.
6. 백엔드·공급자·스토어·앱 진입 검증이 모두 끝난 뒤 공개 상태를 `active`로 전환한다.
7. 마지막에 OPS-002의 재개 공지·푸시 발송과 ticket·receipt 확인 절차를 수행한다.

1.2.8 내부 검증에서 발견한 변경 때문에 운영 스키마나 자격 증명을 다시 중단해야 하면 공개 상태는
계속 닫아 둔다. 검증 편의를 이유로 사업자 등록·신고 완료 전에 운영 환경이나 일부 공급자만 먼저
활성화하지 않는다.

### 검토한 대안과 시행착오

- 별도 Supabase 프로젝트 또는 persistent branch와 공급자 테스트 앱을 구성하면 신고 전에도 폐쇄형
  실기기 검증이 가능하지만, 동일한 인증·마이그레이션·자격 증명 설정을 두 환경에 유지해야 해 현재는
  채택하지 않는다.
- 운영 Supabase만 먼저 복구하면 OTA를 적용하지 않은 구버전이 다시 접근할 수 있고, 지도 공급자까지
  복구하면 실제로 관측된 구버전의 반복 호출도 다시 성공할 수 있으므로 부분 복구를 테스트 환경
  대용으로 사용하지 않는다.

### 영향과 재검토 조건

신고 완료 전에는 실제 공급자를 사용하는 1.2.8 TestFlight 검증이 지연된다. 선행 절차 일정이 크게
미뤄지거나 여러 명이 장기간 병렬 검증해야 하는 상황이 되면, 운영 환경을 먼저 여는 대신 격리된
내부 환경 도입을 다시 검토한다.

## OPS-005 — 재개 상태 조회는 읽기 전용이며 기본값은 운영 중단이다

TestFlight 내부 그룹의 접근 범위는 실제 빌드 배포 시 다시 확인한다.

### 검토한 대안과 시행착오

### 2026-10-10 내부 검증용 복구 승인과 정비 창 제약

로컬 1.2.8 설치·중단 안내 확인 뒤 사용자가 DB·네이버·카카오 복구와 내부 진입 준비를

- production Supabase는 `INACTIVE`, 공개 상태는 `suspended`, 웹 홈은 503이다.
- 로그인한 네이버 `ridemap` Application에는 Static Map만 남아 있고 앱용 API는 복구되지 않았다.
- 설치한 로컬 Release의 `Expo.plist`에는 `EXUpdatesRequestHeaders`가 없다. 현재 설치본을
  `internal-testflight` 빌드로 간주하지 않는다. 승인된 내부 채널 설정을 포함한 재빌드가 필요하다.

  구 바이너리를 구별할 수 있다고 가정하지 않는다.
- Supabase IP Network Restrictions는 Postgres·pooler만 제한하며 HTTPS Auth·Data API·Storage를
  제한하지 않는다. 이를 내부 실기기 접근 허용 장치로 사용하지 않는다.
  [공식 문서](https://supabase.com/docs/guides/platform/network-restrictions)

  별도 승인 없이 묶지 않는다. 백업에서 유지된 설정을 확인하기 전에는 비활성이라고 단정하지 않는다.

다음 실행 전에 **공개 화면·판매 중단을 유지하되 구버전 호출 가능성을 허용하는 정비 창**인지,
**구버전까지 차단하는 강한 격리**가 필요한지 운영자가 결정한다. 후자는 서버 접근 통제·공급자
별도 식별자 등의 추가 설계와 승인이 필요할 수 있으며 기존 OPS-003을 조용히 변경하지 않는다.
완전한 구버전 차단을 약속한 채 기존 키·DB를 먼저 복구하지 않는다.

후속으로 운영자가 **정비 창 방식**, 내부 채널 빌드·DB·지도 공급자 복구·실기기 검증을
명시적으로 승인했다. 구버전 호출 가능성을 포함한 기존 환경 복구로 진행하되 공개 재개,
Git 푸시·공개 배포·재개 알림은 하지 않는다. 계정 정리·장소 검토 등 자동 작업은 상태를

## OPS-008 — 기존 고지·동의와 재개 개정안을 구분해 동기화한다

- 날짜: 2026-10-11
- 상태: 활성(소스 준비, 시행·배포 미실행)
- 보완 대상: OPS-006의 운영 주체 표기와 OPS-007의 시행일·고지 경계
- 관련 구현: `constants/legal.ts`, `constants/legal-history.ts`, `config/legal-publication.json`,
  `app/legal/[type].tsx`, `website/src/index.js`, `scripts/check-legal-publication.ts`

### 배경

운영 주체·네이버 검색을 추가한 최신 본문이 기존 2026-08-18 시행일을 그대로 표시하고 있었다.
`complete_onboarding`도 동의 버전을 2026-08-18로 고정 저장한다. 새 본문을 옛 날짜로
동의받거나, 시행일을 바꾸며 기존 동의를 새 버전으로 덮어쓰지 않도록 구분이 필요했다.

### 결정

1. 마지막 공개 고지 본문 `cff7145`를 `legal-history.ts`에 보존한다. 원래 8/18 동의 시점의
   본문은 `a6c2191`이며 이후 개인정보 권리 행사 이메일 한 줄이 추가됐다는 차이도 기록한다.
   새 운영 주체·처리 내용으로 과거 본문을 수정하지 않는다.
2. 앱과 웹은 `LEGAL_DOCS`의 현재 고지와 `LEGAL_RELAUNCH_DOCS`의 개정안을 공유한다.
   개정안은 제목·안내·변경 요약에서 초안임을 표시하고 옛 시행일을 붙이지 않는다. 가입 링크는
   현재 문서를 유지하며 초안은 별도 미리보기로만 제공한다. 날짜를 넣었다고 자동 승격하지 않는다.
3. 시행일·고지일·개정 식별자·현재/새 동의 버전은 `config/legal-publication.json`을 기준으로
   맞춘다. 현재는 draft와 null 날짜/새 버전을 유지한다. 시행일은 실제 재개일에 맞춰 확정한다.
   실제 고지·새 동의 계약과 함께 active로 바꾸며 이전 기록은 보존한다.
4. 운영 주체·문의·검색어 전송·위치 저장 경계를 개정안과 현재 1.2.8 KO/EN 제출 초안에
   맞춘다. 집·회사 제외는 표시/통계 제외이지 서버 미저장이 아님을 정확히 안내한다.
   기존 코스 완주 경로와 목적지형 추천의 장소 방문 기록을 구분한다.
5. `check:legal`은 초안 정적 검사를, `check:legal -- --ready`는 시행 준비 조건을 점검한다.
   정적 검사는 실제 고지·원격 DB 동의 반영·법률 적합성·ASC 입력의 증거가 아니다.
6. 웹의 법률 TS 변환은 정확한 선언 문자열 치환 대신 설치된 Vite 8의 TypeScript 변환을
   사용한다. 상대 import의 실제 파일 경로를 유지하고 앱·웹의 공통 원본을 복사하지 않는다.

### 영향과 실제 시행 순서

기존 `complete_onboarding`의 고정 버전과 `user_consents` 저장은 이번에 변경하지 않는다.
새 시행일 확정 후 구버전 호환·기존 기록 보존을 확인한 추가형 동의 계약을 준비하고 승인받아
반영한다. 필요한 기존 이용자의 재동의는 별도 동의 기록으로 받으며 기존 timestamp를 소급
변경하지 않는다. 릴리스 공지를 읽었음을 약관 동의 증거로 사용하지 않는다.

고지 문서가 초안인 상태를 공개 서비스 준비 완료로 표시하지 않는다. 날짜와 처리별 필요한
고지·동의를 정비한 뒤 승인받은 웹 배포·정상 진입·production 빌드/제출을 진행한다.
웹 홈/공유는 계속 503이며 상태는 preparing이다. 전용 심사 접근 기능은 만들지 않는다.
실제 ASC 개인정보 공개와 공급자별 처리 계약 분류는 최종 적용 시 확인한다.
