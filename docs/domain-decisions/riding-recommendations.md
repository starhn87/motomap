# 라이딩 추천 콘텐츠

장소 카테고리와 분리된 목적지 중심의 라이딩 콘텐츠를 어떤 단위로 제공하고, 기존 고정 경로
코스를 어떻게 안전하게 전환할지 기록한다.

현재 구현과 전환 대상:

- `app/(tabs)/courses.tsx`
- `app/course/[id].tsx`
- `components/explore/RecommendedPlaces.tsx`
- `components/explore/WeekendRideRecommendations.tsx`
- `lib/api/courses.ts`, `lib/api/courseLibrary.ts`
- `public.courses`, `public.course_reviews`, `public.course_saves`, `public.course_completions`
- `lib/api/search.ts`, `supabase/functions/moto-chat/`, `website/src/index.js`

## 먼저 확인할 활성 원칙

1. `라이딩 추천`은 카페·음식점·휴게소 같은 장소 카테고리가 아니다. 장소가 무엇인지 나타내는
   기존 카테고리는 그대로 두고, 라이딩 추천은 한 곳 이상의 장소를 엮는 별도 콘텐츠로 제공한다.
2. 라이딩 추천은 고정 경로를 저장하거나 생성하지 않는다. 지도에는 연결선 없이 장소만 표시하고,
   추천 도로는 설명 정보로만 제공한다.
3. 콘텐츠 전체를 한 번에 안내하는 버튼을 두지 않는다. 사용자는 각 장소 상세에서 기존 `도착`
   동작으로 길안내를 시작한다.
4. 장소의 리뷰·즐겨찾기·주행 기록은 기존 장소에만 남긴다. 라이딩 추천에는 별도 리뷰·완주 기록을
   만들지 않는다.
5. 추천에 연결할 장소는 좌표 근접 추정이 아니라 등록 장소 ID 또는 일반 장소의 안정적인 외부
   공급자 ID로 사람이 확정한다.
6. 전환은 새 계약을 먼저 추가하고 구 코스 계약을 유지하는 방식으로 한다. 지원 중인 구버전이
   `courses`를 읽는 동안 테이블·RPC·공유 링크를 제거하지 않는다.
7. 초기 라이딩 추천은 운영자가 선별한 콘텐츠로만 제공한다. 사용자는 장소 제보와 일반 장소
   추천으로 기여하고, 별도의 라이딩 추천 제보 기능은 실제 수요가 확인된 뒤 검토한다.

## RIDING-001 — 장소 분류와 분리된 목적지 기반 콘텐츠로 전환

- 날짜: 2026-08-24
- 상태: 활성(구현 예정)
- 관련 구현: 향후 `public.riding_guides`, `public.riding_guide_stops`,
  `app/riding/[id].tsx`
- 대체 예정: 고정 경로 중심 `courses` 탐색·상세·제보

### 배경

기존 코스는 출발지·경유지·도착지와 경로선을 저장하고 `이 코스로 길안내`, 저장, 완주, 코스
리뷰를 제공한다. 그러나 라이딩의 출발지는 사용자마다 다르고, 실제 선택은 특정 목적지나 들를
장소에서 시작되는 경우가 많다. 고정 경로는 도로 통제와 길찾기 결과를 계속 관리해야 하며,
모토맵이 이미 강점을 가진 장소·리뷰·라이더 정보와도 별도 체계를 만든다.

2026-08-24 운영 DB의 승인·활성 코스 16개를 내용으로 분류한 결과는 목적지·투어형 3개,
추천 구간형 7개, 고정 경로형 6개였다. 다만 사용자 생성 승인·대기 코스와 코스 리뷰·저장·완주
기록은 모두 0건이었다. 현재 콘텐츠의 도로 이야기는 보존할 가치가 있지만, 경로선을 강제하는
행동 모델이 사용자에게 검증된 상태는 아니다.

### 결정

탭의 사용자 표시 이름은 `코스`에서 `라이딩`으로 바꾸고 다음 두 콘텐츠를 함께 제공한다.

- `라이딩 추천`: 운영자가 한 곳 이상의 장소와 추천 이유, 추천 도로를 묶은 편집 콘텐츠
- `추천 목적지`: 기존 장소 데이터를 지역·신규·평점·내 바이크 맥락으로 탐색하는 목록

라이딩 추천 상세는 다음 원칙을 따른다.

- 제목, 요약, 상세 설명, 지역·계절·분위기 태그, 추천 도로를 표시한다.
- 하나의 대표 목적지를 반드시 두고 필요하면 함께 들를 장소를 추가한다.
- 지도에는 각 장소의 기존 카테고리 마커만 표시하고 장소 사이 경로선은 그리지 않는다.
- 장소 순서는 읽기 좋은 편집 순서일 뿐 필수 방문 순서나 내비게이션 경유 순서가 아니다.
- 각 장소를 선택하면 기존 등록 장소 또는 일반 장소 상세를 연다. 즐겨찾기·리뷰·`도착`은 그
  상세 화면의 기존 기능을 그대로 사용한다.
- 출발지에 따라 의미가 달라지는 정확한 거리와 예상 시간, 난이도는 제공하지 않는다. `반나절`,
  `봄`, `해안`, `와인딩` 같은 설명형 태그로 기대 범위를 전달한다.
- 라이딩 추천 자체의 리뷰·별점·저장·완주 기능은 만들지 않는다. 다시 찾고 싶은 목적지는 기존
  즐겨찾기에 저장하고 실제 도착은 장소 주행 기록으로 남긴다.

`추천 도로`는 경로 지시가 아니다. 예를 들어 양평 추천은 대표 목적지를 `양평 만남의 광장`으로
연결하고 `팔당에서 6번 국도로 가기 좋아요`를 설명할 수 있지만, 앱이 팔당을 경유지로 넣거나
사용자의 길찾기 결과를 변경하지 않는다.

### 데이터 모델 설계

기존 `courses`의 의미를 바꾸지 않고 다음 공개 읽기 전용 테이블을 추가한다.

#### `riding_guides`

| 필드 | 의미 |
|---|---|
| `id uuid` | 콘텐츠 ID |
| `title text` | 제목 |
| `summary text` | 카드용 짧은 설명 |
| `description text` | 상세 설명 |
| `featured_roads text[]` | 추천 도로 이름·짧은 구간 설명. 경로 계산에는 사용하지 않음 |
| `regions text[]` | 지역 탐색·추천용 정규화 지역 |
| `tags text[]` | 계절·분위기·테마 태그 |
| `cover_image_url text` | 선택적인 대표 이미지 |
| `legacy_course_id uuid` | 기존 `/course/:id` 호환용 1:1 연결. 없으면 `null` |
| `published_at`, `deleted_at` | 공개·소프트 삭제 상태 |
| `created_at`, `updated_at` | 운영 이력 |

#### `riding_guide_stops`

| 필드 | 의미 |
|---|---|
| `id uuid` | 연결 ID |
| `guide_id uuid` | `riding_guides` 외래 키 |
| `position integer` | 편집 표시 순서 |
| `role text` | `primary` 또는 `stop` |
| `place_id uuid` | 등록 장소 대상 |
| `general_place_id uuid` | 일반 장소 대상 |
| `note text` | 이 장소를 추천하는 이유 |

`place_id`와 `general_place_id`는 `num_nonnulls(...)=1`로 정확히 하나만 허용한다. 가이드마다
`primary`는 하나만 허용하고 `(guide_id, position)`은 유일하게 만든다. 장소 좌표·이름을 별도
복제해 독립 식별자로 쓰지 않는다. 일반 장소가 등록 장소로 승격되면
`general_places.promoted_place_id`를 따라 등록 상세를 열고, 등록 장소를 일반 장소로 전환할 때는
장소 이용 기록과 함께 이 연결도 같은 트랜잭션에서 일반 장소 ID로 옮긴다.

두 테이블은 `public` 스키마에 생성하므로 RLS를 켠다. `anon`과 `authenticated`에는 공개·미삭제
콘텐츠의 `SELECT`만 허용하고 클라이언트 쓰기 권한은 주지 않는다. 운영 쓰기는 마이그레이션과
서버 권한으로만 수행한다. 연결 조회에 별도 뷰가 필요하면 Postgres 17에서
`security_invoker = true`를 사용한다.

### 기존 16개 코스 전환 원칙

좌표와 가장 가까운 장소를 자동으로 연결하지 않는다. 실제 점검에서 도로상의 코스 점은 가장
가까운 등록 장소가 수십 km 떨어진 경우가 있었고, 이미 등록 해제된 일반 장소가 후보로 잡히기도
했다. 설명에 적힌 장소명과 외부 공급자 장소 ID를 사람이 교차 확인한다.

전환은 다음 세 묶음으로 진행한다.

1. 이름으로 등록 장소가 명확한 투어부터 전환한다.
   - `용인-이천 카페 투어`: 롤링트라이브, 카페194, 카페피네스
   - `천안 바이커 카페 투어`: 안라커피, 로맨틱투휠, 할리우드
   - `파주-양주 북부 코스`: 리로드, 라드
2. 일부 장소가 명확한 콘텐츠는 대표 목적지부터 확정하고 나머지는 설명으로 남기거나 별도
   외부 장소 ID를 확인한다.
   - 강화도, 대부도, 북한강, 양평, 포천-철원, 설악, 지리산
3. 현재 좌표만으로 장소 연결을 신뢰할 수 없는 콘텐츠는 전국 장소 검증을 거친 뒤 공개한다.
   - 동해안, 남해, 제주, 하동, 변산반도, 영남알프스

모든 기존 코스를 무조건 같은 수의 가이드로 만들 필요는 없다. 대표 목적지와 추천 이유가 약한
콘텐츠는 공개를 보류하거나 다른 가이드와 합친다. 최근 등록 해제된 장소를 과거 좌표와 가깝다는
이유로 다시 연결하지 않는다.

### 검색·추천·공유 계약

- 검색은 등록 장소, 일반 장소, 라이딩 추천 순으로 보여준다. 기존
  `search_courses_v2`를 변경하지 않고 `search_riding_guides_v1`을 추가한다.
- AI 추천은 기존 `moto-chat`을 구버전용으로 유지하고, 장소와 라이딩 추천만 쓰는 새 버전의
  Edge Function을 추가한다. 같은 응답 필드의 의미를 조용히 바꾸지 않는다.
- 라이딩 추천 공유 주소는 `https://motomap.kr/riding/:id`로 한다. 웹 AASA와 폴백 페이지에
  `/riding/*`를 추가하고 `/course/*`는 계속 유지한다.
- 새 앱에서 기존 `/course/:id`를 열면 `legacy_course_id`로 연결된 라이딩 추천으로 이동한다.
  연결이 아직 없거나 조회에 실패하면 기존 코스 상세를 폴백으로 연다.
- 새 추천 경로를 AASA에 추가하는 것은 웹·JS 변경이며 현재 `applinks:motomap.kr` entitlement를
  바꾸지 않으므로 새 네이티브 빌드를 요구하지 않는다.

### 구버전 호환과 퇴역 조건

지원 중인 1.2.6과 기존 1.2.7 코드가 `courses`, 코스 검색 RPC, 코스 리뷰·저장·완주를 계속
호출할 수 있으므로 새 테이블을 추가한 뒤에도 기존 계약을 유지한다. 신버전 UI에서 코스 제보를
숨겨도 구버전 요청은 현재 승인 흐름으로 처리한다. 현재 사용자 생성·대기 코스가 0건이라는
점은 전환을 단순하게 하지만 구버전 계약을 즉시 삭제할 근거는 아니다.

다음 조건을 모두 만족한 뒤 별도 결정으로 구 코스를 퇴역한다.

1. 코스를 사용하는 앱 버전이 공식 지원 범위에서 제외됐다.
2. 공유 링크와 푸시 알림의 `/course/:id` 호환 경로가 충분한 기간 유지됐다.
3. 전환 시점 이후 생긴 코스 리뷰·저장·완주·사용자 제보가 없는지 다시 확인했다.
4. Sentry와 PostHog에서 구 코스 화면·API 호출이 관찰되지 않는다.
5. 보존이 필요한 데이터가 있으면 삭제하지 않고 라이딩 추천 또는 장소 기록으로 명시적으로
   승계했다.

구 테이블을 제거하는 단계는 백엔드 API 계약 변경으로 별도 버전 정책 검토가 필요하다. 초기
추가형 배포는 기존 필드·RPC를 건드리지 않으므로 API 계약 버전을 올리지 않는다.

### 단계별 구현 계획

#### 1단계 — 콘텐츠 매핑 확정

- 16개 코스별 대표 목적지와 함께 소개할 장소를 실제 공급자 ID로 확인한다.
- 대표 목적지가 약한 콘텐츠의 보류·통합 여부를 결정한다.
- 제목·요약·추천 도로·태그를 경로 지시가 아닌 편집 문구로 다시 쓴다.
- 변환 직전 코스 리뷰·저장·완주·사용자 제보가 여전히 0건인지 다시 검사한다.

#### 2단계 — 추가형 DB 계약

- `riding_guides`, `riding_guide_stops`와 제약·인덱스·RLS·명시적 권한을 마이그레이션으로 추가한다.
- 확정된 콘텐츠만 시드하고 기존 `courses`는 수정하지 않는다.
- anon·authenticated 공개 조회, 미공개 차단, 클라이언트 쓰기 거부, 등록·일반 장소 상세 해석을
  실제 쿼리로 검증한다.
- 적용 전후 Supabase security·performance advisor를 확인한다.

#### 3단계 — 앱의 라이딩 화면

- 파일 경로 `/courses`는 기존 탭 라우트 호환을 위해 유지하고 사용자 표시 이름만 `라이딩`으로
  바꾼다.
- `라이딩 추천`과 `추천 목적지`를 제공하고 기존 코스 목록·시간 필터·완주 기반 추천을 제거한다.
- `/riding/[id]` 상세에 설명, 추천 도로, 장소 목록과 연결선 없는 지도를 구현한다.
- 장소 선택은 기존 상세를 열고 가이드 자체에는 전역 길안내·리뷰·저장·완주 동작을 넣지 않는다.
- 신버전 제보 화면에서 코스 제보 진입을 숨긴다.

#### 4단계 — 주변 기능과 호환 계층

- 통합 검색의 마지막 결과를 코스에서 라이딩 추천으로 교체한다.
- AI 추천, 최근 검색, 분석 이벤트, 빈 상태와 사용자 문구를 새 개념으로 바꾼다.

### 검토한 대안과 시행착오

- 장소 카테고리에 `코스`를 추가하면 한계령휴게소처럼 하나의 장소가 `휴게소`이면서 라이딩 추천에
  포함되는 관계를 표현하지 못하고 기존 검색·필터 의미도 깨지므로 채택하지 않았다.
- 기존 `courses`에 `destination` 타입만 추가하면 거리·시간·난이도·경로·완주·리뷰처럼 새 개념과
  맞지 않는 필드와 동작이 계속 남으므로 채택하지 않았다.
- 모든 코스를 단일 장소 하나로 바꾸면 제주 일주나 카페 투어의 맥락이 사라진다. 대신 하나의
  대표 목적지와 선택적인 함께 들를 장소를 가진 편집 콘텐츠로 일반화한다.
- 코스 좌표를 가장 가까운 장소와 자동 병합하면 잘못된 장소나 등록 해제 장소가 연결될 수 있어
  채택하지 않았다.
- 구 테이블을 한 번에 교체하면 지원 중인 앱의 검색·상세·딥링크·푸시가 깨지므로 추가형 전환과
  장기 폴백을 사용한다.

### 영향과 재검토 조건

라이딩 추천은 장소의 새로운 분류나 운영 승인 등급이 아니다. 추천에 포함됐다는 사실만으로 일반
장소를 등록 장소로 승격하거나 바이크 특화 근거로 사용하지 않는다. 장소 폐업·숨김·등록 해제 시
해당 장소를 포함한 공개 가이드를 함께 검토하는 운영 절차가 필요하다.

사용자가 실제로 GPX, 고정 와인딩 경로, 코스 이탈 감지나 완주를 반복 요청하고 그 가치가 목적지
상세 이동보다 높게 확인되면 `정밀 코스`를 별도 고급 기능으로 다시 검토한다. 이 경우에도 라이딩
추천과 장소 카테고리를 합치지 않고 독립 콘텐츠 관계를 유지한다.
