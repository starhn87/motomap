# 라이딩 추천 콘텐츠

장소 카테고리와 분리된 목적지 중심의 라이딩 콘텐츠를 어떤 단위로 제공하고, 기존 고정 경로
코스를 어떻게 안전하게 전환할지 기록한다.

## 먼저 확인할 활성 원칙

1. `라이딩 추천`은 카페·음식점·휴게소 같은 장소 카테고리가 아니다. 장소가 무엇인지 나타내는
   기존 카테고리는 그대로 두고, 라이딩 추천은 한 곳 이상의 장소를 엮는 별도 콘텐츠로 제공한다.
2. 라이딩 추천은 고정 경로를 저장하거나 생성하지 않는다. 지도에는 연결선 없이 장소만 표시하고,
   추천 도로는 설명 정보로만 제공한다.
3. 콘텐츠 전체를 한 번에 안내하는 버튼을 두지 않는다. 사용자는 각 장소 상세에서 기존 `도착`
   동작으로 길안내를 시작한다.
4. 장소의 리뷰·즐겨찾기·주행 기록은 기존 장소에만 남긴다. 라이딩 추천에는 별도 리뷰·완주 기록을
   만들지 않는다.
5. 추천에 연결할 장소는 좌표 근접 추정이 아니라 등록 장소 ID 또는 일반 장소의 안정적인 외부
   공급자 ID로 사람이 확정한다.
6. 전환은 새 계약을 먼저 추가하고 구 코스 계약을 유지하는 방식으로 한다. 지원 중인 구버전이
   `courses`를 읽는 동안 테이블·RPC·공유 링크를 제거하지 않는다.
7. 사용자는 공개 콘텐츠를 직접 작성하는 대신 `라이딩 추천 제안`을 보낸다. 제출 원문과 운영자가
   다듬어 발행하는 라이딩 추천은 별도 데이터로 관리한다.
8. 라이딩 추천 제안은 출발지·고정 경로·거리·예상 시간·난이도를 받지 않는다. 대표 목적지와 추천
   이유를 필수로 받고, 함께 들를 장소·추천 도로·태그는 선택적으로 받는다.
9. 운영 심사에서는 제안을 새 추천으로 발행하거나 기존 추천에 병합할 수 있다. 추천에 포함됐다는
   사실만으로 일반 장소를 등록 장소로 승격하지 않는다.
10. 신버전의 내 정보에서는 장소 즐겨찾기만 `즐겨찾기`로 제공한다. 라이딩 추천에는 저장·완주를
    만들지 않으며, 레거시 코스 저장·완주 데이터와 API는 구버전 호환을 위해서만 유지한다.

## RIDING-001 — 장소 분류와 분리된 목적지 기반 콘텐츠로 전환

- 날짜: 2026-08-24
- 상태: 활성(구현 완료·배포 대기)
- 관련 구현: `public.riding_guides`, `public.riding_guide_stops`,
  `app/riding/[id].tsx`, `components/submit/SubmitRidingGuide.tsx`
- 대체 예정: 고정 경로 중심 `courses` 탐색·상세·제보

### 배경

기존 코스는 출발지·경유지·도착지와 경로선을 저장하고 `이 코스로 길안내`, 저장, 완주, 코스
리뷰를 제공한다. 그러나 라이딩의 출발지는 사용자마다 다르고, 실제 선택은 특정 목적지나 들를
장소에서 시작되는 경우가 많다. 고정 경로는 도로 통제와 길찾기 결과를 계속 관리해야 하며,
모토맵이 이미 강점을 가진 장소·리뷰·라이더 정보와도 별도 체계를 만든다.

2026-08-24 운영 DB의 승인·활성 코스 16개를 내용으로 분류한 결과는 목적지·투어형 3개,
추천 구간형 7개, 고정 경로형 6개였다. 다만 사용자 생성 승인·대기 코스와 코스 리뷰·저장·완주
기록은 모두 0건이었다. 현재 콘텐츠의 도로 이야기는 보존할 가치가 있지만, 경로선을 강제하는
행동 모델이 사용자에게 검증된 상태는 아니다.

### 결정

탭의 사용자 표시 이름은 `코스`에서 `라이딩`으로 바꾸고 다음 두 콘텐츠를 함께 제공한다.

- `라이딩 추천`: 운영자가 한 곳 이상의 장소와 추천 이유, 추천 도로를 묶은 편집 콘텐츠
- `추천 목적지`: 기존 장소 데이터를 지역·신규·평점·내 바이크 맥락으로 탐색하는 목록

라이딩 추천 상세는 다음 원칙을 따른다.

- 제목, 요약, 상세 설명, 지역·계절·분위기 태그, 추천 도로를 표시한다.
- 하나의 대표 목적지를 반드시 두고 필요하면 함께 들를 장소를 추가한다.
- 지도에는 각 장소의 기존 카테고리 마커만 표시하고 장소 사이 경로선은 그리지 않는다.
- 장소 순서는 읽기 좋은 편집 순서일 뿐 필수 방문 순서나 내비게이션 경유 순서가 아니다.
- 각 장소를 선택하면 기존 등록 장소 또는 일반 장소 상세를 연다. 즐겨찾기·리뷰·`도착`은 그
  상세 화면의 기존 기능을 그대로 사용한다.
- 출발지에 따라 의미가 달라지는 정확한 거리와 예상 시간, 난이도는 제공하지 않는다. `반나절`,
  `봄`, `해안`, `와인딩` 같은 설명형 태그로 기대 범위를 전달한다.
- 라이딩 추천 자체의 리뷰·별점·저장·완주 기능은 만들지 않는다. 다시 찾고 싶은 목적지는 기존
  즐겨찾기에 저장하고 실제 도착은 장소 주행 기록으로 남긴다.

`추천 도로`는 경로 지시가 아니다. 예를 들어 양평 추천은 대표 목적지를 `양평 만남의 광장`으로
연결하고 `팔당에서 6번 국도로 가기 좋아요`를 설명할 수 있지만, 앱이 팔당을 경유지로 넣거나
사용자의 길찾기 결과를 변경하지 않는다.

### 데이터 모델 설계

기존 `courses`의 의미를 바꾸지 않고 다음 공개 읽기 전용 테이블을 추가한다.

#### `riding_guides`

| 필드 | 의미 |
|---|---|
| `id uuid` | 콘텐츠 ID |
| `title text` | 제목 |
| `summary text` | 카드용 짧은 설명 |
| `description text` | 상세 설명 |
| `featured_roads text[]` | 추천 도로 이름·짧은 구간 설명. 경로 계산에는 사용하지 않음 |
| `regions text[]` | 지역 탐색·추천용 정규화 지역 |
| `tags text[]` | 계절·분위기·테마 태그 |
| `cover_image_url text` | 선택적인 대표 이미지 |
| `legacy_course_id uuid` | 기존 `/course/:id` 호환용 1:1 연결. 없으면 `null` |
| `published_at`, `deleted_at` | 공개·소프트 삭제 상태 |
| `created_at`, `updated_at` | 운영 이력 |

#### `riding_guide_stops`

| 필드 | 의미 |
|---|---|
| `id uuid` | 연결 ID |
| `guide_id uuid` | `riding_guides` 외래 키 |
| `position integer` | 편집 표시 순서 |
| `role text` | `primary` 또는 `stop` |
| `place_id uuid` | 등록 장소 대상 |
| `general_place_id uuid` | 일반 장소 대상 |
| `note text` | 이 장소를 추천하는 이유 |

`place_id`와 `general_place_id`는 `num_nonnulls(...)=1`로 정확히 하나만 허용한다. 가이드마다
`primary`는 하나만 허용하고 `(guide_id, position)`은 유일하게 만든다. 장소 좌표·이름을 별도
복제해 독립 식별자로 쓰지 않는다. 일반 장소가 등록 장소로 승격되면
`general_places.promoted_place_id`를 따라 등록 상세를 열고, 등록 장소를 일반 장소로 전환할 때는
장소 이용 기록과 함께 이 연결도 같은 트랜잭션에서 일반 장소 ID로 옮긴다.

두 테이블은 `public` 스키마에 생성하므로 RLS를 켠다. `anon`과 `authenticated`에는 공개·미삭제
콘텐츠의 `SELECT`만 허용하고 클라이언트 쓰기 권한은 주지 않는다. 운영 쓰기는 마이그레이션과
서버 권한으로만 수행한다. 연결 조회에 별도 뷰가 필요하면 Postgres 17에서
`security_invoker = true`를 사용한다.

#### `riding_guide_submissions`

공개 콘텐츠와 사용자 제안 원문을 분리한다. 운영자가 문장을 다듬거나 여러 제안을 합쳐도 누가
무엇을 제안했는지와 처리 결과가 사라지지 않아야 한다.

| 필드 | 의미 |
|---|---|
| `id uuid` | 제안 ID |
| `submitted_by uuid` | 제안 사용자 |
| `title text` | 선택적인 제안 제목. 대표 목적지를 고르면 앱이 초깃값을 제시함 |
| `reason text` | 라이더에게 추천하는 구체적인 이유 |
| `featured_roads text[]` | 선택적인 추천 도로·구간 설명. 경로 좌표가 아님 |
| `tags text[]` | 선택적인 계절·분위기·테마 |
| `status text` | `pending`, `editing`, `published`, `merged`, `rejected` |
| `result_guide_id uuid` | 새로 발행하거나 병합한 최종 라이딩 추천 |
| `rejected_reason text` | 사용자에게 보여줄 반려 사유 |
| `reviewed_at`, `created_at`, `updated_at` | 심사·생성 이력 |

`editing`은 제안 가치가 인정됐지만 운영자가 문구·장소 신원을 다듬는 상태다. 사용자의 `내 제보`
화면에는 `pending=검토 중`, `editing=추천 준비 중`, `published·merged=반영됨`,
`rejected=반려`로 간결하게 표시한다.

#### `riding_guide_submission_stops`

| 필드 | 의미 |
|---|---|
| `id uuid` | 제안 장소 연결 ID |
| `submission_id uuid` | `riding_guide_submissions` 외래 키 |
| `position integer` | 사용자가 제안한 표시 순서 |
| `role text` | `primary` 또는 `stop` |
| `place_id uuid` | 등록 장소 대상 |
| `general_place_id uuid` | 일반 장소 대상 |
| `note text` | 이 장소를 함께 추천한 이유 |

제안에도 대표 목적지는 정확히 하나만 두고, 각 행은 등록 장소와 일반 장소 중 하나만 연결한다.
사용자가 카카오 검색 장소를 고르면 기존 `ensureGeneralPlace`로 안정적인 `general_places` ID를 만든
뒤 연결한다. 라이딩 추천 제안은 해당 장소에 사용자 기록이 생기는 행위이므로 일반 장소 행 생성
시점과도 맞는다. 좌표와 이름만 제안 테이블에 복사해 별도 장소 정체성을 만들지 않는다.

제안과 장소 연결은 하나의 `security invoker` RPC에서 트랜잭션으로 저장한다. 함수 실행 권한은
`authenticated`에만 명시적으로 부여하고, 부모·자식 테이블 RLS는 `(select auth.uid()) =
submitted_by`인 생성과 본인 조회만 허용한다. 제출 후 클라이언트 수정·삭제는 허용하지 않는다.
`anon`은 제안 원문을 읽을 수 없으며 운영 처리는 서버 권한으로만 한다. 새 `public` 테이블은 Data
API 자동 노출 여부와 별개로 필요한 권한을 명시적으로 `grant`하고 모든 RLS 역할을 실제 쿼리로
검증한다.

### 라이딩 추천 제안 UX

제보 탭의 `코스` 항목은 `라이딩`으로 바꾸고 다음 순서로 입력받는다.

1. **대표 목적지 선택(필수)**: 모토맵 등록 장소와 일반 장소 검색을 함께 제공한다. 검색 결과가
   외부 장소이면 안정적인 공급자 ID로 일반 장소를 만든다.
2. **추천 이유(필수)**: 경치, 노면 흐름, 휴식, 음식, 집결처럼 실제 라이딩에서 좋았던 이유를
   구체적으로 적게 한다.
3. **함께 들를 곳(선택)**: 같은 장소 선택기를 재사용한다. 표시 순서일 뿐 필수 경유 순서가
   아니라는 설명을 붙인다.
4. **추천 도로(선택)**: `북한강로`, `6번 국도 팔당~양평 구간` 같은 텍스트를 받는다. 지도에서
   선을 긋거나 도로 좌표를 요구하지 않는다.
5. **태그(선택)**: 계절·해안·와인딩·카페 투어처럼 탐색에 도움이 되는 제한된 칩을 우선하고
   자유 입력을 보조로 둔다.
6. **제출 전 확인**: 장소 마커만 있는 미리보기와 `출발지는 사람마다 달라 고정 경로를 저장하지
   않아요`라는 안내를 보여준다.

제안 제목은 대표 목적지를 고르면 `양평 만남의 광장으로 가는 라이딩`처럼 자동 제안하고 사용자가
수정할 수 있게 한다. 거리·예상 시간·난이도·출발지는 폼에서 제거한다. 대표 목적지와 추천 이유가
있으면 제안할 수 있어야 하며, 사진은 초기 필수 범위에서 제외하고 장소·리뷰 사진을 재사용한다.
제출 버튼과 완료 문구는 각각 `라이딩 추천 보내기`, `추천을 검토한 뒤 알려드릴게요`로 한다.

### 라이딩 추천 제안 심사

제안 승인은 등록 장소 승인과 다른 판단이다. 일반 장소가 포함돼 있어도 다음을 만족하면 라이딩
추천으로 발행할 수 있다.

- 대표 목적지와 선택 장소가 실제 동일한 장소인지 공급자 ID·주소·좌표로 확인한다.
- 추천 이유가 단순 광고나 좌표 나열이 아니라 라이더가 방문할 구체적인 가치를 설명한다.
- 추천 도로가 있으면 이륜차 통행이 합법적이며 자동차전용도로·상시 통제 구간을 권하지 않는지
  확인한다. 불확실한 도로 문구는 장소 제안 전체를 반려하기보다 편집에서 제외할 수 있다.
- 기존 추천과 대표 목적지·주제·장소 구성이 실질적으로 같은지 확인한다. 같은 목적지라도 계절이나
  테마가 충분히 다르면 별도 추천이 될 수 있으므로 이름 일치만으로 중복 판정하지 않는다.
- 장소의 현재 영업·접근 상태는 확인하지만 바이크 특화 등록 기준 충족을 요구하지 않는다.

AI는 `새 추천`, `기존 추천에 병합`, `판단 유보`, `반려`와 근거를 Discord에 제안한다. 운영자가
최종 결과를 선택하고, 새 추천은 공개 전 편집 상태에서 제목·설명·장소를 확인한다. 기존 추천에
병합할 때는 원문을 덮어쓰지 않고 `result_guide_id`로 연결한다. 사용자에게는 실제 공개 또는 병합이
완료된 뒤 `라이딩 추천에 반영됐어요` 알림을 보낸다. 선정만 되고 편집 중인 상태를 공개 완료로
오해하게 하는 승인 알림은 보내지 않는다.

`docs/submission-approval-policy.md`에는 라이딩 추천 제안 기준을 주 기준으로 추가하고,
`supabase/functions/_shared/submissionPolicy.ts`의 버전·규칙 ID와 Discord 문구를 같은 커밋에서
동기화한다. 지원 중인 구버전이 보낼 수 있는 고정 경로형 코스 기준은 레거시 부록으로 유지한다.

### 기존 16개 코스 전환 원칙

좌표와 가장 가까운 장소를 자동으로 연결하지 않는다. 실제 점검에서 도로상의 코스 점은 가장
가까운 등록 장소가 수십 km 떨어진 경우가 있었고, 이미 등록 해제된 일반 장소가 후보로 잡히기도
했다. 설명에 적힌 장소명과 외부 공급자 장소 ID를 사람이 교차 확인한다.

전환은 다음 세 묶음으로 진행한다.

1. 이름으로 등록 장소가 명확한 투어부터 전환한다.
   - `용인-이천 카페 투어`: 롤링트라이브, 카페194, 카페피네스
   - `천안 바이커 카페 투어`: 안라커피, 로맨틱투휠, 할리우드
   - `파주-양주 북부 코스`: 리로드, 라드
2. 일부 장소가 명확한 콘텐츠는 대표 목적지부터 확정하고 나머지는 설명으로 남기거나 별도
   외부 장소 ID를 확인한다.
   - 강화도, 대부도, 북한강, 양평, 포천-철원, 설악, 지리산
3. 현재 좌표만으로 장소 연결을 신뢰할 수 없는 콘텐츠는 전국 장소 검증을 거친 뒤 공개한다.
   - 동해안, 남해, 제주, 하동, 변산반도, 영남알프스

모든 기존 코스를 무조건 같은 수의 가이드로 만들 필요는 없다. 대표 목적지와 추천 이유가 약한
콘텐츠는 공개를 보류하거나 다른 가이드와 합친다. 최근 등록 해제된 장소를 과거 좌표와 가깝다는
이유로 다시 연결하지 않는다.

2026-08-24 구현에서는 운영 DB의 활성 코스·장소 ID와 이름을 다시 대조해 다음 10개만 초기
라이딩 추천으로 확정했다.

- 강화도: 강만장, 블랙바트
- 대부도: 헬로모토
- 북한강: 브리끄, 두물머리
- 설악: 한계령휴게소, 미시령 옛길 정상
- 양평: 양평 만남의 광장
- 용인·이천: 롤링트라이브, 카페194, 카페피네스
- 천안: 안라커피, 로맨틱투휠, 할리우드
- 파주·양주: 리로드, 라드
- 포천·철원: 포천아우토반카페, 바이크와커피가만나다
- 지리산: 성삼재휴게소, 정령치휴게소

동해안, 남해, 제주, 하동, 변산반도, 영남알프스 6개는 설명에 맞는 안정적인 장소 ID가 현재
데이터에서 확인되지 않아 보류했다. 시드 마이그레이션도 코스와 모든 연결 장소의 ID·이름·활성
상태가 일치할 때만 각 추천을 넣는다. 따라서 운영 데이터가 없는 새 로컬 DB나 중간에 장소가
숨겨진 환경에서 잘못된 부분 콘텐츠가 만들어지지 않는다.

### 검색·추천·공유 계약

- 검색은 등록 장소, 일반 장소, 라이딩 추천 순으로 보여준다. 기존
  `search_courses_v2`를 변경하지 않고 `search_riding_guides_v1`을 추가한다.
- AI 추천은 기존 `moto-chat`을 구버전용으로 유지하고, 장소와 라이딩 추천만 쓰는 새 버전의
  Edge Function을 추가한다. 같은 응답 필드의 의미를 조용히 바꾸지 않는다.
- 라이딩 추천 공유 주소는 `https://motomap.kr/riding/:id`로 한다. 웹 AASA와 폴백 페이지에
  `/riding/*`를 추가하고 `/course/*`는 계속 유지한다.
- 새 앱에서 기존 `/course/:id`를 열면 `legacy_course_id`로 연결된 라이딩 추천으로 이동한다.
  연결이 아직 없거나 조회에 실패하면 기존 코스 상세를 폴백으로 연다.
- 새 추천 경로를 AASA에 추가하는 것은 웹·JS 변경이며 현재 `applinks:motomap.kr` entitlement를
  바꾸지 않으므로 새 네이티브 빌드를 요구하지 않는다.

### 구버전 호환과 퇴역 조건

지원 중인 1.2.6과 기존 1.2.7 코드가 `courses`, 코스 검색 RPC, 코스 리뷰·저장·완주를 계속
호출할 수 있으므로 새 테이블을 추가한 뒤에도 기존 계약을 유지한다. 신버전 UI는 고정 경로형 코스
제보를 라이딩 추천 제안으로 교체한다. 구버전이 제출한 `courses` 대기 행은 Discord에서
`레거시 코스 제보`로 구분하고 현재 승인 흐름으로 처리한다. 현재 사용자 생성·대기 코스가 0건이라는
점은 전환을 단순하게 하지만 구버전 계약을 즉시 삭제할 근거는 아니다.

다음 조건을 모두 만족한 뒤 별도 결정으로 구 코스를 퇴역한다.

1. 코스를 사용하는 앱 버전이 공식 지원 범위에서 제외됐다.
2. 공유 링크와 푸시 알림의 `/course/:id` 호환 경로가 충분한 기간 유지됐다.
3. 전환 시점 이후 생긴 코스 리뷰·저장·완주·사용자 제보가 없는지 다시 확인했다.
4. Sentry와 PostHog에서 구 코스 화면·API 호출이 관찰되지 않는다.
5. 보존이 필요한 데이터가 있으면 삭제하지 않고 라이딩 추천 또는 장소 기록으로 명시적으로
   승계했다.

구 테이블을 제거하는 단계는 백엔드 API 계약 변경으로 별도 버전 정책 검토가 필요하다. 초기
추가형 배포는 기존 필드·RPC를 건드리지 않으므로 API 계약 버전을 올리지 않는다.

### 검토한 대안과 시행착오

- 장소 카테고리에 `코스`를 추가하면 한계령휴게소처럼 하나의 장소가 `휴게소`이면서 라이딩 추천에
  포함되는 관계를 표현하지 못하고 기존 검색·필터 의미도 깨지므로 채택하지 않았다.
- 기존 `courses`에 `destination` 타입만 추가하면 거리·시간·난이도·경로·완주·리뷰처럼 새 개념과
  맞지 않는 필드와 동작이 계속 남으므로 채택하지 않았다.
- 모든 코스를 단일 장소 하나로 바꾸면 제주 일주나 카페 투어의 맥락이 사라진다. 대신 하나의
  대표 목적지와 선택적인 함께 들를 장소를 가진 편집 콘텐츠로 일반화한다.
- 코스 좌표를 가장 가까운 장소와 자동 병합하면 잘못된 장소나 등록 해제 장소가 연결될 수 있어
  채택하지 않았다.
- 구 테이블을 한 번에 교체하면 지원 중인 앱의 검색·상세·딥링크·푸시가 깨지므로 추가형 전환과
  장기 폴백을 사용한다.

### 영향과 재검토 조건

라이딩 추천은 장소의 새로운 분류나 운영 승인 등급이 아니다. 추천에 포함됐다는 사실만으로 일반
장소를 등록 장소로 승격하거나 바이크 특화 근거로 사용하지 않는다. 장소 폐업·숨김·등록 해제 시
해당 장소를 포함한 공개 가이드를 함께 검토하는 운영 절차가 필요하다.

사용자가 실제로 GPX, 고정 와인딩 경로, 코스 이탈 감지나 완주를 반복 요청하고 그 가치가 목적지
상세 이동보다 높게 확인되면 `정밀 코스`를 별도 고급 기능으로 다시 검토한다. 이 경우에도 라이딩
추천과 장소 카테고리를 합치지 않고 독립 콘텐츠 관계를 유지한다.

- 관련 구현: `app/favorites.tsx`, `app/(tabs)/profile.tsx`, `app/_layout.tsx`

### 배경

`저장·완주` 화면의 `코스 기록`은 고정 경로형 코스의 저장·완주를 모으던 UI다. 라이딩 추천은
고정 경로와 별도 저장·완주를 만들지 않고, 다시 찾을 목적지는 장소 즐겨찾기에 남긴다는 현재
모델과 맞지 않는다. 별도의 `주행 기록` 메뉴도 있어 코스 기록이라는 이름이 실제 주행 이력처럼
보이는 혼동도 있었다.

### 결정

내 정보의 `저장·완주`를 `즐겨찾기`로 바꾸고 별 아이콘을 사용한다. 즐겨찾기 화면에서는 등록
장소와 일반 장소를 한 목록으로 바로 보여주며 `장소 / 코스 기록` 구분 탭과 레거시 코스 목록
조회는 제거한다.

### 검토한 대안과 시행착오

코스 기록을 별도 메뉴로 유지하면 과거 데이터를 볼 수 있지만, 현재 라이딩 추천에 저장·완주가
있는 것처럼 기대하게 만든다. `저장한 콘텐츠`처럼 범위를 넓히는 방식도 검토할 수 있으나 현재
저장 가능한 비장소 콘텐츠가 없으므로 도입하지 않는다.

### 영향과 재검토 조건

이 변경은 신버전 UI의 진입점만 숨긴다. 지원 중인 구버전과 기존 딥링크 호환을 위해
`course_saves`, `course_completions`, 관련 RPC·API와 레거시 상세 폴백은 삭제하지 않는다.
향후 라이딩 추천 자체를 저장하거나 컬렉션 기능을 도입하면 즐겨찾기 화면의 콘텐츠 범위를 다시
검토한다.
