# 릴리스와 버전 호환성

앱 바이너리, OTA, 네이티브 브리지와 백엔드가 서로 다른 시점에 배포되더라도 기존
사용자의 핵심 기능과 데이터를 지키기 위한 결정 기록이다.

관련 구현:

- `config/release-policy.json`, `config/release-notes.json`
- `lib/appVersion.ts`, `lib/appCompatibility.ts`, `lib/updateCheck.ts`
- `modules/kakao-navi/`, `scripts/check-release-compatibility.mjs`
- `public.app_compatibility_policy`

## 현재 계약

- 현재 앱 버전: **1.2.8**
- 공식 지원 직전 버전: **1.2.7**
- 원격 최소 실행 버전: **1.2.4**
- 네이티브 브리지 계약: **1**
- 백엔드 API 계약: **1**

`config/release-policy.json`이 코드가 읽는 기준이고 이 문서는 결정과 운영 절차를
보존한다. 버전·브리지·API 계약을 바꿀 때는 코드, 이 문서, 릴리즈 노트와 App Store
제출 문서를 같은 커밋에서 갱신한다. CI가 현재 값의 동기화를 검사한다.

1.2.8은 Expo 57 **재개 후보**다. 로컬 내부 채널 Release 빌드·설치와 기본 실기기 검증은
완료했고 사용자 승인 후 내부 TestFlight 1.2.8 (36)의 Apple 업로드를 완료했다.
TestFlight 설치/후속 전체 검증과 App Store 심사·production OTA·공개 운영 재개는 아직 별도다.
원격 정책·중단 상태는 변경하지 않았으며 위 최소 버전은 로컬 계약 기록이다.

2026-10-11 제출 준비 후속: 앱 공지·스토어 문서의 1.2.8 릴리스 노트 초안을 동기화했다.
최신 소스의 실기기/TestFlight 검증과 승인된 심사 접근은 아직 필요하다. `preparing`에서
production은 로그인 이전에 막히므로 리뷰어 계정만으로 접근된다고 안내하지 않는다.
검증한 소스를 production으로 별도 빌드하고 profile·채널·버전을 확인한 실제 build ID로
제출한다. `--latest`로 내부 채널 바이너리를 공개 제출본으로 선택하지 않는다. 초안 작성은
빌드·업로드·공개 운영·알림 승인이나 CPU/메모리 개선·프리 웜업 완료를 의미하지 않는다.

2026-10-11 후속 승인: 사용자가 최신 내부 빌드·실기기 검증과 통과 후 TestFlight 업로드를
승인했다. 공개 운영·Git 푸시·App Store 심사는 포함하지 않는다. 로컬 검증한 Xcode 27.0
(27A266a)과 같은 안정판을 쓰도록 internal-testflight 프로필의 iOS image를
`macos-tahoe-26.6-xcode-27.0`으로 고정한다. Expo 57의 자동 sdk-57 이미지(Xcode 26.6)나
움직이는 latest 별칭으로 검증 툴체인이 바뀌지 않도록 한다. production 프로필은 이번에
바꾸지 않으며 공개 제출 전 툴체인을 별도로 대조한다.
[공식 이미지 목록](https://docs.expo.dev/build-reference/infrastructure/)

## 먼저 확인할 활성 원칙

1. `runtimeVersion`은 `appVersion` 정책을 유지한다. 네이티브 코드·플러그인·권한·
   네이티브 의존성이 바뀌면 앱 버전과 런타임을 함께 올린다.
2. 최신 버전 `N`과 직전 버전 `N-1`을 공식 지원한다. `N-1`은 원칙적으로 90일 또는
   최신 버전 보급률 95%까지 유지한다.
3. 강제 업데이트는 보안, 데이터 손상, API 계약 불일치처럼 구버전을 계속 실행하는
   편이 더 위험할 때만 사용한다. 최신 버전이 나왔다는 이유만으로 최소 버전을 올리지
   않는다.
4. OTA는 네이티브 기능을 앱 버전 문자열로 추측하지 않고 실제 브리지의 `features`를
   확인한다. 없는 기능은 숨기거나 기존 동작으로 폴백하며 앱 전체를 종료하지 않는다.
5. 백엔드는 추가형 변경을 먼저 배포하고 구버전과 신버전을 동시에 받는다. 필드 삭제,
   이름 변경, RPC 인자·응답의 비호환 변경은 기존 계약에서 하지 않고 `*_v2`처럼 새
   경계를 만든다.
6. Sentry·PostHog에는 앱 버전, 빌드 번호, 런타임, OTA ID, 네이티브 브리지와 API 계약
   버전을 함께 남긴다. 수정 이슈는 바로 닫지 않고 새 빌드의 `Pending release`로 관리한
   뒤 48~72시간 재발이 없을 때 해결 처리한다.
7. 런타임별 OTA 동기화 범위는 변경 위험도와 관측된 사용량을 함께 본다. 운영 차단·보안·데이터
   보호 변경은 사용량과 무관하게 도달 가능한 모든 런타임에 배포하고, 문구·스타일 같은 비필수
   변경만 REL-005의 활성 런타임 기준으로 범위를 줄일 수 있다.

## REL-001 — 앱 버전을 OTA 호환성 경계로 사용

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `app.config.js`, `eas.json`, `config/release-policy.json`

### 배경

여러 App Store 바이너리가 동시에 사용되는 동안 새 JS가 구 네이티브 메서드를 호출하면
시작 즉시 충돌할 수 있다. 반대로 네이티브 변경이 없는 수정까지 매번 심사 빌드로 보내면
복구 속도가 느려진다.

### 결정

마케팅 버전과 runtime을 같은 값으로 둔다. 같은 바이너리 안의 JS 변경은 해당 runtime
OTA로 배포하고 네이티브 경계가 바뀌면 새 앱 버전을 만든다. 빌드 번호는 EAS remote
source와 `autoIncrement`로 관리한다. `release/<version>` Git 브랜치나 태그를 남겨 지원
중인 이전 runtime에 긴급 수정만 선택적으로 백포트할 수 있게 한다.

### 검토한 대안과 시행착오

runtime을 고정하면 OTA 도달 범위는 넓지만 네이티브 계약이 다른 바이너리를 구분하지
못한다. fingerprint 정책은 정밀하지만 현재 릴리스 운영에는 계약 변화가 불투명해질 수
있어 도입하지 않는다.

### 영향과 재검토 조건

Expo가 fingerprint 정책을 안정화하고 runtime별 백포트·승격 도구가 현재 방식보다 명확한
운영 이점을 제공하면 다시 검토한다.

## REL-002 — 원격 최소·권장 버전은 읽기 전용 정책으로 관리

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `public.app_compatibility_policy`, `lib/appCompatibility.ts`, `lib/updateCheck.ts`

### 배경

App Store 공개 조회는 최신 버전만 알려 주며 Apple CDN 지연이 있다. 최소 지원 버전이나
긴급 차단 여부를 표현할 수 없고, 출시 뒤 구버전 앱에 운영 결정을 전달할 방법도 없었다.

### 결정

플랫폼별 `latest`, `recommended`, `minimum_supported`와 안내 문구·스토어 URL을 Supabase의
공개 읽기 전용 행으로 제공한다. `anon`·`authenticated`는 `SELECT`만 가능하고 변경은
`service_role`만 한다. 원격 조회는 2.5초 안에 끝나지 않거나 값·순서가 잘못되면 무시한다.
그때는 App Store 조회와 로컬 릴리즈 노트가 계속 동작한다.

현재 iOS 원격 정책은 latest/recommended 1.2.6, minimum 1.2.4다. 1.2.7이 TestFlight에만
있는 동안에는 변경하지 않는다. App Store 승인 후 latest/recommended를 1.2.7로 올리고,
minimum은 구버전 위험과 보급률을 확인한 뒤 별도로 결정한다.

### 영향과 재검토 조건

최소 버전 변경은 사용자 진입을 막는 운영 변경이다. 변경 전 해당 버전의 보안·데이터 위험,
App Store 가용성, Sentry·PostHog 보급률을 기록하고 승인받는다.

## REL-003 — 네이티브 브리지는 기능 계약을 직접 노출

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `modules/kakao-navi/ios/KakaoNaviModule.swift`, `modules/kakao-navi/index.ts`

### 배경

기능 도입 버전을 문서와 JS 조건문에 흩어 두면 OTA 백포트나 새 브리지 추가 때 조건이
서로 달라진다. iOS 전용 모듈의 무조건 로드는 미지원 플랫폼의 앱 시작도 막을 수 있다.

### 결정

네이티브 모듈은 `bridgeVersion`과 `features`를 상수로 노출한다. JS는 optional module로
읽고 미지원 환경에서는 구독을 no-op으로, 실제 안내 요청은 명시적 오류로 처리한다.
상수를 도입하기 전 구 브리지는 이미 검증된 기능 집합만 명시적으로 폴백하고, 새 네이티브
방어 기능은 지원한다고 추측하지 않는다.
기능 추가·삭제 또는 wire 타입 변경 시 `nativeBridgeVersion`을 올리고 CI 검사와 이 문서를
함께 갱신한다.

### 영향과 재검토 조건

단순 네이티브 내부 버그 수정처럼 JS 계약이 동일해도 새 바이너리는 필요하지만 브리지
계약은 올리지 않을 수 있다. JS가 새 메서드·이벤트·상수를 사용하면 반드시 올린다.

## REL-004 — TestFlight 전용 API는 공개 제출 전에 철회할 수 있다

- 날짜: 2026-08-24
- 상태: 활성
- 관련 구현: `supabase/migrations/20260824111321_drop_registered_place_reactions.sql`,
  `config/release-policy.json`

### 배경

1.2.7 TestFlight에서 시험한 등록 장소 좋아요와 인기 순위를 제출 전에 철회했다. App Store 운영
버전 1.2.6은 해당 테이블·RPC를 호출하지 않는데도 일반 공개 구버전 호환을 가정하면 사용하지 않는
API와 데이터를 장기간 유지하게 된다.

### 결정

App Store에 공개된 버전과 지원 대상 OTA가 한 번도 사용하지 않은 TestFlight 전용 API는 같은
후보 버전을 제출하기 전에 클라이언트 호출과 DB 계약을 함께 제거할 수 있다. 이 경우 공개된 API
계약의 호환성을 깨지 않으므로 `apiContractVersion`은 올리지 않는다. TestFlight 설치본에서는 새
OTA가 먼저 적용되도록 한 뒤 제거 마이그레이션을 적용한다.

### 영향과 재검토 조건

공개 버전, 심사 제출본 또는 운영 OTA가 한 번이라도 호출한 API에는 이 예외를 적용하지 않는다.
그때는 추가형 변경과 버전 경계, 구계약 유지 기간을 기존 원칙대로 설계한다.

## REL-005 — 비필수 OTA 백포트는 관측된 활성 런타임에 한정할 수 있다

- 날짜: 2026-08-30
- 상태: 활성
- 관련 구현: `app.config.js`, EAS Update production 채널, PostHog 릴리스 속성

### 배경

앱 버전을 런타임 경계로 사용하므로 동일한 문구·스타일 변경도 출시 런타임마다 별도 OTA가
필요하다. 설치자가 없는 런타임까지 매번 동기화하면 검증과 배포 기록만 늘어나지만, 분석에서
보이지 않는다는 이유만으로 실제 설치자를 0명으로 단정하면 장기간 앱을 열지 않은 이용자가
뒤늦게 실행할 때 오래된 화면을 받게 된다.

### 결정

운영 차단, 보안, 개인정보·위치정보 보호, 데이터 손상 방지, 필수 업데이트 연결처럼 안전 경계를
바꾸는 OTA는 관측 사용량과 무관하게 도달 가능한 모든 런타임에 발행한다. 문구, 간격, 색상 등
서비스 안전과 기능 계약에 영향을 주지 않는 비필수 변경만 다음 기준으로 대상 런타임을 줄인다.

1. 현재 최신 지원 런타임은 항상 포함한다.
2. PostHog `Application Opened`의 `app_version` 또는 `$app_version` 기준 최근 90일 고유 사용자가
   1명 이상인 런타임을 포함한다. 최근 30일 수치와 마지막 관측 시각도 함께 확인한다.
3. 직전 EAS Update의 최근 30일 `uniqueUsers`를 교차 확인한다. 이 값은 해당 업데이트를 받은
   이용자이지 전체 설치자 수가 아니므로 단독으로 0명을 판정하지 않는다.
4. 유효한 버전 속성이 있는 PostHog 최근 90일 사용자가 0명이고 EAS 지표도 0명일 때만 비필수
   백포트를 생략할 수 있다. 데이터가 누락되거나 조회가 실패한 런타임은 0명이 아니라 `미확인`으로
   취급해 포함한다.
5. 조회 날짜, 기간, 버전별 결과, 실제 발행 대상을 같은 배포 기록에 남긴다.

### 영향과 재검토 조건

분석 초기화를 막는 운영 중단 번들에서는 배포 이후 실행을 PostHog로 새로 측정할 수 없다. 따라서
중단 중 판단은 중단 전 PostHog 활동과 EAS Update 적용 지표를 함께 사용한다. 향후 앱 시작 전에
개인정보를 침해하지 않는 익명 배포 상태 지표를 별도로 수집하게 되면 이 기준을 재검토한다.

## REL-006 — 재개 패키지 전환은 지원 조합·네이티브 경계 단위로 준비한다

- 날짜: 2026-10-04
- 상태: 대체됨(REL-007; 2026-10-04 준비 기록 보존)
- 관련 문서: [업그레이드 준비 계획](../package-upgrade-plan.md), [성능 계획](../performance-optimization-plan.md), PERF-002

### 배경

운영 재개 시 패키지 갱신을 먼저 안정화하고 성능 최적화를 진행하기로 했다. 현재 Expo 54에서
목표 후보 57까지의 전환에는 네이버 심벌 patch·KNSDK 동적 framework·수명주기·권한·OTA가
함께 영향을 받는다. npm 최신값을 일괄 설치하거나 다른 네이티브 조합에 같은 runtime을 쓰면
원인 추적·구버전 안전성을 잃는다.

### 결정

1. 지금은 manifest·lock·앱 버전·원격 정책을 바꾸지 않는다. 공식 릴리스·공개 패키지 메타데이터와
   기존 소스·보안 경고를 검토해 후보를 준비하고, 실제 설치·빌드·검증은 이후 별도 합의해 진행한다.
2. Expo/RN/React·Expo 모듈은 SDK 지원 조합으로 단계 전환한다. npm `latest`나 넓은 peer 범위를
   앱 호환성 증거로 쓰지 않는다. 독립 라이브러리·major·SDK 교체와 성능 개선은 별도 논리 단위다.
3. patch와 plugin은 새 상류 구현·생성물을 검토해 옮긴다. patch 실패·peer 충돌을 강제로 무시하거나
   생성된 native 폴더를 무조건 삭제하지 않는다. 직접 수정·untracked 변경은 먼저 보호한다.
4. SDK 중간 단계는 production·OTA로 배포하지 않는다. 구버전 최소 측정은 승인된 기존 바이너리만
   사용하고 불가능하면 미측정으로 남긴다. 다른 네이티브 조합을 담은 설치용 비교 빌드가 필요하면
   별도 앱 버전·runtime·채널 경계를 먼저 승인받는다. SDK가 다른 두 빌드를 같은 1.2.8 runtime으로
   배포하지 않는다.
5. 재개 버전 후보는 1.2.8이지만 현재 계약은 1.2.7 그대로다. 실제 native 전환의 버전·runtime을
   확정할 때 정책·릴리스 노트·제출 문서를 함께 갱신한다. native/API 계약 변경은 별도로 판정한다.
6. 선행 조건 전에는 앱·운영 DB·공급자를 활성화하지 않는다. 내부 검증은 OPS-003을 따르고
   업그레이드·성능 계획을 운영 재개 승인으로 간주하지 않는다. 푸시·빌드/배포는 승인 범위대로 한다.

### 검토한 대안과 영향

- 모든 라이브러리를 latest로 통일하면 Expo의 지원 RN·React·Sentry·저장소 조합과 어긋난다.
- 패키지 갱신과 최적화를 한 commit에 섞으면 좋아지거나 악화된 원인을 분리하기 어렵다.
- 새 SDK가 안 맞는 경우 기존 native SDK로 되돌리는 일은 OTA로 할 수 없다. 공개 전에 호환성·
  보안·릴리스 경계를 검증하고, 목표를 낮춰야 하면 근거와 재개 범위를 다시 승인받는다.
- 목표 SDK·툴체인·공급자·runtime 경계가 바뀌면 이 결정·준비 계획·PERF-002를 함께 갱신한다.

## REL-007 — Expo 57 소스 전환과 배포 승인을 분리

- 날짜: 2026-10-10
- 상태: 활성(소스·설치 착수, 네이티브 검증·운영 복구 대기)
- 대체 대상: REL-006의 준비 전용 범위. 호환성·중간 SDK 비배포 원칙은 유지한다.

### 결정

1. 사용자 승인을 받아 SDK 54 → 55 → 56 → 57 의존성·소스를 단계 검토한다. 최종 후보는
   Expo 57 지원 RN/React 조합이며 RN·React 최신 major를 독립적으로 섞지 않는다.
2. 네이티브 의존성 전환 후보는 앱/runtime 1.2.8로 묶는다. 로컬 계약·릴리스 노트·제출 문서는
   같은 커밋에서 갱신하되 원격 최소/권장 버전과 운영 상태는 바꾸지 않는다.
3. SDK별 정적 검사와 최종 patch 적용 결과를 기록한다. prebuild·Pods·codegen·네이티브 빌드와
   실기기 검증이 남아 있으면 지원 완료·성능 개선 완료로 표현하지 않는다.
4. 운영 복구·푸시·빌드·배포는 매번 승인 범위를 확인한다. internal-testflight 빌드를
   production 심사 빌드로 승격하지 않는다. 공개 preparing과 중단 게이트는 유지한다.
5. iOS 최소 지원 버전 상승(16.4)과 SDK 공급자의 대응 여부는 공개 전 점검한다.
   CPU·메모리 개선 코드는 패키지 전환과 분리하며 PERF-003의 검증 경계를 따른다.

### iOS 27 SDK의 scene 실행 경계

- 사용자 승인으로 Xcode 27 안정판 업데이트를 시작했다. Expo 57.0.27의
  `expo-build-properties.ios.enableSceneSupport`를 켜 iOS 27 SDK의 필수 scene 실행 경로를 사용한다.
- Expo는 scene 이벤트를 기존 AppDelegate의 URL·universal link·수명주기 훅으로 전달한다.
  생성물에서 카카오 URL 처리와 React Native 전달이 유지됨을 확인했다. KNSDK subscriber를
  scene별로 중복 등록하거나 SDK를 미리 초기화하지 않는다.
- JS 메서드·이벤트·상수 계약은 바꾸지 않아 native/API 계약은 1을 유지한다.
  공개 전 후보 1.2.8 안의 네이티브 설정 변경이며 1.2.7 OTA에는 포함하지 않는다.
- prebuild·plist와 소스 회귀 검사만 통과했다. 설치·콜드/웜 링크·로그인·길안내의
  background/foreground 실기기 검증이 끝나기 전에는 지원 완료로 표시하지 않는다.

후속으로 iOS 27 SDK의 Pods·codegen 및 Release 서명 없는 컴파일을 통과했다.
개발용 서명 갱신은 Apple Developer Program License Agreement 동의 요구로 차단됐다.
서명·설치·콜드/웜 링크·SDK 실행 검증은 남아 있으므로 공개 호환성 검증 완료로 표시하지 않는다.

이후 사용자 계약 동의 확인 뒤 개발용 Release 서명 빌드·기기 설치를 통과했다.
설치본은 로컬 1.2.8 build 1 / runtime 1.2.8이며 TestFlight·공개 제출본이 아니다.
중단 안내 표시까지 확인했지만 콜드/웜 링크·로그인·지도·길안내의 활성 기능 회귀는 남아 있다.
단일 중단 화면 CPU 예비 기록을 공개 호환성 검증 완료나 성능 개선 결과로 사용하지 않는다.

### 내부 채널 로컬 빌드

사용자가 내부 채널 빌드·DB·지도 공급자 복구·실기기 검증을 승인했다. 로컬 Release에서는
EAS의 자동 채널 주입이 없으므로 `EAS_BUILD_PROFILE=internal-testflight`를 명시한 설정만
`updates.requestHeaders['expo-channel-name']`을 생성한다. 기본·production 프로필에는 내부
헤더를 넣지 않는다. 생성된 Expo.plist와 서명된 앱에서 다시 확인하며 JS에서 채널을 위조하거나
중단 게이트를 제거하지 않는다. 같은 1.2.8 네이티브 조합의 채널 지정이며 브리지/API 계약은 1이다.
이는 TestFlight 업로드·production 제출·OTA 발행·공개 재개 승인이 아니다.

후속으로 내부 채널 Release 서명·설치 및 사용자 확인에 의한 지도·마커·검색·상세·경로
미리보기·정지 상태 길안내 시작/앱 복귀/종료의 기본 검증을 통과했다. 실제 주행·모든 로그인
수단·콜드/웜 링크·장시간과 전체 릴리스 검증이 남아 있으므로 공개 지원 완료로 표시하지 않는다.

## 릴리스 체크리스트

### 2026-10-11 스플래시 생성 회귀 복원

기존 `splash-icon.png` 파일은 바뀌지 않았지만 Expo 57로 생성한 storyboard에 이전
`expo.splash`의 이미지·검은 배경·전체 화면 contain이 반영되지 않았다. 사용자 요청으로
`expo-splash-screen` 플러그인을 명시하고 iOS `enableFullScreenImage_legacy`를 켜 기존
디자인을 복원한다. 새 이미지·앱 아이콘으로 대체하거나 JS 진입 화면을 추가하지 않는다.

공개 전 1.2.8 후보의 네이티브 생성 설정 수정이다. 앱/runtime 1.2.8과 native/API 계약 1은
유지하며 OTA로만 복원됐다고 표시하지 않는다. 생성 storyboard·원본 자산·서명 Release의
콜드 실행을 확인한다. 플러그인의 legacy 옵션은 향후 제거될 수 있으므로 Expo 업그레이드마다
기존 디자인과 실제 생성물을 비교하고, 대체 방식이 필요하면 디자인 유지 조건으로 검토한다.
[Expo 스플래시 설정 안내](https://docs.expo.dev/versions/latest/sdk/splash-screen/)

같은 날 실기기 후속: 원본 스플래시 직후 별도 화면이 보인다는 사용자 확인으로 복원 미완료를
발견했다. 네이티브 생성물은 맞았지만 `ServiceLoadingScreen`이 운영 상태 조회와 lazy 로딩
동안 앱 아이콘·별도 문구·스피너를 그렸다. 해당 대기 화면도 동일 원본·검은 배경·전체 화면
contain으로 이어지게 수정한다. SafeArea 안의 72px 아이콘으로 대체하지 않고 운영 상태/OTA
검사·실패 폐쇄·모듈 초기화 경계는 그대로 둔다. 네이티브 파일 비교만으로 시작 UX 완료를
판정하지 않으며 설치 후 콜드 실행의 연속 화면을 다시 확인한다.

후속 사용자 확인으로 별도 화면 전환은 해소됐지만 원본이 지나치게 짧게 보이는 문제를 확인했다.
최초 루트 마운트의 단조 시계를 기준으로 최소 500ms를 확보하고 iOS 네이티브 스플래시를
180ms cross-dissolve로 숨긴다. 이는 OS 실행부터 정확히 500ms라는 의미가 아니며, JS가
시작되기 전의 로딩 시간은 별도다. 운영 상태 조회와 기존 화면 준비는 이 시간과 병행한다.

- 활성 화면은 기존 lazy import·폰트·기본 루트 레이아웃이 준비됐을 때, 중단/재시도/업데이트
  안내는 해당 레이아웃이 준비됐을 때 숨긴다. 모든 지도 타일·서버 데이터 완료를 기다리지 않는다.
- 준비에 이미 500ms 이상 걸렸으면 추가로 500ms를 더 지연시키지 않는다. 웜 복귀·재시도마다
  스플래시를 다시 띄우지 않으며 effect 정리 시 예약을 취소한다. 루트 오류 경계로 전환할 때는
  네이티브 스플래시를 숨겨 오류 안내를 가리지 않는다.
- 운영 게이트·버전/OTA 검사·딥링크 전달은 유지한다. 프리 웜업·SDK 선행 초기화·추가 요청은
  넣지 않는다(PERF-006). 이 변경은 시작 UX 조정이며 CPU·메모리 개선 증거로 사용하지 않는다.
- 로컬 내부 Release 설치·콜드/웜 링크를 다시 확인한 뒤 커밋한다. 푸시·OTA·공개 배포는
  이번 승인 범위 밖이다. 앱/runtime 1.2.8, native/API 계약 1과 원본 이미지 설정은 유지한다.

1. `config/release-policy.json`의 앱·지원·계약 버전을 결정한다.
2. `config/release-notes.json`, App Store 문서, 이 문서의 현재 계약을 함께 갱신한다.
3. 백엔드 변경은 구버전 요청을 먼저 수용하고 직전 버전 최신 OTA와 새 TestFlight 양쪽에서
   인증·검색·즐겨찾기·리뷰·딥링크·푸시를 확인한다.
4. `npm run check:release`, `npm run typecheck`, Edge Function 타입체크를 통과시킨다.
5. TestFlight에서 새 설치와 직전 버전 업데이트, 길안내 시작·백그라운드·복귀·종료를
   확인한다.
6. 위험도가 높은 지도·인증·길안내 OTA는 단계 배포하고 Sentry·PostHog의 버전 태그로
   이상을 확인한다. 문제면 신규 배포를 중단하거나 embedded update로 롤백한다.
7. App Store 승인 후 원격 latest/recommended와 사용자용 공지를 갱신한다. minimum은
   별도 근거와 승인 없이 올리지 않는다.
8. 운영 중단 뒤 재개하는 릴리스는 일반 배포보다 `service-suspension.md`의 **OPS-003**을
   우선한다. 활성 production OTA나 운영 재개 푸시만으로 서비스를 먼저 열지 않는다.
   공개 상태를 닫아둔 채 백엔드·공급자를 복구하고 `internal-testflight` 채널로 내부 검증한 뒤,
   1.2.8 스토어 가용성 → 공개 상태 `active` 전환 → 운영 공지 순서를 지킨다.
9. 1.2.8 재개 빌드는 `external-provider-resilience.md`의 필수 체크리스트와 장애 주입 검증을
   통과해야 한다. 네이버 지도, 카카오 검색·길안내, 날씨·미세먼지·유가와 소셜 로그인에서
   무한 로딩, 오류 원문 노출, 실패의 0건 오인과 설정 오류 반복 호출이 남아 있으면 공개하지 않는다.
