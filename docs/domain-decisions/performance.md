# 앱 성능 측정·최적화

화면 반응·자원 사용량을 어떻게 검증하고, 최적화 과정에서 무엇을 지켜야 하는지 기록한다.
실행 시나리오·비교 조건·결과 양식은 [성능 계획](../performance-optimization-plan.md)에서 관리한다.

## 활성 원칙

- 실측 전에 병목이나 최적화 효과를 확정하지 않는다. 코드상의 후보와 실제 관측을 구분한다.
- 개발 빌드는 원인 탐색에 사용하고, 최종 성능은 조건을 맞춘 실기기 release 계열에서 비교한다.
- 화면 첫 표시·핵심 조작 가능·선택 정보 준비, JS·네이티브 CPU·대기, heap·전체 메모리를 분리한다.
- 이미 적용한 windowing·구독 격리·이미지 제한은 효과를 검증한다. 기존 실패 접근을 되풀이하지 않는다.
- 속도를 위해 마커·검색·리뷰 등 결과를 누락하거나 위치·길안내 정확성, 레이아웃·gesture 계약을 깨지 않는다.
- 원본 위치·사용자 콘텐츠를 성능 로그에 넣지 않는다. 측정도 운영 중단·개인정보·릴리스 경계를 따른다.
- 병목 하나씩 수정해 전후 수치와 기능 회귀·트레이드오프를 남긴다. 측정 잡음 수준이면 효과 미확인이다.
- 명확한 구독·타이머·임시 자원 해제 결함은 PERF-003에 따라 소스 단계에서 수정할 수 있다.
- 패키지 전환이 예정돼 있으면 구버전은 최소 기준만 확보하고, 신버전 안정화 후 전체 측정·최적화한다(PERF-002).

## PERF-001 — 운영 중단 중에는 계획만, 재개 조건 충족 후 측정

- 날짜: 2026-10-04
- 상태: 대체됨(PERF-003; 2026-10-04 준비 기록 보존)
- 관련 문서: [성능 계획](../performance-optimization-plan.md), [기존 성능 백로그](../../PLAN.md#성능구조-후순위-백로그)
- 관련 구현: `app/_layout.tsx`, `components/ActiveRootLayout.tsx`, `components/map/`,
  `components/ui/ImageViewer.tsx`, `hooks/usePlaces.ts`, `hooks/useUnifiedPlaceSearch.ts`,
  `lib/queryClient.ts`, `modules/kakao-navi/`

### 배경

화면 로드·메모리·CPU를 포함해 다방면으로 측정하고 개선할 계획이 필요하다. 다만 현재는
사업자·위치기반서비스 신고 보완·대기로 앱과 백엔드를 활성화할 수 없다. 코드 정리는
자동으로 성능 개선을 보장하지 않으며 기존 지도·사진 최적화와 네이티브 hang도 구분해야 한다.

### 결정

1. 지금은 코드·문서 검토와 외부 호출 없는 정적 검사만 한다. 앱 실행·계측 추가·DB 복구·API
   활성화·빌드·OTA는 하지 않는다. 측정을 이유로 중단 게이트를 우회하지 않는다.
2. [OPS-003](service-suspension.md)의 신고·보호조치 조건 충족 후 공개 상태 `preparing`을 유지하며
   승인된 내부 검증부터 시작한다. 별도 상시 내부 환경을 이번 계획에서 새로 만들지 않는다.
3. 네이티브 길안내 hang을 우선 조사하고, 시작·지도·상세·사진·긴 세션의 기준값을 수집한다.
   그 결과로 사용자 영향이 큰 병목을 선정한다. 모든 최적화를 공개 재개의 선행 조건으로 만들지 않는다.
4. 동일 기기·버전·캐시·데이터·네트워크·발열 조건에서 반복 비교한다. 실패·취소·표본 수를
   공개하고 평균만으로 완료를 선언하지 않는다. 목표값은 기준값 수집 후 조정한다.
5. 원인별 최소 커밋으로 측정 결과와 도메인 정책을 동기화한다. 네이티브·DB·의존성·계측 등
   계획 실행 작업의 푸시·배포는 승인 후 진행하고 지원 runtime의 기능 회귀를 확인한다.

### 검토한 대안과 시행착오

- **지금 앱·DB를 열어 측정:** 신고·운영 중단 경계를 넘으므로 채택하지 않는다.
- **무조건 memo·캐시 축소·SDK 업그레이드:** 실제 병목 근거가 없고 요청 증가·호환성 회귀가 가능하다.
- **평균 FPS·JS heap만 확인:** 네이티브 I/O 대기, 이미지·지도 메모리, 긴 프레임을 놓친다.
- **기존 최적화 재구현:** 지도 windowing·구독 격리·원본 ±1 렌더는 이미 적용됐다.
  먼저 효과·경계 조건을 검증하고 과거 마커 캡처·텍스처 폭주·검색 카메라 회귀를 피한다.

### 영향과 재검토 조건

- 새 성능 수치는 실제 측정 이후에만 보고서에 추가한다. 가설·목표를 측정 결과처럼 표시하지 않는다.
- 프로파일 원본은 비공개로 관리하고 저장소에는 위치·사용자 정보가 제거된 요약만 남긴다.
- SDK·runtime 전환, 대규모 데이터 증가, 성능 회귀, 운영·개인정보 경계 변화가 있으면
  이 기록과 계획·관련 도메인·백로그를 함께 갱신한다. 이전 결과는 후속 결정과 연결해 보존한다.

## PERF-002 — 버전업 영향과 최적화 효과를 분리한다

- 날짜: 2026-10-04
- 상태: 활성(패키지 전환·측정 실행 대기)
- 보완 대상: PERF-001과 성능 계획의 실행 순서. 운영 중단·개인정보 경계는 그대로 유지한다.
- 관련 문서: [업그레이드 계획](../package-upgrade-plan.md), [성능 계획](../performance-optimization-plan.md), REL-006

### 배경

재개 버전에서 Expo·RN·라이브러리를 갱신한 뒤 성능을 측정하기로 했다. 구 조합에서 전체 최적화를
먼저 하면 다시 측정해야 하고, 패키지 갱신과 개선 코드를 섞으면 원인·회귀를 구분하기 어렵다.

### 결정

1. 실행이 허용된 기존 바이너리에서 앱 시작·지도·사진 메모리·길안내 시작만 최소 비교 기준으로 남긴다.
   중단 게이트 때문에 실행 불가능하면 미측정으로 기록하고 운영 차단을 우회하지 않는다.
2. 단계별 패키지 전환·기능 안정화를 끝낸 조합을 고정한 뒤 전체 성능을 측정한다.
   그 조합 안에서 실제 병목만 개선하며 업그레이드 commit과 최적화 commit을 나눈다.
3. 구버전→신버전은 버전업 영향, 신버전 기준→동일 패키지 최적화본은 최적화 효과로 보고한다.
   기존 표본이 없으면 버전업 효과를 수치로 단정하지 않는다.
4. 중간 SDK 빌드는 공개·OTA 배포하지 않는다. 서로 다른 네이티브 비교본을 같은 runtime으로
   배포하지 않으며 필요한 설치용 비교 경계는 REL-006에 따라 별도 승인받는다.

### 검토한 대안과 재검토 조건

- 최신 패키지가 항상 더 빠르다고 가정하지 않는다. 실제 회귀·사용자 상태·SDK 기능을 함께 확인한다.
- 구버전 전체 측정을 끝내야 버전업할 수 있다는 조건은 두지 않는다. 최소 기준도 불가능하면
  신버전 기준부터 확보해 최적화 비교를 이어간다.
- 목표 SDK·공급자·계측 도구가 바뀌면 계획과 REL-006을 함께 갱신하고 비교 조건의 차이를 남긴다.

## PERF-003 — 업데이트 중 자원 수명주기를 검토하고 효과는 실측으로 확정

- 날짜: 2026-10-10
- 상태: 활성(소스 개선·로컬 측정 준비 승인, 기기 설치·앱 실측 대기)
- 관련 기록: REL-007, OPS-006, PERF-002

### 결정

1. 패키지 갱신과 함께 위치/방향 구독, 이벤트 listener, 타이머, 요청 취소와 임시 이미지 해제를
   검토한다. 코드로 입증되는 종료 후 작업·중복 구독은 외부 호출 없는 테스트를 붙여 별도 커밋으로 수정한다.
2. 구독 격리·마커 windowing·사진 원본 ±1 렌더 등 기존 최적화는 유지한다. 확인되지 않은 병목을
   이유로 정확도·표시 규칙·데이터 보존을 낮추거나 일괄 memo·캐시 축소를 적용하지 않는다.
3. 개선된 자원 소유권/해제 경계와 미측정 CPU·메모리 효과를 구분해 기록한다. 실기기 release
   계열의 반복 진입·복귀·긴 세션에서 피크/안정 메모리, idle/동작 CPU, hang을 비교해야 효과가 확정된다.
4. 운영 복구·앱 실행·프로파일·네이티브 빌드·배포는 별도 승인 후 진행한다. 중단 게이트를 우회하지 않는다.
   새 조합의 전체 측정 순서와 민감 정보 제거 원칙은 기존 성능 계획과 PERF-002를 유지한다.

### 첫 소스 수정 결과 — MAP-036

- 위치/방향 watch의 비동기 생성이 cleanup보다 늦어지는 경우를 재현하고 늦은 구독도 해제하도록 수정했다.
- 권한·캐시·현재 위치·position/heading 구독 대기, 지연 콜백·연속 세션 등 순수 회귀 테스트를 추가했다.
- 구독 해제 계약은 검증했지만 기기 센서·native 메모리·CPU·배터리 개선은 미측정이다.
  S02/S08/S10에서 기존 High/10m 정확도·지도 따라가기·길안내 동작을 함께 검증한다.

### 2026-10-10 후속 승인·도구 확인

- 1.2.8 측정용 로컬 빌드·기기 설치·프로파일 준비는 사용자가 승인했다. 운영 복구·공급자
  활성화·공개 배포 승인은 별개이며 중단 게이트를 우회하지 않는다.
- 별도 snapshot의 iOS prebuild·plist 검사는 통과했다. macOS 27에서 설치된 Xcode 26.6이
  실행 거부됐고 Instruments 연결도 미완료다. 공용 Xcode 갱신 승인을 요청하고 Pods 다운로드를 중단했다.
- 상세 환경·미완료 항목·재개 순서는 [성능 계획 11절](../performance-optimization-plan.md#11-2026-10-10-실기기-측정-준비-결과--설치실측-미완료)에 남긴다.
  앱 설치·native compile·성능 개선율은 아직 검증되지 않았다.

후속으로 Xcode 27 안정판 업데이트를 승인받아 설치했고 OS 비호환 실행 거부는 사라졌다.
첫 실행의 Apple Xcode·SDK 약관 동의는 별도 사용자 확인 대기다. scene 설정·전체 iOS codegen은
검증했지만 전체 Pods·compile·기기 설치·실측은 아직 미완료다. 법적 동의나 운영 게이트를 우회하지 않는다.

그 뒤 사용자가 약관 동의를 직접 완료했다고 확인했다. Xcode 27.0/27A266a·iOS SDK 27.0·
첫 실행 구성 검사를 통과했고 Instruments에서도 실기기가 온라인으로 확인됐다. Pods 설치를 재개했다.
도구 연결 복구는 성능 개선 결과가 아니며 운영 복구와 공개 배포 승인 경계는 유지한다.
