# 알림 탭과 화면 진입

## NOTIFY-001 — 승인 알림의 상세 요청을 시작·OTA 경계에서도 보존한다

- 날짜: 2026-10-14
- 상태: 소스 보완·1.2.8 iOS OTA 발행 완료(실기기 적용·상세 진입 확인 대기)
- 관련 구현: `lib/push.ts`, `lib/notificationNavigation.ts`,
  `lib/serviceResumeNotification.ts`, `lib/setupServiceResumeNotification.ts`, `app/_layout.tsx`

### 배경과 확인한 사실

운영자가 장소 제보 승인 푸시는 받았지만 탭해도 추가된 장소 상세로 이동하지 않는다고 보고했다.
당시 앱이 완전히 종료돼 있었는지 기억하지 못해 콜드·웜 두 경로를 점검한다.

- 운영 DB 읽기 전용 확인: 최근 승인 알림에 문자열 `placeId`가 있고 해당 장소가 존재하며
  상세 조회용 `all_places` RPC에도 포함된다. 승인 트리거는 `type: place_approved`와 `placeId`를 보낸다.
- 일반 탭 처리는 `content.data`만 읽었고 재개 알림만 iOS 원본 `trigger.payload.body/data`를
  확인했다. 설치된 Expo Notifications 57은 보통 `userInfo.body`에서 data를 만들지만 원문만
  있는 응답도 방어해야 한다. 실제 문제 기기의 원본 응답을 확보한 것은 아니다.
- 루트가 일반 탭을 `none`으로 판단해 시작 중 OTA 다운로드·reload를 허용했다.
  native emitter가 교체되면 활성 앱이 뒤늦게 읽는 마지막 응답이 사라질 수 있다(OPS-012).
- Expo Router의 push는 큐를 사용하므로 단순히 Stack 준비가 늦다는 이유로 확정하지 않는다.

### 결정

1. 명시적인 기본 탭만 처리한다. 가공된 data를 우선하고 iOS push 원문의 body/data를 같은
   파서로 확인한다. 모르는 타입·잘못된 대상 ID에서 새 상세 경로를 만들지 않는다.
2. 승인 장소는 알림 목록과 동일한 `focusPlaceOnMap`으로 지도에 포커스하고 장소 상세를 연다.
   기존 지도 인스턴스를 유지하고 옛 일반 장소의 `kakao*`/`generalPlaceId`를 비워 새 nonce로
   이전 선택이 다시 소비되지 않게 한다. 반려·답변처럼 상세가 없는 알림은 기존
   목록 진입을 유지한다. 재개 알림의 스토어 연결은 루트에만 맡긴다.
3. 유효한 일반 알림은 시작 판정 `navigation`으로 넘겨 해당 실행의 OTA 강제 reload를
   생략한다. 다운로드 도중 들어온 탭도 reload 직전에 다시 확인한다. 알림 없는 시작은 기존 OTA
   확인·다운로드·재시작을 그대로 수행한다. 게이트·동의 우회나 SDK 선행 초기화는 하지 않는다.
4. 콜드 조회보다 새 웜 탭이 우선하고 같은 응답이 1초 안에 연속 전달될 때만 합친다.
   같은 알림을 나중에 다시 탭하면 새 상세 요청으로 처리한다. 언마운트 후에는
   라우팅하지 않는다. 성공한 마지막 응답은 최신 응답이 바뀌지 않았을 때만 비워 재진입을 막는다.
   라우터에 요청을 전달한 것이 실제 장소 시트 표시를 증명하지는 않는다.
5. 서버·DB·알림 기록·푸시 토큰·네이티브 계약은 변경하지 않는다. 테스트 푸시를 무단 발송하지 않는다.

### 검증과 재검토

네이티브 API·라우터 대역으로 실제 앱 JS를 실행해 콜드/웜, 원문 폴백, 초기/다운로드 중
OTA 경계, 중복/늦은 응답, 정리·실패 재시도와 기존 알림 이동을 검사한다.
이는 실기기 푸시→장소 시트 완료 검증을 대체하지 않는다. 재발하면 실제 응답 형태와
지도 요청 소비·조회 취소를 추가 확인하되 토큰·본문·좌표·사용자 ID를 로그에 남기지 않는다.

2026-10-14: 타입 검사, 전체 앱 테스트 231/231, 웹 테스트 5/5, OTA 호환성 검사와
변경 리뷰를 통과했다. 앱/runtime 1.2.8·native 2·API 1은 그대로다.
이 검증 시점에는 실제 기기 승인 알림 응답 확보·테스트 푸시·Git 푸시·OTA 발행은 미실행이었다.

### 2026-10-14 승인 후 배포

운영자가 main 푸시와 1.2.8 OTA 발행을 명시 승인했다. 변경 리뷰와 타입 검사·231개 앱 테스트·
OTA 호환성 검사를 다시 통과한 `b86cdd7`을 origin/main에 푸시했다.

- 채널/브랜치: `production`, 플랫폼: iOS, EAS environment: `production`
- 앱/runtime: `1.2.8`, native bridge: `2`, API 계약: `1` (변경 없음)
- EAS Update 그룹: `49f3d04e-3802-44d2-bd8d-66a3f23aab47`
- iOS 업데이트: `01a135f4-7513-7f2b-a475-f70edd6c4013`
- 발행 시각: `2026-10-13T15:49:35.635Z` (2026-10-14 00:49:35 KST)
- 메시지: `Fix approved place notification tap routing`

별도 iOS export의 source map에서 수정 모듈 5개와 기존 카카오 콜백 모듈이 소스와 정확히
일치함을 확인한 뒤 동일 산출물을 `--skip-bundler`로 발행했다. 발행 결과를 원격 재조회해
업데이트 ID·runtime·iOS·배포 커밋을 확인했다. 거절된 홈페이지 시안은 롤백된 상태이며
운영 홈페이지 파일, DB·푸시 토큰·외부 공급자·네이티브 설정은 수정하지 않았다.

발행은 기기 적용·실제 상세 표시 완료를 의미하지 않는다. 앱을 일반 실행으로 먼저 업데이트한
뒤 승인 알림을 탭해 장소 상세가 열리는지 사용자 확인이 필요하다. 새 빌드나 테스트/전체 재개
푸시를 발송하지 않았으며 실기기 검증을 위해 임의 알림을 추가하지 않는다.

## NOTIFY-002 — 인증 준비 후 토큰을 동기화하고 실패한 로그아웃에서는 연결을 복구한다

- 날짜: 2026-10-14
- 상태: 소스·로컬 회귀 검증 완료, Git 푸시·OTA는 승인 대기
- 관련: `lib/pushTokens.ts`, `components/ActiveRootLayout.tsx`, `stores/useAuthStore.ts`,
  `tests/pushTokens.test.ts`, [AUTH-006](authentication.md#auth-006--늦은-세션-복원은-로그아웃새-인증-상태를-덮어쓰지-않는다)

### 확인한 사실과 해석의 한계

운영 DB 읽기 전용 점검에서 활성 프로필 164개 중 토큰은 6개 계정에 6개였다. 재개 이후
로그인 이력이 있는 4개 계정 중 3개에도 토큰이 없었다. 하지만 OS 알림 권한 상태·과거 등록
실패 이력은 서버에 없어, 나머지 158명이 알림을 거부했거나 전부 버그로 누락됐다고 단정할
수 없다. 로그인 시각도 앱 실행 시각과 동일하지 않다.

기존 등록은 인증 복원과 병렬로 한 번 실행돼 세션 준비 전 건너뛸 수 있었고, 로그인·설정
권한 변경 뒤 복구 경로와 DB 반환 오류 확인이 없었다. iOS 임시 허용도 등록 대상에서 빠졌다.
실제 모듈의 대역 검사로 로그아웃 실패 시 로그인은 유지되지만 토큰만 삭제되는 경로도 재현했다.
토큰 직접 삭제용 주기 작업이나 사용자 정의 트리거는 발견하지 않았다.

### 결정

1. 활성 루트에서 인증·동의 복원이 끝난 로그인 계정으로 동기화를 시작한다. 로그인 직후,
   앱이 다시 활성화될 때, APNs/FCM 토큰 변경 때 재등록한다. 자동 동기화에서는 권한 창을
   띄우지 않고 기존 알림·제보 화면의 명시적 권한 요청은 유지한다. iOS 정식·임시·일시 허용을
   인정하되 조용한 전달 등 실제 표시 방식은 OS 설정에 따른다.
2. 세션·Expo 토큰·DB·캐시 오류를 검사한다. 일시 실패는 1.5초·5초 간격으로 최대 두 번
   추가 시도한다. 설정·스키마·소유권 오류는 재시도로 감추지 않는다. 읽기·토큰 조회는 12초
   제한, DB 요청은 AbortSignal로 취소하며 쿼리가 끝나기 전 직렬 큐를 풀지 않는다. 사용자 권한
   선택과 취소할 수 없는 캐시 쓰기는 타임아웃 경쟁으로 방치하지 않는다.
3. 같은 등록은 합치고 등록·삭제·로그아웃을 직렬화한다. 계정·요청 세대가 바뀐 늦은 결과는
   무시한다. DB 저장 후에만 캐시를 갱신하고, 토큰 교체 시 이전 토큰은 같은 계정의 해당 기기
   연결만 삭제한다. 설정에서 권한을 거부하면 현재 기기의 알려진 연결만 해제한다.
4. 로그아웃은 토큰 해제를 마친 뒤 실행한다. 정리 실패는 사용자에게 재시도를 안내하며 로그인
   성공 해제로 표시하지 않는다. 인증 로그아웃 또는 마지막 세션 확인이 실패하면 동일 계정의
   토큰 재등록을 시도한다. 정리 중 계정이 바뀌면 새 계정을 로그아웃하거나 옛 계정을 덮어쓰지
   않는다. 복구까지 네트워크가 실패한 경우 즉시 복구를 보장하지 않으며 다음 활성화에서 다시 시도한다.
5. RLS와 데이터 모델은 유지한다. 정상적인 A 로그아웃→B 로그인은 A 연결 삭제 후 B로
   등록한다. 과거에 다른 계정 소유로 남은 동일 토큰은 기존 RLS가 막으므로 임의 이전하지
   않는다. 이 예외는 소유 확인과 별도 승인된 서버 정비가 필요하다. 로그인 계정만 바꿔
   다른 사용자의 토큰을 가져오는 함수나 서비스 키를 앱에 추가하지 않는다.
6. 최종 실패는 단계·제한된 기술 오류 코드와 고정 문구만 Sentry warning으로 보고한다.
   같은 단계·코드는 프로세스 내 5분간 중복 보고하지 않는다. 공급자 오류 원문·푸시 토큰·사용자
   식별자·좌표를 새 진단 필드에 복제하지 않는다. 일반 권한 거부·취소는 장애로 보고하지 않는다.

### 검증과 재검토

실제 앱 모듈에 네이티브·인증·DB·시간 대역을 연결한 회귀 검사로 인증 준비, 권한 변경,
임시 허용, 재시도·늦은 응답, 토큰 회전, 직렬화, 계정 전환, 로그아웃 실패 복구를 확인한다.
대역 검사는 실제 APNs 토큰 발급·실기기 권한 설정 왕복·운영 DB 등록 성공을 대신하지 않는다.
DB·RLS·의존성·네이티브·runtime은 바꾸지 않았고 새 알림도 발송하지 않았다.
Git 푸시·1.2.8 OTA는 운영자의 별도 승인을 받은 뒤 수행한다.

타입 검사, OTA 호환성 검사(app 1.2.8/native 2/API 1)를 통과했다. 추가 코드 리뷰의 계정 전환·
최종 세션 확인 실패 경합 두 건을 수정하고 재검토를 통과했다. 실기기·운영 반영은 아직 하지 않았다.
