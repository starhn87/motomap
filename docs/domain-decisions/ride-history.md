# 라이딩 경로 기록과 리플레이

모토맵 길안내 중의 실제 이동 경로를 개인 기록으로 보존하고, 개별 라이딩 리플레이와
누적 라이딩 지도로 보여주는 기준을 기록한다.

관련·예정 구현:

- `app/navi.tsx`, `lib/guideEvents.ts`, `lib/guideSession.ts`
- `lib/rideRecorder.ts`, `lib/api/rideSessions.ts`
- `app/my-rides.tsx`, `app/ride-map.tsx`, `app/ride/[id].tsx`
- `public.ride_sessions`, `public.place_rides`

## 먼저 확인할 활성 원칙

1. 경로 기록은 로그인 사용자가 명시적으로 켠 뒤, 실제 모토맵 길안내 중이면서 앱이
   포그라운드인 동안에만 수행한다. 미리보기·시뮬레이션과 일반 지도 사용은 기록하지 않는다.
2. 출발 전에 계산한 `예정 경로`와 GPS로 수집한 `실제 경로`를 구분한다. 누락 구간을 예정
   경로나 직선으로 채워 실제로 달린 경로처럼 표현하지 않는다.
3. 기존 `place_rides`에는 실제 경로가 없으므로 과거 이동 경로를 역산하지 않는다. 과거 기록은
   방문 장소만 보여주고, 실제 경로는 기능을 켠 다음 길안내부터 쌓는다.
4. GPS 원본을 실시간으로 서버에 전송하지 않는다. 기기에서 임시 보존한 뒤 이상점을 제거하고
   단순화한 여러 선분과 요약 수치만 본인 비공개 데이터로 저장한다.
5. 경로 기록 실패가 길안내·도착 기록·리뷰 제안을 방해해서는 안 된다. 네트워크 실패는 로컬
   동기화 대기열로 넘기고 길안내 흐름에서는 조용히 격리한다.
6. 경로·목적지·출발지 좌표는 PostHog나 Sentry에 보내지 않는다. 진단에는 좌표 개수, 기록
   품질, 지속 시간처럼 위치를 복원할 수 없는 수치만 사용한다.
7. 투어 묶기·사진·회고는 `ride_sessions`가 안정적으로 쌓인 뒤 그 위에 구현한다. 경로 기반이
   없는 별도의 투어 원장을 먼저 만들지 않는다.

## RIDE-001 — 포그라운드 길안내 중에만 실제 경로를 기록한다

- 날짜: 2026-08-26
- 상태: 활성(구현 전)
- 관련 구현: `app/navi.tsx`, `lib/guideEvents.ts`, `hooks/useUserLocation.ts`

### 배경

목적지 도착 횟수만으로도 다녀온 장소는 알 수 있지만, 어느 도로와 지역을 반복해서 달렸는지는
알 수 없다. 라이딩 경로를 빠르게 재생하고 한 지도에 누적하면 내 바이크와 함께한 이동 영역을
직관적으로 돌아볼 수 있고, 장소 목록보다 라이더의 정체성을 강하게 표현할 수 있다.

바이크 길안내는 대체로 화면을 켜고 KNSDK를 보며 진행한다. 항상 위치를 추적하거나 별도의
백그라운드 기록 권한을 사용하는 것은 얻는 정보에 비해 배터리·개인정보·심사 부담이 크다.

### 결정

`onGuideStarted`에서 실제 라이딩 세션을 만들고 `Location.watchPositionAsync`를 시작한다.
기록 조건은 로그인, 사용자 동의, 실제 안내 모드, `AppState=active`를 모두 만족할 때다.
앱이 비활성화되면 구독을 중지하고 현재 선분을 닫는다. 안내가 계속되는 상태에서 앱이 다시
활성화되면 새 선분으로 기록을 재개한다.

초기 수집 기준은 `Accuracy.High`, 이동 거리 약 20m, 보조 시간 간격 약 5초로 잡고 실기기
결과로 조정한다. 정확도가 나쁜 점과 물리적으로 불가능한 순간 이동을 제외하고, 긴 시간 간격이나
앱 비활성화 경계는 별도 선분으로 나눈다. 거리 계산은 단순화 전 유효 좌표로 수행하고 지도 표시용
경로는 약 10~20m 허용 오차로 단순화한다.

라이딩 중 좌표는 앱 샌드박스의 임시 파일에 주기적으로 저장한다. 정상 종료하면 서버 동기화 후
지우고, 앱이 강제 종료되면 다음 실행에서 `일부 기록`으로 복구한다. 업로드가 실패하면 파일을
유지하고 로그인·네트워크가 다시 유효할 때 재시도한다.

iOS의 `UIBackgroundModes: location`과 Always 사용 설명은 KNSDK가 초기화 과정에서 자체
백그라운드 위치 업데이트를 켜기 때문에 이미 필요하다. 이를 제거하면 CoreLocation 예외로 앱이
종료될 수 있다. 이 네이티브 선언을 유지하는 것과 모토맵 경로 기록기가 백그라운드 위치 API를
사용하지 않는 것은 별개의 결정이다. 새 기록기는 `TaskManager`나
`Location.startLocationUpdatesAsync`를 사용하지 않는다.

### 데이터와 화면 경계

`ride_sessions`는 한 번의 실제 길안내를 나타낸다. 사용자·바이크 스냅샷, 시작·종료 시각,
최종 목적지, 예정·실제 거리, 경로 우선순위, 도착·취소·중단 상태, 기록 품질을 저장한다. 예정
경로는 `LineString`, 실제 경로는 중간 누락을 보존할 수 있는 `MultiLineString`으로 저장한다.
`place_rides`에는 nullable `ride_session_id`를 추가해 도착 기록과 연결하되 구버전 삽입 계약은
그대로 유지한다. 모든 쓰기는 본인 여부, 좌표 범위·개수, 중복 세션을 검증하고 RLS로 본인만
조회·삭제할 수 있게 한다.

`주행 기록`에는 누적 경로 지도와 최근 라이딩을 추가하고 기존 장소별 도착 통계는 유지한다.
개별 리플레이는 단순화한 실제 경로를 약 12~18초에 재생하며, 선을 점차 그리고 바이크 마커와
카메라는 제한된 핵심 지점에서만 갱신한다. 비활성화로 빠진 구간은 화면에서도 연결하지 않는다.
누적 지도는 우선 반투명 경로를 겹쳐 자주 달린 길이 자연스럽게 진해지도록 하고, 기록량으로
성능 문제가 확인된 뒤에만 서버 구간 집계를 추가한다.

### 검증과 구현 순서

첫 단계는 KNSDK 화면이 열린 실기기에서 포그라운드 Expo 위치 구독이 유지되는지 확인하는
진단 구현이다. 개발 단계에서 좌표 수신 횟수·거리·누락 구간과 기록 경로를 한 화면에 보여주고,
사용자는 약 10분의 실제 주행 한 번으로 결과를 확인한다. 정상 주행, 앱 전환·복귀, GPS 유실,
안내 취소·도착, 오프라인, 강제 종료 복구와 장시간 발열은 이후 단계에서 나누어 검증한다.

구현 순서는 실기기 가능성 검증, 추가형 DB·RLS·RPC, 좌표 필터·단순화, 로컬 임시 파일·재시도,
길안내 수명주기 연동, 설정·최초 동의, 최근 기록·누적 지도, 리플레이, 삭제·내 데이터·분석 보완
순으로 한다. 네이티브 계약을 바꾸지 않고 검증되면 DB 마이그레이션 뒤 현재 런타임 OTA로
배포한다. KNSDK 화면에서 JS 위치 구독이 유지되지 않는다는 실증이 있을 때만 네이티브 위치
이벤트 브리지를 새 빌드 범위로 재검토한다.

### 검토한 대안과 시행착오

백그라운드 위치를 항상 기록하면 화면 잠금과 앱 전환도 이어지지만 현재 사용 맥락에는 과하고,
권한 설명과 배터리·개인정보 부담이 커 채택하지 않았다. 예정 경로만 저장하는 방식은 간단하지만
경로 이탈·재탐색을 실제 이동으로 오인하게 한다. 앱이 비활성화된 두 좌표를 직선으로 잇는 방식도
실제로 지나지 않은 도로를 그릴 수 있어 사용하지 않는다.

### 영향과 재검토 조건

실사용에서 화면 잠금·앱 전환 때문에 유효 경로가 자주 절반 이하로 남거나, KNSDK 화면 중 JS
구독이 비결정적으로 멈추면 백그라운드 또는 네이티브 기록을 재검토한다. 공개 공유를 추가할 때는
출발·도착 주변 숨김과 위치 공개 동의를 별도 결정으로 기록한다.
