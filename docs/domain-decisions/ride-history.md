# 라이딩 경로 기록과 라이딩 지도 Visualizer

모토맵 길안내 중의 실제 이동 경로를 개인 기록으로 보존하고, 선택한 기간의 여러 라이딩을
지도 위에서 빠르게 재생하는 Visualizer와 누적 라이딩 지도로 보여주는 기준을 기록한다.

관련 구현:

- `app/navi.tsx`, `lib/guideEvents.ts`, `lib/guideSession.ts`
- `lib/rideRecorder.ts`, `lib/api/rideSessions.ts`
- `lib/rideRecordingPreference.ts`, `lib/api/rideRecordingConsent.ts`
- `app/my-rides.tsx`, `app/ride-map.tsx`, `app/ride/[id].tsx`
- `docs/ride-map-testflight-checklist.md`
- `public.ride_sessions`, `public.place_rides`

## 먼저 확인할 활성 원칙

1. 경로 기록은 로그인 사용자가 명시적으로 켠 뒤, 실제 모토맵 길안내 중이면서 앱이
   포그라운드인 동안에만 수행한다. 미리보기·시뮬레이션과 일반 지도 사용은 기록하지 않는다.
2. 출발 전에 계산한 `예정 경로`와 GPS로 수집한 `실제 경로`를 구분한다. 누락 구간을 예정
   경로나 직선으로 채워 실제로 달린 경로처럼 표현하지 않는다.
3. 기존 `place_rides`에는 실제 경로가 없으므로 과거 이동 경로를 역산하지 않는다. 과거 기록은
   방문 장소만 보여주고, 실제 경로는 기능을 켠 다음 길안내부터 쌓는다.
4. GPS 원본을 실시간으로 서버에 전송하지 않는다. 기기에서 임시 보존한 뒤 이상점을 제거하고
   단순화한 여러 선분과 요약 수치만 본인 비공개 데이터로 저장한다.
5. 경로 기록 실패가 길안내·도착 기록·리뷰 제안을 방해해서는 안 된다. 네트워크 실패는 로컬
   동기화 대기열로 넘기고 길안내 흐름에서는 조용히 격리한다.
6. 경로·목적지·출발지 좌표는 PostHog나 Sentry에 보내지 않는다. 진단에는 좌표 개수, 기록
   품질, 지속 시간처럼 위치를 복원할 수 없는 수치만 사용한다.
7. 투어 묶기·사진·회고는 `ride_sessions`가 안정적으로 쌓인 뒤 그 위에 구현한다. 경로 기반이
   없는 별도의 투어 원장을 먼저 만들지 않는다.
8. 집·회사 도착은 실제 주행 자체를 지우지 않지만 장소 방문 횟수, 바이크별 방문, 추천·운영
   후보 신호에서는 제외한다. 개인 목적지 여부는 기기에서만 판단하고 서버에는 일반적인 제외
   플래그만 남긴다.
9. 핵심 결과물은 방문 장소를 날짜별로 나열하는 타임라인이 아니라, 모토맵 길안내로 쌓인 여러
   실제 경로를 기간·바이크별로 골라 지도 위에서 시간순으로 빠르게 재생하는 `라이딩 지도`다.
   개별 라이딩 상세와 방문 장소는 이 지도를 보조하는 탐색 수단으로 둔다.

## RIDE-001 — 포그라운드 길안내 중에만 실제 경로를 기록한다

- 날짜: 2026-08-26
- 상태: 활성
- 관련 구현: `app/navi.tsx`, `lib/guideEvents.ts`, `hooks/useUserLocation.ts`

### 배경

목적지 도착 횟수만으로도 다녀온 장소는 알 수 있지만, 어느 도로와 지역을 반복해서 달렸는지는
알 수 없다. 라이딩 경로를 빠르게 재생하고 한 지도에 누적하면 내 바이크와 함께한 이동 영역을
직관적으로 돌아볼 수 있고, 장소 목록보다 라이더의 정체성을 강하게 표현할 수 있다.

바이크 길안내는 대체로 화면을 켜고 KNSDK를 보며 진행한다. 항상 위치를 추적하거나 별도의
백그라운드 기록 권한을 사용하는 것은 얻는 정보에 비해 배터리·개인정보·심사 부담이 크다.

### 결정

`onGuideStarted`에서 실제 라이딩 세션을 만들고 `Location.watchPositionAsync`를 시작한다.
기록 조건은 로그인, 사용자 동의, 실제 안내 모드, `AppState=active`를 모두 만족할 때다.
앱이 비활성화되면 구독을 중지하고 현재 선분을 닫는다. 안내가 계속되는 상태에서 앱이 다시
활성화되면 새 선분으로 기록을 재개한다.

초기 수집 기준은 `Accuracy.High`, 이동 거리 약 20m, 보조 시간 간격 약 5초로 잡고 실기기
결과로 조정한다. 정확도가 나쁜 점과 물리적으로 불가능한 순간 이동을 제외하고, 긴 시간 간격이나
앱 비활성화 경계는 별도 선분으로 나눈다. 거리 계산은 단순화 전 유효 좌표로 수행하고 지도 표시용
경로는 약 10~20m 허용 오차로 단순화한다.

라이딩 중 좌표는 앱 샌드박스의 임시 파일에 주기적으로 저장한다. 정상 종료하면 서버 동기화 후
지우고, 앱이 강제 종료되면 다음 실행에서 `일부 기록`으로 복구한다. 업로드가 실패하면 파일을
유지하고 로그인·네트워크가 다시 유효할 때 재시도한다.

iOS의 `UIBackgroundModes: location`과 Always 사용 설명은 KNSDK가 초기화 과정에서 자체
백그라운드 위치 업데이트를 켜기 때문에 이미 필요하다. 이를 제거하면 CoreLocation 예외로 앱이
종료될 수 있다. 이 네이티브 선언을 유지하는 것과 모토맵 경로 기록기가 백그라운드 위치 API를
사용하지 않는 것은 별개의 결정이다. 새 기록기는 `TaskManager`나
`Location.startLocationUpdatesAsync`를 사용하지 않는다.

### 데이터와 화면 경계

`ride_sessions`는 한 번의 실제 길안내를 나타낸다. 별도 보관 동의, 사용자·바이크 스냅샷, 시작·종료 시각,
최종 목적지, 실제 거리, 도착·취소·중단 상태, 기록 품질을 저장한다. Visualizer에는 경로 모양뿐
아니라 재생 순서를 위한 시간이 필요하므로 실제 경로의 기준 데이터는 끊김을 보존한 선분별
`[longitude, latitude, elapsed_ms]` JSON 배열로 저장한다. 지도 표시 외에 서버 공간 검색이
실제로 필요해질 때만 이 배열에서 PostGIS `MultiLineString` 파생값을 추가한다. 두 표현을 처음부터
함께 받아 서로 다른 원본이 생기게 하지 않는다. 예정 경로는 실제 이동으로 오인할 여지가 있고
초기 Visualizer가 사용하지 않으므로 첫 스키마에는 저장하지 않는다.

`place_rides`에는 nullable `ride_session_id`를 추가해 도착 기록과 연결하되 구버전 삽입 계약은
그대로 유지한다. 모든 쓰기는 활성 동의, 본인 여부, 좌표 범위·개수, 중복 세션을 검증하고 RLS로 본인만
조회·삭제할 수 있게 한다. 경로 행은 완료 뒤 불변으로 취급해 클라이언트에는 조회·삽입·삭제만
허용하고 수정 권한은 열지 않는다.

`주행 기록`의 중심 화면은 `라이딩 지도`로 바꾼다. 사용자가 기간과 바이크를 고르면 해당 범위의
여러 실제 경로를 시간순으로 빠르게 재생하고, 재생이 끝나면 누적 경로를 한 화면에 남겨 자주
달린 도로와 지역을 직관적으로 보여준다. 최근 라이딩과 기존 장소별 도착 통계는 지도에서 개별
세션이나 장소로 들어가는 보조 목록으로 유지한다. 개별 라이딩 상세에서도 같은 재생 엔진을
하나의 세션에 한정해 재사용한다. 구체적인 화면·재생 규칙은 RIDE-003을 따른다.

### 검증과 구현 순서

첫 단계는 KNSDK 화면이 열린 실기기에서 포그라운드 Expo 위치 구독이 유지되는지 확인하는
진단 구현이다. 개발 단계에서 좌표 수신 횟수·거리·누락 구간과 기록 경로를 한 화면에 보여주고,
사용자는 약 10분의 실제 주행 한 번으로 결과를 확인한다. 정상 주행, 앱 전환·복귀, GPS 유실,
안내 취소·도착, 오프라인, 강제 종료 복구와 장시간 발열은 이후 단계에서 나누어 검증한다.

구현 순서는 실기기 가능성 검증, 추가형 DB·RLS·RPC, 좌표 필터·단순화, 로컬 임시 파일·재시도,
길안내 수명주기 연동, 설정·최초 동의, 정적 누적 지도, Visualizer 재생 엔진, 기간·바이크 필터,
개별 라이딩 상세, 삭제·내 데이터·분석 보완 순으로 한다. 네이티브 계약을 바꾸지 않고 검증되면
DB 마이그레이션 뒤 현재 런타임 OTA로 배포한다. KNSDK 화면에서 JS 위치 구독이 유지되지 않는다는
실증이 있을 때만 네이티브 위치 이벤트 브리지를 새 빌드 범위로 재검토한다.

### 검토한 대안과 시행착오

백그라운드 위치를 항상 기록하면 화면 잠금과 앱 전환도 이어지지만 현재 사용 맥락에는 과하고,
권한 설명과 배터리·개인정보 부담이 커 채택하지 않았다. 예정 경로만 저장하는 방식은 간단하지만
경로 이탈·재탐색을 실제 이동으로 오인하게 한다. 앱이 비활성화된 두 좌표를 직선으로 잇는 방식도
실제로 지나지 않은 도로를 그릴 수 있어 사용하지 않는다.

### 영향과 재검토 조건

실사용에서 화면 잠금·앱 전환 때문에 유효 경로가 자주 절반 이하로 남거나, KNSDK 화면 중 JS
구독이 비결정적으로 멈추면 백그라운드 또는 네이티브 기록을 재검토한다. 공개 공유를 추가할 때는
출발·도착 주변 숨김과 위치 공개 동의를 별도 결정으로 기록한다.

## RIDE-002 — 집과 회사는 주행 경로가 아니라 장소 방문 통계에서 제외한다

- 날짜: 2026-08-26
- 상태: 활성
- 관련 구현: `lib/ridePlaceStats.ts`, `components/PersonalPlaceRideSync.tsx`,
  `supabase/migrations/20260826042447_exclude_personal_destinations_from_place_stats.sql`,
  `supabase/migrations/20260826043743_harden_personal_place_ride_rpcs.sql`

### 배경

집으로 돌아가는 이동은 라이딩 거리와 실제 동선에는 분명 포함되지만, 집을 가장 많이 방문한
장소나 특정 바이크가 자주 찾는 장소로 보여 주는 것은 기록의 의미를 흐리고 사생활 노출 위험도
키운다. 회사 역시 통근 목적지일 뿐 라이더에게 추천할 장소라는 신호는 아니므로 같은 기준이
필요하다. 반대로 해당 도착 행을 삭제하면 앞으로 `ride_sessions`와 연결할 실제 주행 맥락까지
잃게 된다.

### 결정

집과 회사는 동일하게 처리한다. 도착·경유 사실을 담은 `place_rides` 행은 보존하되
`excluded_from_place_stats=true`로 표시한다. 이 행은 내 장소별 주행 목록과 횟수, 공개 장소
방문·기종 집계, 바이크-장소 매칭, 미등록 장소 운영 후보에서 제외한다. 앞으로 실제 경로를 담을
`ride_sessions`의 거리·시간·경로와 완주 상태는 제외하지 않는다.

새 도착은 로컬에 저장된 집·회사와 40m 이내인지 기기에서 판정해 처음부터 제외 플래그를 함께
기록한다. 40m는 장소 공급자별 대표 좌표 차이를 흡수하기 위한 통계 전용 허용치이며, 집·회사
버튼의 선택 상태 판정은 기존의 엄격한 좌표 비교를 유지한다.

과거 기록도 집·회사 좌표를 서버로 보내지 않는다. 로그인한 사용자의 미제외 도착 기록 ID와
목적지 좌표를 내려받아 기기 안에서 비교하고, 일치한 기록 ID만 본인 한정 RPC로 보낸다. DB에는
집/회사 구분, 로컬 저장 이름·주소, 새 개인 좌표를 추가하지 않는다. 한 번 제외된 행은 나중에
집·회사 설정을 지워도 다시 집계하지 않는다. 같은 카페를 어떤 사용자가 회사로 저장해도 그
사용자의 방문만 제외되고 다른 라이더의 집계에는 영향을 주지 않는다.

### 검토한 대안과 시행착오

도착 행 자체를 삭제하면 장소 통계는 단순하지만 실제 주행 세션과의 연결 및 감사 가능성을 잃어
채택하지 않았다. 조회할 때마다 현재 집·회사 좌표로만 거르면 설정을 삭제한 순간 과거 집 방문이
다시 노출된다. 집/회사 타입이나 좌표를 서버에 저장하면 집계는 쉬워지지만 로컬 전용 개인 장소
정책을 불필요하게 넓힌다. 좌표를 보정 RPC 인자로 보내는 초안도 검토했으나, 본인 기록을 내려받아
로컬 비교 후 ID만 보내는 방식으로 바꿨다.

### 영향과 재검토 조건

사용자가 집·회사를 잘못 저장하면 해당 반경의 과거 장소 방문 통계도 계속 제외된다. 실제 사용에서
복구 요청이 확인되면 전체 행을 되살리는 토글이 아니라, 본인에게만 대상과 영향을 보여 주는 명시적
복원 흐름을 별도 결정으로 설계한다. 40m 안에 서로 다른 장소가 밀집해 오탐이 확인되면 공급자 ID
우선 비교와 반경 축소를 검토한다.

## RIDE-003 — 여러 라이딩을 시간순으로 빠르게 재생하는 지도를 핵심 경험으로 둔다

- 날짜: 2026-08-27
- 상태: 활성
- 관련 구현: `app/ride-map.tsx`, `components/rides/RideMapVisualizer.tsx`,
  `lib/ridePlayback.ts`, `lib/api/rideSessions.ts`

### 배경

원래 의도한 기능은 Google 지도 타임라인처럼 방문 장소와 이동 내역을 일자별 목록으로 관리하는
기능이 아니다. 타임라인 데이터를 Visualizer로 시각화할 때처럼, 여러 날에 걸쳐 쌓인 이동 경로가
지도 위에서 빠르게 그려지며 `내가 어느 길과 지역을 많이 달렸는지`를 한눈에 돌아보는 경험이다.

모토맵은 상시 위치 기록을 하지 않으므로 하루의 모든 이동이나 생활 장소를 복원하지 않는다.
사용자가 기록을 켜고 모토맵 길안내를 사용한 실제 라이딩만 재료로 삼는다. 따라서 누락 없는 생활
타임라인을 흉내 내기보다 제한된 기록 범위를 솔직히 보여주고, 그 안에서 라이딩 정체성과 재미를
강하게 만드는 것이 목표다.

### 핵심 화면

`라이딩 지도`는 다음 구조로 시작한다.

1. **범위 선택**: 최근 30일, 올해, 보관 중인 전체 기록을 제공한다. 사용자 지정 기간은 실제
   기록이 늘어 반복 수요가 확인될 때 추가한다.
2. **바이크 선택**: 전체 바이크 또는 내 차고의 특정 바이크 기록만 고른다. 세션에 저장한 바이크
   스냅샷을 사용하므로 이후 차고에서 바이크를 삭제해도 당시 기록의 정체성은 유지한다.
3. **요약**: 선택 범위의 라이딩 횟수, 실제 기록 거리, 주행 시간을 재생 전후에 간결하게 보여준다.
4. **지도 재생**: 선택한 세션을 오래된 순서부터 빠르게 재생한다. 실제 선분이 진행 방향대로
   늘어나고 바이크 마커가 현재 재생 위치를 따라간다.
5. **누적 결과**: 재생이 끝나면 모든 경로를 지도에 남긴다. 같은 도로를 여러 번 달린 부분은
   반투명 선이 겹쳐 자연스럽게 더 진해져 자주 달린 길과 활동 지역이 드러난다.
6. **세부 탐색**: 지도 경로나 보조 목록에서 개별 라이딩을 선택하면 날짜·목적지·바이크·거리와
   해당 세션만의 리플레이를 연다. 방문 장소 목록은 핵심 화면을 대체하지 않는다.

초기 필터에는 목적지·지역·요일 같은 세분화를 넣지 않는다. 실제 기록이 충분히 쌓여 사용자가
기간과 바이크 외의 구분을 반복해서 필요로 할 때 추가한다.

### 재생 규칙

- 재생 시간은 원래 주행 시간과 1:1로 대응하지 않는다. 선택한 전체 기록을 기본 약 20~30초 안에
  볼 수 있도록 거리와 세션 수에 따라 압축하고, 사용자가 `1×·2×·4×`로 조절할 수 있게 한다.
- GPS 점의 원래 시간 순서는 유지하되 정차 시간은 압축한다. 서로 다른 세션과 비활성화로 끊긴
  선분 사이에는 선을 그리지 않는다. 다음 시작점으로 넘어갈 때는 마커를 잠시 숨기고 카메라만
  이동해 존재하지 않는 이동 경로를 만들지 않는다.
- 카메라는 마커를 매 프레임 중앙에 고정하지 않는다. 현재 경로가 안전 영역 밖으로 나갈 때만
  부드럽게 이동하고, 세션 전환에서는 전체를 잠깐 조망한 뒤 다음 출발점으로 이동한다. 빠른 재생
  중 과도한 확대·축소와 흔들림을 피한다.
- 재생 중에는 일시정지·다시 시작·처음부터 보기와 진행 위치 탐색을 제공한다. 앱이 비활성화되면
  재생을 멈추고 복귀 시 같은 위치에서 이어간다.
- 예정 경로는 재생하지 않는다. 실제 GPS 경로만 그리고, 품질이 낮거나 일부만 기록된 세션은
  목록과 재생 시작 시 `일부 기록`으로 표시한다.

### 렌더링과 데이터 전략

첫 구현은 저장된 단순화 경로를 클라이언트에서 합성한다. 매 GPS 점마다 React 상태와 네이티브
Polyline 전체를 다시 만들지 않고, 경로를 화면 재생용 청크로 미리 나눠 낮은 빈도로 공개한다.
바이크 마커와 카메라도 같은 제한된 틱에서만 갱신해 네이티브 지도 텍스처와 브리지 호출 폭주를
피한다.

서버에는 기기에서 이미 단순화한 선분만 저장한다. 초기 구현은 최대 1년의 보관 범위에서 100개
세션씩 커서 페이지를 순차 조회한 뒤 클라이언트에서 합성한다. 로드 시간이 길어지거나 메모리·프레임
저하가 확인되면 목록·요약과 경로 조회를 분리하고 기간별 추가 단순화 또는 서버 구간 집계를
도입한다. 서버 집계로 바꾸더라도 개별 라이딩의 단순화 선분과 누락 경계는 보존한다.

### 검증과 단계별 구현

1. **기록 가능성 검증**: KNSDK 길안내 중 Expo 위치 구독이 유지되는지 약 10분 실주행 한 번으로
   확인한다. 이 단계만 실제 바이크 주행이 필요하다.
2. **기록 기반 구축**: DB·RLS·동기화 대기열과 실제/예정 경로 분리를 구현한다.
3. **정적 라이딩 지도**: 기간·바이크 필터와 선택 범위의 누적 경로를 먼저 보여줘 데이터 정확도와
   지도 성능을 확인한다.
4. **Visualizer 재생**: 실주행을 기다리지 않고 익명 합성 경로 테스트로 선분 간 공백, 시간 정렬,
   거리 기반 보간을 검증하고 카메라, 속도 조절과 일시정지는 실기기에서 확인한다.
5. **실제 기록 검증**: 정상 종료, 앱 전환·복귀, GPS 유실, 경로 이탈·재탐색, 안내 취소·도착,
   오프라인과 강제 종료 복구가 지도에서 허위 연결 없이 표현되는지 확인한다.
6. **개별 상세와 운영 보완**: 개별 리플레이, 삭제·내 데이터, 비식별 성능 계측을 연결한다.

### 검토한 대안과 영향

일별 방문 장소 목록을 첫 화면으로 두면 기존 `place_rides`만으로도 빨리 만들 수 있지만 사용자가
원한 경로 시각화와 자주 달린 지역의 발견이 약해 채택하지 않는다. 모든 경로를 실제 시간 비율로
재생하면 장거리 라이딩에서 지루하고, 모든 점을 동일 속도로 넘기면 GPS 밀도 차이 때문에 화면
속도가 불규칙하므로 전체 재생 목표 시간에 맞게 시간축을 압축한다.

이 화면은 본인만 볼 수 있는 개인 기록으로 시작한다. 향후 영상·이미지 공유를 추가하면 집·회사
설정과 무관하게 각 세션 시작·종료 주변을 숨기는 규칙과 명시적 공개 동의를 먼저 설계한다. 기록이
적은 초기 상태에서는 빈 지도를 보여주지 않고 `길안내를 시작하면 달린 길이 여기에 그려져요`라는
설명과 기록 설정 진입을 제공한다.

## RIDE-004 — 경로 기록은 기능별 별도 동의와 최대 1년 보관을 강제한다

- 날짜: 2026-08-28
- 상태: 활성
- 관련 구현: `lib/api/rideRecordingConsent.ts`, `lib/rideRecordingPreference.ts`,
  `app/settings.tsx`, `supabase/migrations/20260828010941_add_ride_sessions.sql`,
  `constants/legal.ts`

### 배경

실제 이동 경로는 계정과 결합된 개인위치정보다. 기존 개인정보 처리방침과 위치기반 서비스
이용약관에는 연속 경로를 서버에 저장하지 않는다고 적혀 있었으므로 단순 설정 토글만 추가하면
문서와 실제 동작이 어긋난다. 위치정보법상 고지한 목적과 동의 범위 안에서만 이용해야 하고,
별도 동의로 보관하더라도 동의일부터 최대 1년이라는 경계를 제품과 DB가 함께 지켜야 한다.

### 결정

경로 기록을 처음 켤 때 수집 대상, 포그라운드 한정, 서버 저장, 본인 전용, 보관기간, 중지와
삭제의 차이를 한 화면에서 알리고 별도 동의를 받는다. 동의는 서버의
`ride_recording_consents`에 고정된 정책 버전·동의 시각·만료 시각으로 남긴다. 기기에는 동의 ID와
만료 시각, 새 기록 활성화 여부를 계정별로 저장한다. 재설치·다른 기기에서는 자동으로 새 기록을
켜지 않으며 다시 명시적으로 켜야 한다.

`ride_sessions` 삽입은 같은 사용자의 만료되지 않고 철회되지 않은 동의 ID를 반드시 요구한다.
RLS는 만료 즉시 경로를 숨기고, `pg_cron`이 만료된 동의에 연결된 경로를 5분 주기로 물리 삭제한다.
재동의는 앞으로 수집할 경로에만 적용하며 과거 동의의 경로 보관기간을 연장하지 않는다.

설정 토글을 끄는 것은 새 수집의 일시 중지다. 기존 경로는 동의 만료 전까지 유지하고 개별 상세에서
삭제할 수 있다. `경로 전체 삭제 및 동의 철회`는 서버 경로, 기기의 미동기화 파일, 활성 동의를
함께 제거한다. 계정 탈퇴도 외래키 연쇄 삭제로 같은 결과를 낸다.

경로 좌표·목적지는 PostHog 이벤트와 Sentry 진단에 넣지 않는다. PostHog 화면 리플레이에서는
네이티브 지도뿐 아니라 라이딩 지도와 개별 상세 화면 전체를 `PostHogMaskView`로 가린다. 향후
리플레이 설정이나 화면 구조를 바꾸기 전에는 실제 경로·목적지 노출 여부를 다시 검토한다.

### 검토한 대안과 재검토 조건

로컬 토글 값만 동의 증적으로 쓰면 다른 기기와 서버의 삽입 계약을 검증할 수 없어 채택하지 않았다.
회원 탈퇴 전까지 무기한 보관하는 방식은 장기 누적 지도에는 유리하지만 위치정보 보관 경계를
위반할 위험이 있어 채택하지 않았다. 장기 회고 수요가 확인되면 원본 개인 경로의 보관기간을 늘리는
대신, 사용자가 직접 내보내 기기에 보관하거나 개인을 식별할 수 없는 집계만 남기는 방식을 먼저
검토한다. 법률 문구와 실제 사업자 지위는 배포 전에 별도 법률 검토가 필요하다.
