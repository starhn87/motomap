# 인증과 세션 저장

로그인 세션을 기기에 저장하고 앱 시작·백그라운드 전환 뒤 복원하는 과정의 결정 기록이다.

관련 구현:

- `lib/authStorage.ts`
- `lib/supabase.ts`
- `stores/useAuthStore.ts`

## 먼저 확인할 활성 원칙

1. 네이티브의 Supabase 세션은 `SecureStore`에 저장하고 일반 `AsyncStorage`에는 남기지 않는다.
2. iOS가 잠긴 백그라운드에서 키체인 접근을 잠시 거부해도 세션 없음으로 해석하지 않는다.
3. 인증 복구 실패는 처리된 오류로 기록하고 재시도 UI를 유지하며 Promise rejection을 전역으로 흘리지 않는다.

## AUTH-001 — 백그라운드 키체인 접근은 활성화 뒤 재시도

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `lib/authStorage.ts`, `stores/useAuthStore.ts`

### 배경

iOS에서 앱이 하루 이상 백그라운드에 머문 상태로 시스템 시간 변경 이벤트가 발생했을 때
`SecureStore.getItemAsync`가 `User interaction is not allowed`로 거부됐다. 정상 세션이 있는
기기에서도 일시적으로 발생할 수 있으며, 이를 `null`로 바꾸면 사용자를 로그아웃시킬 수 있다.
인증 초기화 호출부가 이 예외를 처리하지 않아 Sentry에는 `onunhandledrejection`으로 남았다.

### 결정

이 오류만 키체인의 일시적 비가용 상태로 분류한다. 앱이 `active`가 될 때까지 읽기·쓰기·삭제를
보류한 뒤 같은 작업을 한 번 재시도한다. 기다리는 동안 일반 저장소로 폴백하거나 세션 없음으로
처리하지 않는다. 그 밖의 저장소·세션 복구 오류는 Sentry에 처리된 오류로 기록하고 기존 재시도
UI를 보여준다.

### 검토한 대안과 시행착오

키체인 접근 등급을 잠금 상태에서도 읽을 수 있게 낮추면 백그라운드 갱신은 쉬워지지만 인증
토큰의 보호 범위도 넓어진다. 일반 저장소 폴백은 보안 저장 전환의 목적을 무너뜨린다. 세션
없음으로 반환하는 방식은 일시적 OS 상태를 로그아웃으로 오인하므로 채택하지 않았다.

### 영향과 재검토 조건

동일 오류가 앱 활성 상태에서도 반복되면 기기 잠금 외의 원인을 분리해 재검토한다. Expo
SecureStore가 백그라운드 접근을 명시적으로 큐잉하는 API를 제공하면 자체 대기를 대체한다.

## AUTH-002 — 구조화된 Supabase 오류를 Sentry용 Error로 정규화

- 날짜: 2026-08-26
- 상태: 활성
- 관련 구현: `stores/useAuthStore.ts`

### 배경

인증 초기화에서 프로필 또는 세션 복구가 실패했을 때 Supabase의 PostgREST 오류 객체를 그대로
`Sentry.captureException`에 넘겼다. 이 값은 `Error` 인스턴스가 아니라
`{ code, details, hint, message }` 형태라 Sentry 이슈 제목이 실제 원인 대신
`Object captured as exception with keys...`로 기록됐다. 사용자 화면에서는 재시도 가능한 복구
오류로 처리됐고 전역 크래시는 아니었지만, 운영자가 오류 코드와 실패 단계를 제목에서 구분할 수
없었다.

### 결정

인증 복구 오류는 `message`를 가진 `Error`로 정규화해 보고한다. Supabase `code`는 오류 이름과
태그로, `details`와 `hint`는 별도 Sentry 컨텍스트로 보존하고 세션·프로필·인증 이벤트·초기화 중
어느 단계에서 실패했는지도 태그로 구분한다. 좌표나 토큰 같은 민감 정보는 컨텍스트에 넣지 않는다.

`onAuthStateChange`에서 시작한 비동기 세션 해석과 초기화 전체에도 마지막 실패 경계를 두어 예상치
못한 Promise rejection이 전역으로 새지 않게 한다. 실패 시 기존처럼 `restoring` 상태와 재시도 UI를
유지하며, 오류를 숨기거나 로그아웃으로 바꾸지 않는다.

### 검토한 대안과 시행착오

처리된 오류라는 이유로 Sentry 보고를 제거하면 일시적 네트워크 오류와 권한·스키마 회귀를 구분할
근거도 사라진다. 구조화 객체를 `captureMessage`로 보내면 스택이 약해지므로 실제 메시지를 가진
`Error`로 바꾸고 원래 진단 필드를 컨텍스트에 남기는 방식을 선택했다.

### 영향과 재검토 조건

기존의 일반화된 이슈는 새 OTA 뒤 같은 실패가 발생했을 때 실제 메시지와 코드가 있는 새 이벤트로
대체된다. 특정 코드가 반복되면 그때 네트워크 재시도, RLS 또는 프로필 생성 순서 중 실제 원인에
맞는 처리를 추가한다. 일시적 오류가 과도한 운영 노이즈가 되면 먼저 오류 코드별 빈도와 사용자
복구 여부를 확인하고 경고 수준 조정을 검토한다.

## AUTH-003 — identity 연결 시 모토맵 프로필 사진을 우선 보존

- 날짜: 2026-08-26
- 상태: 활성
- 관련 구현: `stores/useAuthStore.ts`, `lib/nickname.ts`

### 배경

Supabase Auth는 검증된 이메일이 같은 소셜 identity를 기존 사용자에게 자동 연결할 수 있다. 이때
Auth의 `user_metadata.avatar_url`은 새 소셜 제공자 사진으로 바뀔 수 있지만 모토맵에서 사용자가
직접 저장한 `profiles.avatar_url`은 그대로 남는다. 프로필 화면이 Auth 메타데이터를 기준으로
렌더해 기존 사진이 덮어써진 것처럼 보였다.

### 결정

모토맵 프로필 사진의 정본은 `public.profiles.avatar_url`이다. 인증 세션을 복구할 때 프로필 행의
사진을 함께 조회하고, 값이 있으면 세션 사용자 메타데이터에 우선 반영한다. 저장된 프로필 사진이
없을 때만 소셜 제공자가 준 `user_metadata.avatar_url`을 폴백으로 사용한다.

토큰 갱신이 소셜 제공자 메타데이터를 다시 전달하더라도 현재 세션에 반영된 모토맵 사진을
보존한다. 사용자가 앱에서 새 사진을 선택하면 기존처럼 프로필 테이블과 Auth 메타데이터를 함께
갱신한다. 이 우선순위는 identity 자동 연결과 설정에서 수행하는 수동 연결에 동일하게 적용한다.

### 검토한 대안과 시행착오

identity 연결 직전과 직후에 `auth.updateUser`로 사진을 다시 쓰는 방식은 연결이 성공한 뒤 메타데이터
갱신만 실패하면 사용자에게 전체 연결 실패처럼 보일 수 있다. 또한 자동 연결은 로그인 전에 기존
사용자를 알 수 없어 사전 스냅샷을 가져오기 어렵다. 이미 보존되는 프로필 테이블을 정본으로 읽는
방식이 두 연결 경로를 함께 다루고 부분 실패도 만들지 않는다.

### 영향과 재검토 조건

닉네임이나 다른 프로필 속성에도 소셜 identity 연결로 같은 문제가 확인되면 Auth 메타데이터 전체를
정본으로 쓰지 않고 프로필 행에서 명시적으로 조합하는 공통 경계를 검토한다. 프로필 사진 저장소를
교체하더라도 `profiles.avatar_url` 우선 원칙은 유지한다.
