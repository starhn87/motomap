# 장소 선별·운영 상태 검증

모토맵 등록 장소가 라이더에게 실제로 유용한지와 현재 운영 중인지를 서로 다른 축으로
관리한다. 이 문서는 장소를 추가·숨김·복구하거나 외부 장소 데이터를 검증할 때 가장 먼저
확인한다.

## 활성 원칙

1. **바이크 관련성과 운영 상태를 분리한다.** 라이더에게 유용해도 폐업할 수 있고, 영업
   중이어도 모토맵의 선별 기준에는 맞지 않을 수 있다.
2. **사용자가 직접 검증한 장소는 관련성 재심사에서 보호한다.** 다만 이전·휴업·폐업 같은
   운영 상태 확인까지 면제하지는 않는다.
3. **자동 신호만으로 장소를 삭제하거나 숨기지 않는다.** 신호 수집 → 사람 검토 → 소프트
   숨김(`deleted_at`) 순서를 지키고, 모든 판단 근거와 조치를 이력으로 남긴다.
4. **하드 삭제를 운영 절차로 사용하지 않는다.** 리뷰·즐겨찾기·주행 기록과의 연결을
   보존하기 위해 폐업 확정 장소도 복구 가능한 소프트 숨김으로 처리한다.
5. **전국 신규 장소는 보수적으로 추가한다.** 공식 브랜드 채널에서 현재 지점을 확인하고,
   외부 장소 공급자의 이름·주소·고유 ID가 정확히 일치하며 기존 장소와 중복되지 않을 때만
   승인 장소로 추가한다.
6. **외부 공급자 식별자를 저장한다.** `source_provider`와 `source_place_id`를 남겨 같은 장소를
   중복 등록하지 않고 다음 검증 때 동일 대상을 다시 찾을 수 있게 한다.
7. **운영 상태 신호의 강도를 구분한다.** 공공 인허가 폐업 기록과 사업자 공식 공지는 강한
   신호이고, 검색 결과 부재나 사용자 후기 감소는 검토를 시작하는 약한 신호다.
8. **보호 장소는 자동 숨김하지 않는다.** 강한 폐업 신호가 있어도 현재 영업 여부나 이전·상호
   변경 가능성을 운영자가 한 번 더 확인한다.
9. **등록 해제와 외부 장소의 존재를 구분한다.** 모토맵 선별 대상에서 제외하더라도 외부 지도에
   남아 있는 장소 자체를 지우지 않는다. 즐겨찾기·리뷰·주행처럼 일반 장소 대상이 있는 기록은
   같은 일반 장소로 원자적으로 승계하고, 대응 모델이 없는 기록이나 예상 밖 이용자 기록이 있으면
   자동 처리하지 않고 먼저 보고한다.
10. **정기 감지는 사람의 승인 전에는 반영하지 않는다.** 폐업·상호·주소·전화·이전 후보와
    허용 필드의 반영 계획을 운영 채널에 보고하고, 등록 장소 데이터는 운영자의 명시적인
    승인 없이는 수정하지 않는다. 검색 부재·폐업·숨김은 버튼 자동 반영 대상에서 제외한다.
11. **캠핑 카테고리는 오토캠핑만 유지한다.** 바이크가 배정 사이트까지 진입해 사이트 안이나
    바로 옆에 주차할 수 있어야 한다. 별도 주차장에서 짐을 옮기는 일반 야영장과 글램핑·카라반
    전용 시설은 제외하며, 차량 진입 여부가 불명확하면 자동 숨김 없이 검토 대상으로 둔다.
12. **광역자치단체 정식명은 주소 변경으로 보지 않는다.** 외부 공급자의 `강원특별자치도` 같은
    정식 표기는 앱·DB의 축약형 `강원`으로 정규화한 뒤 비교하고, 승인 계획에도 축약형을 유지한다.
13. **등록 장소는 공통 이용 조건과 가치 경로를 함께 통과한다.** 현재 운영, 합법적인 바이크
    접근·주차를 공통으로 확인하고, 바이크 특화·라이딩 지원 기능·라이더가 검증한 일반 목적지 중
    하나의 가치 경로를 확인한다. 카테고리의 기능 자체가 라이더 가치를 입증하면 커뮤니티 언급 수를
    일률적으로 요구하지 않는다.
14. **사용자의 운영 상태 제보도 검토에서 멈춘다.** 폐업·휴업·이전·정보 변경 제보는 전용
    대기열과 Discord 알림으로 수집하되, 제보만으로 장소를 수정하거나 숨기지 않는다.

## CURATION-001 — 관련성·운영 상태를 별도 축으로 관리

- 날짜: 2026-08-22
- 상태: 활성
- 관련 구현: `public.places`, 장소 선별 마이그레이션

### 배경

기존 `approved`와 `deleted_at`만으로는 “모토맵에 어울리는 장소인지”와 “현재 영업 중인지”를
구분할 수 없다. 승인 장소 147곳을 감사한 결과 바이크 관련성이 명시적인 장소와 일반 관광·식당
성격이 강한 장소가 함께 있었고, 일부 장소에서는 폐업·이전·상호 변경 신호도 발견됐다.

### 결정

- 관련성은 `trusted`, `verified`, `review`, `excluded`로 관리한다.
- 운영 상태는 `unknown`, `operational`, `temporarily_closed`, `permanently_closed`, `moved`로
  관리한다.
- 실제 앱 노출 여부는 계속 `deleted_at`으로 결정한다. 상태 필드는 판단과 검토를 설명하며,
  운영 상태 변경만으로 자동 숨김하지 않는다.
- 마지막 검증 시각, 다음 검증 예정 시각, 보호 여부를 장소에 저장하고, 근거와 조치는 별도의
  append-only 이력으로 보존한다.
- 장소에 저장하는 상태·보호·검증 시각은 개인정보나 비밀 운영 정보가 아닌 장소 품질 메타데이터로
  취급한다. 공개 조회가 가능하되 클라이언트는 이를 수정할 수 없고, 감사 근거와 조치 원문은
  서비스 역할만 접근할 수 있는 내부 이력으로 분리한다.

### 검토한 대안과 시행착오

- `approved` 하나에 관련성·영업 상태를 모두 담으면 재검토 이유와 복구 경로를 알 수 없어
  채택하지 않았다.
- 외부 검색 결과에서 사라진 장소를 즉시 삭제하는 방식은 공급자 일시 장애, 상호 변경, 이전을
  폐업으로 오인할 수 있어 채택하지 않았다.
- 하드 삭제는 연결된 사용자 기록을 손상하거나 연쇄 삭제할 수 있어 운영 절차에서 제외한다.

### 영향과 재검토 조건

검증 화면·Discord 운영 액션·정기 작업은 두 상태 축과 증거 이력을 기준으로 만들어야 한다.
분류가 더 세분화되어야 할 만큼 실제 운영 사례가 쌓였을 때만 상태 집합을 확장한다.

## CURATION-002 — 사용자 검증 장소를 보호 목록으로 취급

- 날짜: 2026-08-22
- 상태: 활성
- 관련 구현: 장소 선별 시드 스크립트, 장소 검증 이력

### 배경

운영자가 직접 방문하거나 신뢰할 수 있는 근거로 확인한 43곳은 일반적인 관련성 재심사를 반복할
필요가 없다. 반면 공공 인허가 데이터에는 이 중 일부와 이름·주소가 일치하는 폐업 기록이 있어,
관련성 보호를 영업 상태 보장으로 해석하면 안 된다.

### 결정

- 직접 검증 목록은 `trusted`이자 보호 대상으로 지정한다.
- 별칭은 현재 DB 이름으로 정규화해 한 장소만 보호한다.
- 보호 대상은 관련성 때문에 자동 제외하거나 폐업 신호만으로 자동 숨김하지 않는다.
- 강한 운영 이상 신호가 들어오면 이전, 사업자 변경, 업종 변경 가능성을 포함해 사람이 다시
  확인하고 결과를 이력에 남긴다.

### 영향과 재검토 조건

보호 목록 추가·해제는 운영자의 명시적 판단으로만 수행한다. 보호 목록이 커져 실질적인 검토가
어려워지면 마지막 확인일과 확인 주체를 필수로 만드는 절차를 재검토한다.

## CURATION-003 — 전국 확장은 공식 채널과 장소 식별자의 교집합만 사용

- 날짜: 2026-08-22
- 상태: 활성
- 관련 구현: `scripts/seed-place-curation.mjs`

### 배경

전국의 라이더 특화 장소를 넓히되 일반 관광지나 단순히 오토바이를 판매하는 소형 판매점까지
무분별하게 포함하면 모토맵의 신뢰도가 낮아진다.

### 결정

- 1차 확장은 제조사 공식 딜러·서비스·전용 장비 거점처럼 바이크 관련성이 설명 없이도 명확한
  장소를 우선한다.
- 공식 채널의 현재 지점 정보와 카카오 장소의 정확한 이름·주소·고유 ID를 함께 확인한다.
- 정확 일치가 유일하지 않거나 기존 장소와의 중복 가능성이 있으면 자동 적용하지 않고 검토
  대상으로 남긴다.
- 시드 스크립트는 기본적으로 읽기 전용 계획만 출력하며, 명시적인 적용 옵션이 있을 때만 쓴다.
- 시드의 각 조치는 고유한 완료 이력을 원장으로 사용한다. 완료된 조치를 재실행해 이후 운영자의
  최신 판정을 덮어쓰지 않으며, 반영 도중 중단된 경우에만 보존된 이전 상태를 이용해 복구한다.

### 영향과 재검토 조건

독립 라이더 카페는 최근 운영 증거가 서로 독립적인 출처 두 곳 이상에서 확인될 때 후속 후보로
올린다. 공식 거점만으로 지역 공백이 충분히 줄지 않을 때 이 기준을 재검토한다.

## CURATION-004 — 폐업 감시는 자동 판정이 아니라 검토 대기열을 만든다

- 날짜: 2026-08-22
- 상태: 활성
- 관련 구현: 장소 검증 증거·조치 테이블, 향후 정기 작업과 Discord 운영 액션

### 배경

정기적으로 폐업 장소를 찾아 정리하면 데이터 신뢰도를 높일 수 있지만, 단일 공급자의 상태값은
이전·임시 휴업·상호 변경을 폐업으로 오인할 수 있다. 또한 현재 앱은 네이버 지도 위에 Google
Places 영업시간을 사용하고 있어, Google Places 콘텐츠를 non-Google map과 함께 쓰지 못하게 하는
[Google Maps Platform 서비스별 약관 14.2](https://cloud.google.com/maps-platform/terms/maps-service-terms)를
별도로 검토해야 한다.

### 결정

- 카페·식당·정비·용품점은 30일, 임시 휴업은 14일, 공공 명소·보호 장소는 90일을 기본 재검토
  주기로 삼는다.
- 공공 인허가, 사업자 공식 공지, 외부 공급자 상태, 사용자 제보를 증거로 쌓되 신호 강도와 관찰
  시각을 함께 저장한다.
- 정기 작업은 검토가 필요한 장소만 소량 큐에 넣고, 운영자가 `유지`, `임시 휴업`, `폐업 숨김`,
  `이전 확인`, `복구` 중 하나를 선택한다.
- Google Places를 폐업 자동 판정 소스로 확대하지 않는다. 현재 사용 방식의 약관 적합성 검토가
  끝날 때까지 기존 영업시간 폴백과 폐업 감시 설계를 분리한다.

### 영향과 재검토 조건

초기에는 스키마와 수동 실행 가능한 검증 스크립트부터 운영한다. 오판율과 검토량을 확인한 뒤
Supabase Cron·Edge Function·Discord 보고 자동화를 별도 단계로 도입한다. 공급자 약관이나 앱의
기본 지도 공급자가 바뀌면 Google Places 사용 경계도 다시 검토한다.

2026-08-23에 폐업·이전·상호 변경 후보를 수집하는 Cron·Edge Function을 운영에 배포했다. 매일
09:20 KST에 최대 8곳을 확인하며, 최초 실행은 8곳 중 정상 3곳·변경 후보 5곳·오류 0곳이었다.
후보 5곳은 모두 내부 대기열과 Discord에 보고됐고, 장소 이름·주소·운영 상태·노출 여부와
큐레이션 조치 이력은 자동 변경하지 않았다. 실제 반영은 운영자의 최종 승인 뒤 별도 작업으로만
수행한다.

## CURATION-005 — 리브랜딩·이전은 장소 이력을 유지하고, 미확인 제거는 상태를 단정하지 않는다

- 날짜: 2026-08-22
- 상태: 활성
- 관련 구현: `public.places`, 장소 검증 증거·조치 테이블, 운영자 판단 데이터 마이그레이션

### 배경

운영 검토에서 폐업, 지도 검색 부재, 관련성 제외, 리브랜딩과 이전이 동시에 발견됐다. 같은 물리
장소가 상호만 바뀐 사례를 삭제 후 재등록하면 리뷰·즐겨찾기·주행 기록의 연결이 끊긴다. 반대로
외부 지도에서 검색되지 않는다는 이유만으로 `permanently_closed`를 기록하면 일시적인 검색 누락이나
상호 변경을 폐업으로 단정하게 된다.

### 결정

- 주소·전화·좌표·공식 채널을 교차 확인해 같은 장소임이 확인되면 기존 UUID를 유지한 채 이름,
  주소, 좌표와 외부 공급자 식별자를 갱신한다.
- 이전 상호에 종속된 설명, 영업시간, 태그는 현행 근거가 없으면 함께 제거하거나 확인된 범위로
  축소한다.
- 운영자가 폐업을 직접 확인한 장소만 `permanently_closed`로 기록하고 소프트 숨김한다.
- 검색 결과 부재로 우선 제외하는 장소는 관련성이 이미 확인됐다면 그 상태를 유지하고,
  `operational_status = unknown`인 채 소프트 숨김한다. 다음 검증 시각을 두어 복구 가능성을 남긴다.
- 모토맵 선별 기준에서 제외하는 판단은 `relevance_status = excluded`로 기록하되, 폐업 여부를
  확인하지 않았다면 운영 상태는 `unknown`으로 유지한다.
- 모든 조치는 하드 삭제 없이 근거와 이전·새 상태를 추가 전용 감사 로그에 남긴다.

### 검토한 대안과 시행착오

- 리브랜딩된 장소를 신규 행으로 추가하면 기존 사용자 기록을 고아로 만들고 같은 장소가 중복될 수
  있어 채택하지 않았다.
- 네이버·카카오 중 한 공급자의 검색 부재만으로 영구 폐업을 기록하는 방식은 오판 가능성이 높아
  채택하지 않았다.
- 숨김과 동시에 관련성까지 일괄 `excluded`로 바꾸는 방식은 운영 상태와 적합성 축을 다시 섞으므로
  채택하지 않았다.

### 영향과 재검토 조건

향후 운영 화면은 `soft_hide`, `update_identity` 조치와 근거 강도를 함께 보여줘야 한다. 같은 주소에서
전혀 다른 업종으로 바뀌거나 기존 기록을 새 장소로 승계하기 어려운 사례가 반복되면 UUID 승계
기준을 더 엄격하게 재검토한다.

## CURATION-006 — 등록 해제 시 일반 장소 즐겨찾기를 유지한다

- 날짜: 2026-08-23
- 상태: 대체됨(CURATION-009)
- 관련 구현: `public.places`, `public.general_places`, `public.favorites`, 등록 해제 데이터 마이그레이션

### 배경

모토맵의 보수적인 선별 기준에서 제외할 일반 식당·관광지 26곳을 등록 장소 목록에서 내리기로
했다. 이 조치는 장소가 실제로 사라졌다는 뜻이 아니며, 이용자가 외부 지도 장소로 계속 찾고
즐겨찾을 수 있어야 한다. 한편 등록 장소를 하드 삭제하면 큐레이션 이력과 리뷰·주행·라이더 정보가
연쇄 삭제되거나 참조 제약을 깨뜨린다.

### 결정

- 등록 해제는 하드 삭제가 아니라 `deleted_at`과 `relevance_status = excluded`를 사용하는 소프트
  숨김으로 처리한다.
- 대상의 이름과 좌표로 앱과 동일한 `coordinate` 일반 장소 식별자를 확보한 뒤, 등록 즐겨찾기의
  행 ID와 생성 시각을 유지하면서 `general_place_id`와 장소 스냅샷으로 전환한다.
- 같은 이용자에게 동일 좌표의 일반 즐겨찾기가 이미 있으면 중복 등록 즐겨찾기만 합친다.
- 운영자 본인과 문서화된 테스트 계정 이외의 리뷰, 라이딩, 라이더 정보, 리뷰 좋아요, 장소 신고,
  제보 연결이 발견되면 마이그레이션을 중단하고 영향을 먼저 검토한다.
- 허용된 운영자·테스트 기록도 삭제하지 않고 숨긴 원래 장소 UUID에 보존한다. 일반 장소로 자동
  전환하는 범위는 현재 즐겨찾기로 제한한다.
- 단순 상호 변경은 등록 해제와 분리해 기존 UUID를 유지한 채 이름과 감사 이력만 갱신한다.

### 검토한 대안과 시행착오

- `places` 행을 물리 삭제하면 큐레이션 감사 로그의 `on delete restrict`에 막히고, 제약을 제거해
  강행하면 사용자 기록까지 연쇄 삭제될 수 있어 채택하지 않았다.
- 즐겨찾기 행을 삭제한 뒤 사용자가 다시 찾게 하는 방식은 등록 장소와 일반 장소가 다른 식별자를
  쓰는 내부 사정을 사용자에게 전가하므로 채택하지 않았다.
- 리뷰·주행까지 일괄 일반 장소로 옮기는 방식은 라이더 정보 투표에 대응하는 일반 장소 모델이
  없고 사용자 기록의 의미가 달라질 수 있어 이번 범위에서 제외했다.

### 영향과 재검토 조건

향후 등록 해제 화면이나 운영 자동화도 같은 사전검사와 즐겨찾기 전환을 원자적으로 수행해야 한다.
일반 장소에도 라이더 정보 모델을 도입하거나 실제 이용자 기록이 있는 장소의 등록 해제 사례가
반복되면 리뷰·주행·라이더 정보의 승계 규칙을 별도로 설계한다.

## CURATION-007 — 정기 변경 감지는 운영자 보고에서 멈춘다

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `supabase/functions/place-change-monitor`, `public.place_change_reviews`,
  `public.place_change_monitor_state`, Supabase Cron

### 배경

폐업뿐 아니라 상호 변경, 이전, 주소·전화 변경을 주기적으로 발견해야 장소 신뢰도를 유지할 수
있다. 그러나 지도 검색 결과는 공급자 장애나 표기 차이로 누락될 수 있고, 같은 주소의 새 상호가
리브랜딩인지 별개 사업자인지는 자동으로 확정할 수 없다. 자동 숨김이나 자동 이름 변경은 기존
리뷰·즐겨찾기·주행 기록을 잘못된 장소에 귀속시킬 위험이 있다.

### 결정

- 매일 09:20 KST에 다음 검증일이 지난 활성 장소를 최대 8곳씩 점검한다.
- 카카오 로컬의 상호·주소 검색을 3km 안에서 대조해 검색 부재, 상호·주소·전화 변경, 이전
  가능성을 보수적으로 탐지한다. 공급자 장소 ID 일치를 가장 강한 동일성 근거로 사용한다.
- 감지 결과는 서비스 역할 전용 `place_change_reviews` 대기열에 현재값·관찰값·근거·신뢰도와
  함께 저장하고 Discord에 보고한다. 같은 관찰은 지문으로 합치며 보고 실패는 다음 실행에서
  재시도한다.
- Edge Function과 Cron은 `places`를 수정할 권한이나 코드를 갖지 않는다. 보호 여부와 관계없이
  이름·주소·전화·좌표·운영 상태·`deleted_at`을 자동 변경하지 않는다.
- 운영자가 최종 승인한 뒤에만 별도 원자적 마이그레이션 또는 운영 작업으로 반영하고, 기존
  큐레이션 증거·조치 이력에 판단 근거를 남긴다.
- 검색 결과 부재는 낮은 신뢰도의 검토 신호일 뿐 폐업 판정이 아니다. 단일 공급자의 관찰값도
  그대로 채택하지 않고 공식 채널이나 운영자 확인과 교차 검증한다.

### 검토한 대안과 시행착오

- 일정 신뢰도 이상이면 자동으로 이름을 바꾸거나 소프트 숨김하는 방식은 오탐의 사용자 기록
  영향이 커서 채택하지 않았다.
- Discord 버튼 한 번으로 임의의 변경을 즉시 실행하는 방식은 오조작 시 복구 범위가 커서 초기
  단계에서는 제외했다. 초기 운영에서 보고 구조를 검증한 뒤, 허용 필드와 스냅샷이 고정된 계획만
  승인하는 방식으로 범위를 좁혀 `CURATION-008`에서 대체했다.
- 모든 장소를 한 번에 검색하면 외부 API 호출량과 검토 피로가 커지므로 소량 배치와 카테고리별
  30·90일 재검토 주기를 사용한다.

### 영향과 재검토 조건

초기 운영에서 오탐률, 누락률, Discord 보고량을 확인한다. 공식 사업자 API처럼 동일성과 운영
상태를 더 강하게 보장하는 출처가 생기거나 검토량이 감당하기 어려워질 때만 자동화 범위를 다시
논의한다. 그 경우에도 등록 장소 자동 변경은 별도의 명시적 결정으로만 도입한다.

## CURATION-008 — Discord 승인은 미리 고정된 안전한 변경 계획만 원자적으로 반영한다

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `supabase/functions/place-change-monitor`,
  `supabase/functions/discord-interactions`, `public.resolve_place_change_review`

### 배경

검토 보고마다 현재값과 관찰값을 다시 비교해 별도 작업을 준비하면 안전하지만 반복 작업이 많다.
반대로 버튼이 클릭 시점의 외부 검색 결과를 다시 해석하거나 임의 필드를 수정하면 보고 뒤 데이터
변경, 공급자 오탐, 중복 클릭 때문에 승인한 내용과 실제 반영이 달라질 수 있다.

### 결정

- 감지 시점에 높은 신뢰도로 같은 장소가 확인된 상호·주소·전화·좌표·카카오 식별자만
  `proposed_changes`에 저장하고 Discord 본문에 현재값 → 변경값 계획으로 표시한다.
- `not_found`, 낮거나 중간 신뢰도, `possible_name_change`에는 자동 반영 계획을 만들지 않는다.
  폐업·운영 상태·보호 여부·노출 여부도 버튼으로 변경하지 않는다.
- `계획대로 반영` 버튼은 Discord의 Ed25519 서명을 검증한 인터랙션 함수에서만 처리한다.
  DB 함수는 서비스 역할 전용이며 허용 필드, 값 범위, 현재 장소 활성 상태와 보고 당시 전체
  스냅샷 일치를 다시 검사한다.
- 승인된 패치는 장소 갱신, 검증 근거, 큐레이션 조치, 검토 완료와 다음 점검일을 한 트랜잭션으로
  반영한다. 한 단계라도 실패하면 전부 롤백하고 장소는 바꾸지 않는다.
- 카카오 식별자 연결이 계획에 포함되면 기존 일반 장소 승격 트리거가 같은 식별자의 즐겨찾기·
  리뷰·주행 기록을 등록 장소로 안전하게 승계한다. 이 부수 효과도 Discord 계획에 함께 알린다.
- `변경 없음` 버튼은 장소를 수정하지 않고 검토만 닫는다. 성공하면 원 Discord 메시지의 버튼을
  제거하고 처리자와 반영 필드를 포함한 완료 결과로 갱신한다.

### 검토한 대안과 시행착오

- 클릭 시 외부 공급자를 다시 조회해 계획을 생성하면 보고에서 본 값과 적용값이 달라질 수 있어
  채택하지 않았다.
- Edge Function에서 여러 REST 요청으로 장소·근거·조치를 차례로 갱신하면 부분 성공이 남으므로,
  실제 변경은 Postgres의 단일 원자적 함수에 맡긴다.
- 모든 후보에 승인 버튼을 주면 검색 결과 없음이 폐업 숨김으로 오인될 수 있어, 안전한 패치가
  없는 보고에는 `변경 없음`만 제공한다.

### 영향과 재검토 조건

Discord 채널 접근 권한이 곧 운영 승인 권한의 경계다. 운영자가 늘어나면 허용 사용자나 역할을
별도 설정으로 제한한다. 주소 체계 개편처럼 외부 공급자 표기가 일괄적으로 부정확하거나 승인
오조작 사례가 발생하면 해당 필드를 계획 대상에서 제외하고 수동 작업으로 되돌린다.

2026-08-23 DB 마이그레이션과 두 Edge Function을 운영에 함께 배포했다. 배포 이후 생성되는
새 보고부터 안전한 변경 계획이 있을 때 승인 버튼이 붙으며, 기존 보고는 기존 방식으로 남는다.

## CURATION-009 — 등록 해제 뒤에도 일반 장소가 지원하는 이용 기록을 승계한다

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `public.reviews`, `public.favorites`, `public.place_rides`, 등록 해제 데이터 마이그레이션
- 대체 대상: CURATION-006의 즐겨찾기만 자동 전환하는 범위

### 배경

티하우스에덴을 모토맵 등록 장소에서 일반 장소로 내릴 때 리뷰 1건을 삭제하지 않고 숨긴 원래
장소 UUID에 보존했다. 데이터는 남아 있었지만 일반 장소 상세은 `general_place_id`로 리뷰를
조회하므로 이용자에게는 기존 리뷰와 사진이 사라진 것처럼 보였다. 내부 선별 상태 변경 때문에
사용자가 작성한 기록의 가시성이 달라져서는 안 된다.

### 결정

- 등록 해제는 계속 원래 `places` 행을 소프트 숨김하고 대응하는 `general_places` 행을 먼저
  확정한 뒤 단일 트랜잭션에서 처리한다.
- 즐겨찾기뿐 아니라 일반 장소 대상 컬럼이 이미 있는 리뷰와 주행도 일반 장소로 옮긴다. 리뷰는
  UUID·작성자·별점·본문·사진·작성일·좋아요를 유지하고 `place_id`와 `general_place_id`만 원자적으로
  교체한다. 주행도 기록 ID와 라이더·시각·바이크 스냅샷을 유지한다.
- 리뷰 대상 변경 트리거가 숨긴 등록 장소와 일반 장소의 별점·리뷰 수를 즉시 다시 계산한다.
- 같은 외부 장소가 나중에 다시 등록 승격되면 기존 승격 트리거가 즐겨찾기·리뷰·주행을 같은
  UUID로 등록 장소에 되돌린다.
- 라이더 정보 투표처럼 일반 장소에 대응 모델이 없는 기록은 숨긴 원래 장소에 보존한다. 예상 밖
  실제 이용자의 기록이나 대상 충돌이 발견되면 자동 승계를 중단하고 영향을 먼저 보고한다.

### 검토한 대안과 시행착오

CURATION-006의 보수적 범위는 삭제 위험은 막았지만, 숨긴 장소에 리뷰를 남겨 일반 장소 상세에서
조회할 수 없게 했다. 리뷰를 복제하면 원본과 새 행의 UUID·좋아요·신고 연결이 갈라지므로 채택하지
않고 기존 행의 대상만 바꾼다. 라이더 정보까지 억지로 일반 장소에 연결하는 방식은 데이터 모델이
없어 채택하지 않는다.

### 영향과 재검토 조건

등록 해제 작업은 대상별 리뷰·즐겨찾기·주행·라이더 정보·신고 연결을 사전 검사하고, 승계 전후
행 수와 집계를 검증해야 한다. 일반 장소에 라이더 정보 모델을 도입하면 숨긴 원래 장소에 남기는
예외도 다시 검토한다.

## CURATION-010 — 캠핑 카테고리는 사이트 옆 바이크 주차가 가능한 곳으로 한정한다

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `public.places.category = 'camping'`,
  `docs/reports/camping-place-audit-2026-08-23.md`, 장소·코스 제보 승인 기준

### 배경

기존 캠핑 7곳은 모토캠핑 후기와 접근성을 바탕으로 승인됐지만, 바이크를 별도 주차장에 세우고
짐을 옮겨야 하는 일반 야영장도 포함될 수 있었다. 라이더가 기대하는 모토캠핑의 핵심은 바이크와
같은 사이트에서 머무는 경험이므로 단순히 텐트를 칠 수 있다는 사실만으로는 부족하다.

### 결정

- 바이크 또는 차량이 배정된 야영 사이트까지 진입하고 사이트 안이나 바로 옆에 주차할 수 있는
  곳만 캠핑 카테고리로 승인한다.
- `자동차야영장` 공공 등록, 운영자 안내, 공식 예약 상품의 오토캠핑 표기를 강한 근거로 본다.
- 관광사업 등록 명칭이 `일반야영장`이어도 운영자가 사이트 옆 차량 주차를 명시하면 승인할 수
  있다. 반대로 별도 주차장에서 손수레로 짐을 옮기면 일반 야영장으로 보고 제외한다.
- 글램핑·카라반만 운영하거나 오토바이 사이트 진입이 금지된 곳은 승인하지 않는다.
- 차량 진입 여부를 확인하지 못한 장소는 `review`로 남겨 운영자 확인 전까지 자동 변경하지 않는다.
- 기존 장소를 내릴 때도 하드 삭제하지 않고 CURATION-009의 사용자 기록 사전검사와 일반 장소
  승계 원칙을 따른다.

### 검토한 대안과 시행착오

- 장소 이름에 `오토캠핑`이 있거나 지도 공급자가 오토캠핑장으로 분류했다는 이유만으로 승인하면
  실제 현장 규칙 변경을 놓칠 수 있어 단독 근거로 쓰지 않는다.
- `일반야영장` 등록을 일괄 반려하면 혼합 운영이나 사이트 옆 주차가 가능한 캠핑장을 누락하므로
  운영자·예약 정보의 실제 차량 배치 규칙을 함께 확인한다.

### 영향과 재검토 조건

2026-08-23 감사에서는 7곳 중 5곳이 기준 충족, 모구리 1곳이 기준 미달, 무릉계곡 1곳이 추가
확인 대상으로 분류됐다. 운영자는 보수적인 기준으로 모구리와 무릉계곡 모두 소프트 숨김하고,
나머지 5곳을 검증 완료로 기록하도록 승인했다. 반영 직전 사용자 기록을 다시 검사하고 근거·조치와
상태를 단일 트랜잭션으로 남긴다. 바이크 전용 캠핑존이나 짐 운반 지원처럼 별도 주차의 불편을
실질적으로 없애는 운영 사례가 반복되면 예외 기준을 다시 검토한다.

## CURATION-012 — 등록 해제 일반 장소는 실제 외부 장소 식별자로 승계한다

- 날짜: 2026-08-24
- 상태: 활성
- 관련 구현: `public.general_places`, 등록 해제 데이터 마이그레이션

### 배경

왈츠와닥터만을 일반 장소로 전환하면서 기존 등록 장소의 이름과 좌표로 `coordinate` 일반 장소를
만들고 리뷰를 옮겼다. 리뷰 행과 집계는 보존됐지만, 사용자가 검색해 연 카카오의 `왈츠와 닥터만`은
별도의 안정적인 장소 ID와 약 27m 다른 좌표를 사용했다. 앱은 외부 장소 ID의 정확 일치를 우선하고
좌표 폴백은 오병합을 막기 위해 매우 좁게 제한하므로, 사용자는 리뷰가 사라진 것으로 보게 됐다.

### 결정

- 등록 해제 전에 사용자가 실제로 다시 열 외부 공급자의 장소 ID, 현행 이름·주소·좌표를 확인한다.
- 동일성이 확정되면 `general_places`는 `coordinate` 임시 식별자보다 외부 공급자 ID를 사용한다.
- 리뷰·즐겨찾기·주행은 기존 행과 일반 장소 UUID를 유지한 채 대상과 장소 스냅샷만 갱신한다.
- 같은 주소의 복합 시설처럼 여러 외부 장소가 공존하면 주소나 넓은 좌표 반경만으로 자동 병합하지
  않고, 어느 외부 장소가 기존 등록 장소를 승계하는지 사람이 확정한다.
- 외부 장소 ID를 확정할 수 없을 때만 좌표 식별자를 사용하며, 실제 앱 조회 경로에서 리뷰와
  즐겨찾기가 보이는지 전환 후 검증한다.

### 검토한 대안과 시행착오

좌표 허용 범위를 일괄 확대하거나 공백을 제거한 이름과 주소만으로 자동 병합하면 같은 건물의
식당·박물관·공연장을 하나로 합칠 수 있어 채택하지 않았다. 리뷰를 외부 장소마다 복제하는 방식도
UUID·좋아요·신고 연결과 집계를 갈라놓으므로 채택하지 않는다.

### 영향과 재검토 조건

2026-08-24에 왈츠와닥터만과 고구려돼지갈비의 일반 장소 UUID 및 이용 기록은 유지하면서 카카오
장소 ID로 식별자를 보정했다. 앞으로 등록 해제 마이그레이션의 사후 검증은 DB 행 수뿐 아니라
외부 검색 결과로 열린 상세 화면의 실제 일반 장소 ID까지 확인해야 한다. 공급자별 별칭을 하나의
일반 장소에 여러 개 연결해야 하는 사례가 반복되면 별도 식별자 별칭 모델을 도입한다.

## CURATION-013 — 등록 장소는 공통 이용 조건과 세 가지 가치 경로로 판정한다

- 날짜: 2026-08-24
- 상태: 활성
- 관련 구현: `docs/submission-approval-policy.md`,
  `supabase/functions/_shared/submissionPolicy.ts`, 등록 장소 감사·등록 해제 마이그레이션

### 배경

일반 장소도 리뷰·즐겨찾기·주행 기록과 `장소 추천`을 지원하므로, 평범한 맛집·카페를 등록 장소로
넓게 포함하지 않아도 라이더끼리 공유할 수 있게 됐다. 한편 바이크 특화 업태나 라이더 커뮤니티
언급만을 고유 가치로 요구하면 휴게소·뷰포인트·캠핑·세차처럼 라이딩 과정에서 기능적으로 유용한
장소가 거의 통과하지 못한다. 카테고리마다 라이더 가치가 생기는 방식을 구분할 필요가 있다.

### 결정

- 모든 등록 장소는 현재 운영과 동일성, 합법적인 바이크 접근, 해당 이용 방식에 맞는 실사용
  주차 공간을 공통 최소 조건으로 통과한다.
- 공통 최소 조건과 별개로 다음 가치 경로 중 하나를 통과한다.
  1. `바이크 특화`: 정비·용품·딜러·바이크 테마처럼 사업·서비스·공간이 바이크와 직접 연결된다.
  2. `라이딩 지원 기능`: 휴게소·뷰포인트·캠핑·세차·희소 주유소처럼 라이딩 중 필요한 기능을
     구체적으로 제공한다.
  3. `라이더가 검증한 일반 목적지`: 음식점·일반 카페처럼 업태는 무관하지만 운영자 직접 확인
     또는 구체적인 최근 라이더 목적지 근거와 별도 운영·주차 확인이 있다.
- 라이딩 지원 기능은 기능·동선·카테고리별 이용 조건이 확인되면 라이더 콘텐츠 2개를 요구하지
  않는다. 휴게소의 휴식 기능, 뷰포인트의 경관과 합법 정차, 캠핑의 사이트 옆 주차, 세차장의
  이륜차 허용처럼 그 카테고리에서 직접 확인할 수 있는 효용을 근거로 쓴다.
- 음식점·일반 카페는 운영자 직접 확인 또는 구체적인 최근 라이더 목적지 근거 1개와 지도·공식
  정보의 위치·주차·운영 교차 확인을 요구한다. 단순한 맛·경관·유명세·코스 인접성은 부족하다.
- “반복 방문 가능한 가치”를 별도 관문으로 두지 않는다. 의도는 장소의 취향상 재방문 매력을
  평가하는 것이 아니라, 일반 이용자가 현재 방문해도 검증된 바이크 테마·서비스·주차 조건을
  동일하게 이용할 수 있는지 확인하는 것이다. 이는 모든 장소에 적용되는 근거의 현재성·재현
  가능성으로 검증한다.
- 하루짜리 행사, 임시 팝업, 특정 모임 날의 예외, 후기 한 건에만 나타난 호의, 임시 공터는 등록
  근거로 쓰지 않는다. 계절 운영은 공식 운영 기간과 조건이 명확하면 인정할 수 있다.
- 넓은 주차장은 공통 최소 조건의 근거일 뿐 가치 경로를 대신하지 않는다. 세 가치 경로를
  통과하지 못한 장소는 일반 장소로 두고 사용자의 `장소 추천`으로 공유한다.
- 일반 장소 추천 수, 모토맵 리뷰·즐겨찾기·주행 기록은 조사 후보 신호일 뿐 등록 승격의 독립
  근거로 쓰지 않는다.
- 기존 등록 장소도 이 기준으로 순차 감사한다. 기준 미달 장소는 폐업으로 처리하거나 하드 삭제하지
  않고 CURATION-009·012에 따라 실제 외부 장소 ID의 일반 장소로 이용 기록을 승계한다.

### 검토한 대안과 시행착오

- 주차장 규모를 등록의 핵심 점수로 두면 일반 대형 카페·식당이 대거 포함되므로 공통 최소
  조건으로만 사용한다.
- 라이더 한 명의 추천이나 모토맵 내부 신호를 승인 근거로 쓰면 작은 사용자 기반에서 조작·취향의
  영향이 크고, 일반 장소 추천과 등록 장소의 의미가 다시 합쳐지므로 채택하지 않았다.
- 모든 카테고리에 독립적인 라이더 콘텐츠 2개를 요구하면 온라인 기록이 적은 유용한 휴게소·
  뷰포인트·캠핑·세차장이 사실상 배제된다. 커뮤니티 인기 대신 카테고리 기능을 직접 검증한다.
- 항목별 점수 합산은 주차나 안전 부족을 다른 장점으로 상쇄할 수 있어 사용하지 않는다. 공통
  최소 조건은 반드시 통과하고, 가치 경로는 하나 이상을 명시한다.
- `지속성`을 세 번째 가치 관문으로 두는 방식은 “여러 번 갈 만큼 좋은가”라는 취향 평가로 읽힐
  수 있어 채택하지 않았다. 확인하려던 실제 조건은 `COMMON-EVIDENCE`의 현재성·재현 가능성으로
  옮겼다.

### 영향과 재검토 조건

2026-08-24 첫 적용으로 핏제리아 루카네와 금학칼국수를 일반 장소로 전환한다. 이후 기존 장소
감사에서는 공통 최소 조건, 적용한 가치 경로, 근거의 현재성을 각각 기록하고 근거가 불확실하면
자동 제외하지 않고 검토 상태로 둔다. 음식점·카페가 지나치게 많이 포함되거나 기능형 카테고리가
여전히 과도하게 배제되면 카테고리별 증거 수준을 조정하되, 합법적인 접근·주차 조건은 유지한다.

## CURATION-014 — 사용자 장소 변경 제보는 전용 검토 대기열로 받는다

- 날짜: 2026-08-25
- 상태: 활성
- 관련 구현: `public.place_change_reports`,
  `supabase/functions/report-place-change/index.ts`,
  `components/place/PlaceChangeReportSheet.tsx`

### 배경

정기 변경 감지는 일부 장소만 주기적으로 확인하므로, 실제 방문자가 먼저 알게 된 폐업·휴업·이전
정보를 전달할 경로가 필요하다. 기존 `reports`는 스팸·욕설·저작권 같은 콘텐츠 신고 모델이고,
장소별 한 번만 신고할 수 있어 시간이 지나 다시 바뀌는 운영 상태의 이력과 맞지 않는다.

### 결정

- 등록 장소 상세에서 `폐업`, `임시 휴업`, `이전`, `상호·주소·전화 변경`, `기타`를 제보한다.
- 인증된 사용자만 제출하며 한 사용자·장소에 미검토 제보는 하나만 유지한다. 해결·기각된 뒤에는
  같은 장소의 새 변화를 다시 제보할 수 있다.
- 제보 원문과 사용자 식별자는 서비스 역할만 접근하는 전용 테이블에 저장한다. 앱은 JWT를 다시
  확인하고 호출량을 제한하는 Edge Function을 통해서만 제출한다.
- Discord에는 장소·변경 유형·설명과 내부 제보 ID만 보내고 사용자 식별자는 표시하지 않는다.
- Discord 전송 실패 시 제보를 잃지 않고 오류를 저장하며, 같은 미보고 제보를 재시도할 수 있다.
- 제보는 증거이자 검토 시작 신호일 뿐이다. 장소 행, 운영 상태, `deleted_at`을 자동 변경하지 않고
  운영자가 동일성·이전·실제 영업 상태를 확인한 뒤 기존 큐레이션 절차로 별도 반영한다.
- 계정 삭제 시 사용자가 남긴 미처리·처리 완료 제보도 함께 삭제한다.

### 검토한 대안과 시행착오

기존 콘텐츠 신고의 `other`에 폐업 문구를 넣으면 운영 상태별 분류와 재제보가 불가능하고 Discord
운영 흐름에서도 발견하기 어렵다. 사용자 한 명의 폐업 제보로 즉시 숨기면 이전·임시 휴업·공급자
오인을 복구하기 어려우므로 채택하지 않았다. 정기 감지의 `place_change_reviews`에 바로 합치면
카카오 관찰 스냅샷과 사용자 진술의 출처·신뢰도를 구분할 수 없어 별도 원본 대기열을 유지한다.

### 영향과 재검토 조건

초기에는 Discord 보고 뒤 운영자가 직접 확인하고 기존 변경 절차로 반영한다. 제보량이 늘어 수동
연결이 반복되면 사용자 제보를 정기 감지 대기열의 증거로 연결하는 운영 UI와 안전한 기각 버튼을
추가하되, 폐업·숨김 자동 반영 금지는 별도 결정 없이 완화하지 않는다.
