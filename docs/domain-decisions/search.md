# 통합 검색·검색 결과 지도

텍스트 검색에서 등록 장소·일반 장소·라이딩 추천을 찾고, 결과 지도에서 위치를 비교하는 경험에
관한 결정 기록이다.

관련 구현:

- `app/search.tsx`
- `app/search-results.tsx`
- `components/map/MapHome.tsx`
- `components/search/PointSearchModal.tsx`
- `hooks/useSearchAnchor.ts`
- `lib/api/search.ts`
- `lib/api/kakaoLocal.ts`
- `lib/api/externalPlaces.ts`, `lib/api/naverLocal.ts`
- `lib/mapCamera.ts`
- `lib/mapFocus.ts`

## 먼저 확인할 활성 원칙

1. 검색 기준점은 마지막으로 본 지도 중심을 우선하고, 없으면 사용자 위치를 사용한다.
2. 검색 결과 지도는 기준점 중심 고정 20km 안의 등록 장소·일반 장소로 제한한다. 라이딩 추천은
   대표 목적지 위치를 기준으로 검색하되 목록 결과로만 보여준다. 주변 결과가 없어도 결과 지도에
   전국 결과를 붙이지 않는다.
3. 사용자에게 보이는 결과 순서는 등록 장소, 일반 장소, 라이딩 추천 순이다. 라이딩 추천은 항상
   장소 결과 뒤에 둔다.
4. 이름·태그·주소 등의 매칭 점수와 주변 우선 정렬은 내부 정보다. “이름이 정확히 일치”,
   “주변 결과부터”, “카카오 장소 검색” 같은 구현 설명은 결과 행에 반복 노출하지 않는다.
   일반 장소 공급자 표시는 목록 끝의 별도 출처 문구로만 남긴다.
5. 결과 지도에 위치가 하나뿐이면 바텀시트를 제외한 지도 영역의 중앙에 마커를 둔다.

6. 검색 입력 화면과 길찾기 지점 검색은 먼 고유 장소·지역명도 찾을 수 있도록 주변 우선
   검색을 유지한다. “현재 지도 결과를 한눈에 보는 화면”과 “목적지를 직접 찾는 입력”의
   범위는 의도적으로 다르다.
7. 8번의 고유 상호 직접 포커스까지 적용한 뒤에도 등록 장소·일반 장소·라이딩 추천 원본 결과가
   모두 0개면 지도를 렌더하지 않고 전용 빈 결과 화면과 `새로운 장소 제보` CTA를 보여준다.
   필터 때문에 0개가 된 경우에는 적용하지 않는다.
8. 검색어와 이름이 정확히 일치하는 장소가 하나뿐이면 결과 목록을 거치지 않고 지도에서
   해당 장소 상세를 바로 연다. 현재 지도 20km 밖의 고유 상호는 카카오의 유일한 정확 일치
   좌표를 중심으로 재확인한 뒤 같은 규칙을 적용한다.
9. 검색에서 장소를 선택해 지도 탭으로 돌아갈 때는 검색 직전의 지도 카메라 전체 상태에서
   목적지까지 이동한다. 직전 카메라가 있을 때 사용자 위치를 중간 출발점으로 쓰지 않고,
   지도 가림막이나 장거리 `Fly` 줌아웃도 사용하지 않는다. 루트 화면 전환이 완전히 끝나고
   직전 지도 프레임이 실제로 노출된 다음에 이동을 시작한다.
10. 고정 경로형 코스 검색 RPC는 구버전 호환을 위해 유지하되 신버전 검색에서는 호출하지 않는다.
    새 검색은 별도 `search_riding_guides_v1` RPC를 사용해 같은 응답 필드의 의미를 바꾸지 않는다.
11. 타이핑 검색은 300ms 동안 입력이 안정된 검색어만 요청한다. 검색어가 바뀌면 진행 중인
    Supabase·카카오·네이버 요청을 취소하고, 등록·일반 장소 중복 제거는 공통 검색 함수에서 수행한다.
12. 카카오가 0건이거나 실패한 경우 네이버 지역 검색으로 보완한다(SEARCH-012). 최대 5건뿐인
    네이버 결과는 선택 가능한 목록이며, 전체에서 유일하다고 추정해 자동 이동하지 않는다.

## SEARCH-001 — 결과 지도는 주변 목록만 사용

- 날짜: 2026-08-21
- 상태: 활성
- 관련 구현: `app/search.tsx`, `app/search-results.tsx`, `lib/api/search.ts`
- 대체한 동작: 커밋 `36d24cd`의 주변·전국 결과 무조건 결합

### 배경

결과 지도에서 주변 20km 조회와 전국 조회를 병렬 실행해 합치면서 “카페”처럼 범위가 넓은
검색어에 전국 등록 장소가 모두 붙었다. 카카오 일반 장소는 이미 20km로 제한되어 데이터
출처별 범위도 서로 달랐고, 가까운 장소를 찾으려는 검색의 실용성이 사라졌다.

### 결정

검색 결과 지도에서는 기준점 20km 안의 등록 장소·카카오 일반 장소·코스만 사용하며,
주변 결과가 없어도 전국 결과로 폴백하지 않는다. 결과는 등록 장소, 카카오 일반 장소,
코스 순으로 보여준다. DB의 이름·태그·주소 점수는 정렬에만 사용하고 사용자 문구로
번역해 반복 노출하지 않는다. 주변 우선 정렬이나 카카오 검색 여부도 각 결과의 주소 앞에
반복하지 않고, 필요한 공급자 고지는 일반 장소 목록 끝의 출처 문구로 분리한다.

검색 입력 화면과 길찾기 지점 검색은 지역명이 포함된 검색이나 먼 고유 목적지를 직접 찾는
경로이므로 주변 우선·전국 폴백과 카카오 위치 편향을 유지한다. 여기서 결과 하나를 직접
선택하면 해당 장소로 이동할 수 있다.

### 검토한 대안과 시행착오

주변 결과 뒤에 전국 결과를 모두 붙이면 별도의 범위 토글 없이도 모든 결과를 볼 수 있지만,
일반 카테고리 검색에서는 관련성보다 데이터 양이 앞서게 된다. 결과 지도는 주변 목록만으로
완결하고, 전국 목적지 탐색은 검색 입력 화면의 직접 선택 경로에 남긴다.

### 영향과 재검토 조건

현재 “지도 반경”은 실제 화면 경계가 아니라 지도 중심 기준 고정 20km다. 줌별 실제
뷰포트를 검색 범위로 쓰려면 지도 경계 저장, 캐시 키, PostGIS 범위 조회를 함께 설계한 뒤
재검토한다. 검색 입력은 먼 목적지 직접 선택, 결과 지도는 현재 지역 비교라는 의도된 범위
차이가 흐려지지 않게 두 화면을 함께 비교한다.

## SEARCH-002 — 단일 결과는 가시 지도 영역의 중앙에 배치

- 날짜: 2026-08-21
- 상태: 활성
- 관련 구현: `app/search-results.tsx`

### 배경

위치 결과가 하나여도 가상의 좌표 범위를 만들어 복수 결과용 카메라 맞춤을 적용했다. 남북
여백이 비대칭이라 마커가 위쪽으로 치우쳤고, 실제 결과 바텀시트 높이는 계산에 쓰이지 않았다.

### 결정

지도 초기화와 검색 로딩이 끝난 뒤 위치 결과가 하나면 `animateCameraTo`의 `pivot`을 사용한다.
세로 기준점은 `(화면 높이 - 결과 시트 높이) / 2 / 화면 높이`로 계산해 바텀시트를 제외한
영역의 중앙에 둔다. 복수 위치 결과만 기존 좌표 범위 맞춤을 사용한다. 상세가 열려 있는
동안에는 결과 카메라 보정이 상세 카메라 이동을 덮지 않는다.

### 검토한 대안과 시행착오

최소 위·경도 범위를 강제로 만들어 복수 결과 API를 재사용하면 기기별 시트 높이와 무관한
임의 위치가 된다. 위도 오프셋 상수를 다시 맞추는 대신 SDK가 제공하는 화면 비율 기준점을
사용한다.

### 영향과 재검토 조건

결과 시트의 기본 스냅 포인트를 바꾸면 단일 결과 pivot도 같은 높이를 계속 참조해야 한다.
등록 장소 한 개, 일반 장소 한 개, 필터 후 한 개, 상세를 닫고 목록으로 돌아온 경우를 함께
검증한다.

## SEARCH-003 — 빈 결과를 새로운 장소 기여로 연결

- 날짜: 2026-08-21
- 상태: 활성
- 관련 구현: `app/search-results.tsx`, `app/(tabs)/submit.tsx`

### 배경

검색 결과가 하나도 없어도 빈 지도와 작은 바텀시트가 남아 있어 사용자가 실패 원인과 다음
행동을 알기 어려웠다. 특히 지역명과 카테고리를 함께 검색하면 현재 지도 반경 원칙상 정상적인
0건일 수 있으므로, 빈 지도를 확대해 보는 것보다 검색 범위와 기여 경로를 분명히 보여줄
필요가 있다.

### 결정

등록 장소·20km 안의 카카오 일반 장소·코스 쿼리가 모두 성공한 뒤 원본 결과 합계가 0개면
네이티브 지도와 결과 바텀시트를 언마운트하고 전용 빈 상태를 보여준다. 빈 상태에는 검색어,
현재 지역에서 찾지 못했다는 설명, `새로운 장소 제보` CTA를 제공한다. CTA는 제보 화면의
장소 탭을 명시적으로 열지만, `제주 카페`처럼 검색어가 장소명이 아닐 수 있으므로 폼 값은
자동 입력하지 않는다.

UI 필터가 기존 원본 결과를 0개로 줄인 경우에는 사용자가 필터를 해제할 수 있도록 지도와
필터 바텀시트를 유지한다. 쿼리 실패는 0건으로 취급하지 않고 다시 시도할 수 있는 오류 상태로
분리한다. 일반 검색에서 빈 배열로 실패를 숨기는 카카오 API도 이 화면에서는 오류를 던지는
엄격 모드로 호출한다.

### 검토한 대안과 시행착오

기존 바텀시트 안에 “검색 결과가 없습니다”만 표시하면 지도 자체가 결과인 것처럼 남고 제보
행동도 발견하기 어렵다. 반대로 `items.length`만 확인하면 필터 결과와 네트워크 오류까지 실제
0건으로 오인하므로, 필터 전 원본 결과와 각 쿼리 성공 상태를 함께 확인한다.

### 영향과 재검토 조건

빈 상태에서 지도를 언마운트하므로 다시 결과 지도로 전환할 때 map readiness를 초기화한다.
`이 지역에서 다시 검색`은 반올림된 좌표 캐시를 재사용하지 않도록 요청 revision을 키에 넣는다.
검색 데이터 소스가 추가되면 그 소스가 완료되고 0건인지도 빈 상태 조건에 포함한다.

## SEARCH-004 — 유일한 고유 상호는 결과 목록 없이 바로 포커스

- 날짜: 2026-08-21
- 상태: 활성
- 관련 구현: `app/search-results.tsx`, `lib/api/kakaoLocal.ts`

### 배경

검색 입력 화면은 먼 고유 목적지를 찾도록 주변 우선·전국 폴백을 지원하지만, 엔터로 넘어간
결과 지도는 마지막 지도 중심 20km를 강제했다. 따라서 입력 목록에는 `바이콩즈`가 보여도
결과 지도에서는 공주가 현재 중심에서 멀다는 이유만으로 0건이 됐다. 반대로 결과 지도의 전국
폴백을 되살리면 `카페`처럼 일반적인 검색어가 다시 전국 장소로 넘치는 문제가 재발한다.

### 결정

등록 장소와 카카오 일반 장소를 중복 제거한 뒤, 공백과 구분 기호를 제거한 이름이 검색어와
정확히 일치하는 장소가 하나뿐이면 결과 목록을 렌더하지 않고 지도에서 해당 장소 상세를 바로
연다. 등록 장소라면 등록 상세를 우선하고, 등록되지 않은 장소만 카카오 일반 상세로 연다.

카카오 응답이 마지막 페이지이고 전체 결과 수·노출 가능 결과 수·실제 수신 결과 수가 일치해
결과 집합이 완결됐을 때만 유일성을 판정한다. 그 완결된 결과에서 정확히 일치하는 유효한 국내
장소가 하나뿐이고 현재 20km 밖이라면, 해당 좌표를 새 검색 중심으로 한 번 옮겨 기존 20km
쿼리로 등록 여부와 중복을 재확인한 뒤 바로 포커스한다. 이 재조회 중에도 결과 목록은 보여주지
않는다. `이 지역 둘러보기` 모드는 자동 포커스에서 제외한다.

자동 포커스도 같은 `search_id`로 최종 `search_results_viewed`를 먼저 기록한 뒤
`search_result_selected`를 기록한다. 먼 고유 상호 재탐색의 결과 범위는 `all`, 현재 반경 안의
직접 포커스는 `near`로 구분한다.

### 검토한 대안과 시행착오

`nearOnly=false`로 돌아가 주변 결과가 없을 때 전국 결과를 그대로 표시하는 방식은 고유 상호를
찾지만 일반 카테고리 검색의 전국 결과 범람도 함께 되살린다. 입력 화면에서만 정확한 결과를
탭하도록 요구하는 방식은 엔터·음성 검색·직접 결과 URL에서 같은 검색어가 다르게 동작한다.
따라서 결과 지도 자체에서 정확히 하나인 고유 상호만 목적지 의도로 판정하고 바로 연다. 카카오
결과가 첫 페이지에서 끝나지 않거나 전체 수가 노출 가능 수보다 크면 동명 장소가 더 있을 수
있으므로 자동 포커스하지 않는다. 이 조건 덕분에 `카페` 같은 광범위 검색어도 주변 목록에 남는다.

### 영향과 재검토 조건

자동 중심 이동은 검색어마다 한 번만 수행한다. 사용자가 이후 지도를 옮겨 `이 지역에서 다시
검색`을 누르면 같은 고유 상호로 되돌리지 않는다. 카카오 외 데이터만 가진 먼 등록 장소도
지원해야 하거나 동명 지점 선택이 필요해지면, 전국 exact-name 전용 RPC와 선택 UI를 함께
설계해 재검토한다.

## SEARCH-005 — 장소 포커스는 검색 직전 지도 카메라에서 시작

- 날짜: 2026-08-21
- 상태: 대체됨 (`SEARCH-006`)
- 관련 구현: `components/map/MapHome.tsx`, `hooks/useMapDeepLinks.ts`, `lib/mapCamera.ts`, `lib/mapFocus.ts`

### 배경

검색 화면은 네이티브 스택에서 지도 탭 위에 올라간다. 이때 아래의 네이버 지도 surface가
분리됐다가 다시 붙을 수 있는데, 메인 지도의 `initialCamera`는 저장된 지도 상태를 무시하고
항상 사용자 위치를 사용했다. 따라서 장소 A를 보다가 B를 검색해 선택하면 A에서 B로 이어지지
않고, 사용자 위치가 잠깐 나타난 뒤 B로 이동했다. 기존 검색 기준점은 마지막 중심의 위·경도만
저장해 줌·기울기·방향을 복원할 수도 없었다.

### 결정

메인 지도는 마지막 카메라의 중심·줌·기울기·방향을 렌더링 구독이 없는 세션 스냅샷으로 즉시
기록한다. 검색에서 등록 장소나 카카오 일반 장소를 선택하는 순간 그 스냅샷을 포커스 요청의
불변 출발점으로 함께 전달한다. 지도 탭이 다시 포커스된 뒤 선언형 카메라로 출발점을 먼저
복원하고, 복원이 끝난 다음 목적지까지 이동한다. 최초 구현은 복원 중 네이티브 surface 프레임을
가리고 기존 `Fly` 애니메이션을 사용했으나, 이 표현 방식은 `SEARCH-006`에서 대체한다.

검색 화면 아래에서 지도 탭이 포커스를 잃은 동안 발생한 카메라·따라가기 이벤트는 마지막으로
보인 스냅샷을 덮어쓰지 않는다. 반대로 지도 탭 안의 `근처 다른 장소`처럼 surface가 이미 붙어
있는 상태에서 고른 장소는 불필요한 복원·가림 없이 현재 카메라에서 바로 이동한다.

지도가 재생성될 때 초기 카메라 우선순위는 오버레이가 명시한 목적지, 포커스 요청의 출발점,
마지막 메인 지도 카메라, 사용자 위치, 기본 위치 순이다. 마지막 카메라가 있으면 늦게 도착한
사용자 위치가 복원된 지도를 다시 가져가지 않는다. 검색 기준점용 `mapCenter`는 카메라 이동이
끝났을 때 갱신해 데이터 조회가 이동 프레임마다 반복되지 않게 한다.

### 검토한 대안과 시행착오

검색 화면이 떠 있는 동안 목적지 카메라 명령을 먼저 보내는 방식은 분리된 네이티브 지도가
명령을 버려 실패했다(`9169879`, `e6c4e35`). 목적지까지 이동하는 전체 구간을 커튼으로 가리는
방식은 사용자가 원한 공간적 이동 맥락을 없애 롤백했다(`128ce4f`). `transparentModal`로 지도
surface 분리를 피하는 방식도 iOS에서 검색 화면이 떠 있는 카드처럼 보여 채택하지 않았다.
이번 결정은 목적지를 미리 옮기거나 이동을 숨기지 않고, 출발점만 복원한 뒤 이동 전체를 보여준다.

### 영향과 재검토 조건

검색 입력의 등록 장소·일반 장소, 최근 검색, 즐겨찾기, 음성 검색의 고유 상호 자동 포커스가
같은 출발점 계약을 사용해야 한다. 복수 결과 지도 안에서 목록이나 마커를 선택하는 동작은 그
결과 지도의 현재 카메라에서 상세로 이동하므로 대상이 아니다. 지도 SDK나 네이티브 스택 전환
방식을 바꾸면 detach 시점과 선언형 카메라 반영 순서를 실기기에서 다시 검증한다.

## SEARCH-006 — 검색 장소 이동은 지도를 가리지 않고 직접 팬·줌

- 날짜: 2026-08-21
- 상태: 활성 (`SEARCH-007`이 시작 시점 보완)
- 대체 대상: `SEARCH-005`의 복원 가림막과 `Fly` 표현 방식
- 관련 구현: `components/map/MapHome.tsx`, `hooks/useMapDeepLinks.ts`

### 배경

`SEARCH-005`의 첫 구현은 출발 카메라를 네이티브 지도에 다시 적용하는 동안 테마 배경색으로
지도 전체를 덮고, 복원이 끝나면 `Fly`로 목적지까지 이동했다. 실기기에서 다크 모드 배경은
검은 화면으로 보였고, `Fly`는 먼 장소로 갈 때 전국이 보일 정도로 중간 줌을 낮췄다. 둘 다
“직전에 보던 지도에서 바로 선택한 장소로 이동”한다는 사용자 기대와 반대였다.

### 결정

검색·검색 결과 화면에서 지도 탭으로 돌아갈 때는 `navigate('/')`로 같은 경로의 새 route를
쌓지 않고 `dismissTo('/')`로 기존 `(tabs)` route까지 스택을 되감는다. 이렇게 기존 네이티브
지도 인스턴스와 카메라를 그대로 보존한다. 최초 구현은 화면 포커스가 돌아온 시점에 목적지
이동을 시작했으나, 실제 노출 완료보다 이른 시점이어서 `SEARCH-007`에서 보완한다. 별도의
선언형 카메라 복원, 타이머, 지도 가림막은 사용하지 않는다. 직전 카메라
스냅샷은 검색 왕복이 아니라 지도가 실제로 다시 마운트되는 예외 경로의 `initialCamera`
폴백으로만 사용한다.

메인 지도 안의 `근처 다른 장소`처럼 지도 route가 이미 현재 화면인 선택은 `POP_TO` 대상이
아니므로 `setParams`로 같은 딥링크 계약을 실행한다. 이때 등록 장소와 일반 장소 파라미터를
상호 배타적으로 비워 앞선 선택이 다시 처리되지 않게 한다.

목적지 이동은 500ms `EaseOut` 팬·줌으로 통일한다. 애니메이션을 완전히 없애 공간적 맥락을
끊지는 않되, 장거리 이동도 기다리는 느낌 없이 빠르게 끝내는 길이다. `Fly`처럼 거리에 따라
중간 줌을 크게 낮추는 애니메이션은 검색 장소 포커스에서 사용하지 않는다. 새 포커스 요청을
받으면 사용자 위치 따라가기를 먼저 해제해 비동기 장소 조회 사이에 카메라가 내 위치로
이동하지 않게 한다.

### 검증과 재검토 조건

등록 장소와 카카오 일반 장소, 최근 검색, 즐겨찾기, 음성 검색의 고유 상호 자동 포커스가 모두
같은 표현을 사용한다. 가까운 장소와 먼 장소 모두 검은 프레임이나 전국 줌 없이 출발 지도에서
목적지까지 이어져야 한다. 검색 왕복 뒤 기존 지도 route key가 유지되는지도 회귀 검증한다.
네이버 지도 SDK가 `EaseOut`의 줌 보간 방식을 바꾸거나 Expo Router의 `dismissTo` 동작이
달라지면 실기기에서 다시 검증한다.

## SEARCH-007 — 지도 노출이 끝난 뒤 목적지 이동 시작

- 날짜: 2026-08-21
- 상태: 활성
- 보완 대상: `SEARCH-006`의 이동 시작 시점
- 관련 구현: `components/map/MapHome.tsx`, `hooks/useMapDeepLinks.ts`

### 배경

Expo Router의 `dismissTo('/')`는 기존 지도 인스턴스를 보존했지만, `useIsFocused()`는
native-stack 팝 전환이 끝난 뒤가 아니라 시작할 때 `true`가 된다. 등록 장소와 카카오 일반
장소의 카메라 효과가 이 값만 기다리면서 검색 화면 뒤에서 900ms 이동을 먼저 시작했고,
사용자에게 지도가 다시 보일 때는 이미 애니메이션 중간이었다.

### 결정

메인 지도는 루트 `(tabs)` route의 `transitionEnd` 중 `closing: false`를 상시 구독한다. 이
이벤트는 해당 route의 `onAppear`에서 발생한다. 이후 두 번의 `requestAnimationFrame`을 거쳐
직전 지도 프레임이 최소 한 번 실제로 합성된 다음 등록 장소와 카카오 장소의 딥링크 이동을
허용한다. 검색 화면의 `animation: 'none'`에서도 `onAppear` 이벤트를 기준으로 삼는다.

다른 탭에서 지도 탭으로 돌아오는 경우에는 루트 stack 전환이 없으므로, 지도 탭 focus 후 두
프레임만 기다린다. 같은 지도 안의 `근처 다른 장소` 선택은 이미 노출이 완료된 상태라 지연하지
않는다. 빠르게 다른 화면이 올라오거나 컴포넌트가 사라지면 예약된 프레임을 취소한다.

애니메이션은 500ms `EaseOut`을 사용한다. SDK의 실제 `Fly`는 장거리에서 중간 줌을
전국 단위까지 낮추므로, 이전 회귀를 되살리지 않기 위해 사용하지 않는다.

### 검증과 재검토 조건

검색 입력, 검색 결과, 최근 검색, 즐겨찾기, 고유 상호 자동 포커스에서 `직전 지도 완전 노출 →
전체 이동 시작` 순서를 확인한다. 등록 장소와 일반 장소, 가까운 거리와 서울–제주급 장거리,
위치 따라가기 상태를 함께 검증한다. native-stack 전환 이벤트나 Expo Router 계층이 바뀌면
루트 navigation listener의 대상과 두 프레임 보장을 다시 확인한다.

검색을 즉시 실행했다. 빠르게 입력하면 사용자가 실제로 보지 않을 중간 문자열마다 세 네트워크

검색은 이미 300ms 지연을 두었지만 등록·카카오 중복 제거와 요청 생명주기를 별도로 구현했다.

### 결정

- 일반 타이핑 검색은 마지막 입력 뒤 300ms가 지난 검색어만 요청한다. 음성 검색 완료와 엔터로

- `searchUnifiedPlaces`가 등록 장소·라이딩 추천·카카오 일반 장소를 병렬 조회하고, 등록 장소와
  같은 카카오 결과를 한 곳에서 제거한다. 검색 화면과 지점 검색이 같은 기준을 사용한다.
- React Query와 수동 지점 검색 모두 `AbortSignal`을 Supabase RPC와 카카오 `fetch`까지 전달한다.
  새 검색이 시작되거나 모달이 닫히면 이전 요청을 취소하며, 취소를 0건 결과로 캐시하지 않는다.
- 결과 지도는 URL로 확정된 검색어를 한 번 조회하므로 디바운스하지 않되, 화면 이동이나 검색 범위
  변경 시 이전 요청을 취소하는 계약은 동일하게 사용한다.

### 검토한 대안과 시행착오

React Query 캐시만으로도 같은 검색어의 중복 호출은 줄지만 타이핑 중간 문자열은 모두 다른 키라
요청 수를 줄이지 못한다. 응답 순서 번호만 비교하면 오래된 결과가 화면을 덮는 것은 막아도 이미
시작한 외부 요청 비용은 남는다. 따라서 디바운스와 전송 계층 취소를 함께 적용한다.

### 영향과 재검토 조건

실기기에서 한글 조합 입력, 빠른 삭제와 재입력, 음성 중간 결과, 카카오 장애 시 등록 장소 결과를
확인한다. 300ms가 검색 반응을 느리게 만든다는 근거가 쌓이면 요청 취소는 유지한 채 지연만 조정한다.

## SEARCH-010 — 공급자 일부 실패는 0건이나 유일한 결과가 아니다

- 날짜: 2026-10-11
- 상태: 활성
- 관련 구현: `lib/api/search.ts`, `lib/api/kakaoLocal.ts`, `lib/providerErrors.ts`,
  `app/search.tsx`, `app/search-results.tsx`, 지점·주소 검색 모달

### 배경

등록 장소·라이딩 추천·카카오 검색 중 하나가 실패하면 성공한 결과까지 버리거나,
실패를 빈 배열로 바꿔 정상적인 0건처럼 표시할 수 있었다. 실패한 소스에 같은 이름의
다른 장소가 있는지 확인하지 못했는데도 하나뿐인 결과로 자동 이동하는 것도 부정확하다.

### 결정

- 소스별 성공 결과는 보존하고 `failedSources`로 부분 실패를 전달한다. 전체 실패·취소는
  성공한 0건으로 반환하지 않는다. 검색 화면은 부분 실패 안내와 확인된 결과를 함께 보여준다.
- 정상 0건 화면·0건 분석 이벤트·정확히 하나인 장소 자동 이동은 필요한 모든 소스가
  성공한 경우에만 실행한다. 지점 검색은 사용하지 않는 라이딩 추천 소스의 실패로 막지 않는다.
- 카카오 검색은 10초 후 요청을 취소하고 취소·시간 초과·설정 오류·429·5xx·잘못된 응답을
  구분한다. 키 누락과 401/403 이후 같은 앱 프로세스에서 해당 공급자를 다시 호출하지 않는다.
  설정을 복구하면 앱을 완전히 종료한 뒤 다시 실행해 재검증한다.
- 일시 실패의 자동 재시도는 최대 1회다. 설정·요청 오류·잘못된 응답·429·취소는 자동
  재시도하지 않는다. 사용자 안내에 공급자 원문·키·요청 URL을 넣지 않는다.
- 네이티브 POI의 부가 정보 보완만 `throwOnError: false`를 명시해 기존 POI를 유지한다.
  필수 검색에서 암묵적으로 오류를 숨기지 않는다. 주소 검색은 닫거나 검색어를 바꾸면 요청을
  취소해 이전 응답·오류가 새 화면을 덮지 않게 한다.
- 지도 주변 범위·전국 정확 상호 예외·등록/일반/라이딩 추천 순서·중복 제거는 변경하지 않는다.

### 검토한 대안과 시행착오

하나의 `Promise.all`로 묶으면 카카오 장애가 등록 장소 검색까지 막는다. 모든 실패를 빈
배열로 바꾸면 데이터가 없는지 기능이 고장났는지 알 수 없어 제보 화면으로 잘못 유도한다.
따라서 성공 데이터와 실패 메타데이터를 분리한다. 실패한 소스가 있는 상태에서 확인된
하나의 장소로 자동 이동하는 접근도 채택하지 않는다.

### 영향과 재검토 조건

`tests/providerSearch.test.ts`에서 대역 기반 장애 주입으로 검증한다. 이는 실제 공급자·
실기기 화면 검증을 대체하지 않는다. 검색 외 역지오코딩·지도·길안내·날씨·유가의 실패 경계와
원격 차단·Sentry 진단은 PROVIDER-001 후속 범위이며 전체 완료로 표시하지 않는다.

## SEARCH-011 — 네이버 지역 검색으로 주택명 누락 보완 가능성 검증

- 날짜: 2026-10-11
- 상태: 대체됨(SEARCH-012, 외부 검증 기록은 유지)
- 관련 구현: 향후 `lib/api/search.ts`, `lib/api/generalPlaces.ts`, 검색 입력·결과·지점 검색
- 외부 설정: NAVER API HUB의 `motomap-local-search`, 지역 검색 API만 등록

### 배경

사용자가 지정한 주택명이 네이버 지도 앱에는 있지만 모토맵에는 나오지 않았다. 기존
카카오 키워드 검색과 네이버 클라우드 Geocoding에 같은 명칭 및 띄어쓰기 변형을 요청하면
모두 정상 응답으로 0건이었다. 지도 앱의 검색 데이터와 공개 API의 검색 범위를 동일하다고
가정하지 않고 실제 공개 API 결과를 확인했다. 검색어 원문·주택 주소·좌표·인증키는 이
기록에 저장하지 않는다.

### 검증 결과와 시행착오

- 기존 NAVER Developers 앱은 네이버 로그인만 사용 중이었다. 공식 Playground 호출은
  `Scopes are Empty` 인증 오류로 실패했으며, 이를 검색 결과 0건으로 취급하지 않았다.
- 기존 앱에 검색 API를 추가하려 했으나 `신규로 등록할 수 없는 API`로 저장이 거부됐다.
  미저장 변경을 버리고 기존 로그인 제공 정보·서비스 URL·콜백 URL이 유지됨을 확인했다.
- 검색 API는 2026-07-31부터 신규 신청이 NAVER API HUB로 이관됐다. 사용자가 API HUB
  이용약관과 필수 제3자 제공 동의에 직접 동의한 뒤, 별도 지역 검색용 앱을 등록했다.
  기존 로그인·지도용 키를 교체하거나 앱·DB·배포 설정을 수정하지 않았다.
- 새 공식 `GET https://naverapihub.apigw.ntruss.com/search/v1/local` 호출은 정확한 명칭과
  띄어쓰기 변형 모두 HTTP 200으로 같은 주택 결과를 1건 반환했다. 분류는 `시설,건물>주택`,
  주소는 독립적으로 조회했던 주소 후보와 일치했으며 좌표는 유효한 국내 WGS84 범위였다.
  관찰한 `mapx`·`mapy`는 10^7 배 정수 문자열이므로 후속 어댑터에서 단위를 검증해야 한다.
- 해당 응답의 `total`과 `display`는 각각 5였지만 실제 `items`는 1개였다. 반환된 한 건을
  발견했다는 사실과 전체 데이터에서 유일하다는 판정은 다르다. 기존 카카오의 완결성 판정
  로직을 그대로 이식하거나 이 응답만으로 자동 포커스하지 않는다.
- 도로명주소 API 공식 체험은 정확한 주택명·띄어쓰기 변형에서 정상 0건이었다. 차수를 뺀
  명칭으로는 다른 차수의 건물이 나와 대체하지 않았다. 도로명주소 후보로는 주소 API와
  기존 네이버 Geocoding 모두 1건을 반환했으므로 주소 입력 보완도 별도로 가능하다.

### 보완 후보와 구현 전 조건

- 카카오 검색 전면 교체보다 네이버 지역 검색을 보조 소스로 추가하는 후보를 우선 검토한다.
  이 사례를 해결할 수 있음은 검증했지만 모든 빌라·주택의 검색 커버리지는 보장하지 않는다.
- 새 API도 업체·기관 중심이며 `display` 최대 5, `start`는 1이다. 지도 중심·반경 파라미터가
  없으므로 기존 주변 20km 정책을 결과 좌표로 적용하고, 카테고리 검색을 대체하지 않는다.
- 주소 결과는 목적지 좌표로 사용할 수 있지만 다른 차수·동명 건물로 임의 치환하지 않는다.
- 공급자 중립 결과 타입과 기존 일반 장소 UUID에 대한 공급자 식별자·중복 처리 설계를 먼저
  확정한다. 네이버 결과를 카카오 ID로 저장하거나 리뷰·즐겨찾기·방문 기록을 새 UUID로 끊지
  않는다. 검색 입력·결과 지도·지점 검색·네이티브 POI 진입의 동일성도 함께 검증해야 한다.
- Client Secret은 모바일 번들에 넣지 않고 서버에서만 사용한다. 연동 전 공급자 고지·검색어
  및 위치 전송 범위·사용 조건·호출 한도·장애와 취소 계약을 검토한다. 등록 당시 한시적 무료
  안내를 확인했으나 영구 무료로 가정하거나 유료 전환을 자동 승인하지 않는다.
- 카카오 이륜차 경로 계산·길안내 SDK는 이번 검색 보완과 별개다. 앱 연동·DB 모델 변경·
  공급자 비밀값 배포·푸시·OTA는 이번 검증 범위에 포함하지 않았다.

## SEARCH-012 — 카카오 누락을 네이버 지역 검색으로 보완

- 날짜: 2026-10-11
- 상태: 서버 키·Edge v1 배포·비로그인 SDK 검증 완료 / 실기기 잠금 해제 후 화면 검증 대기
- 관련 구현: `lib/api/externalPlaces.ts`, `lib/api/naverLocal.ts`, `lib/api/generalPlaces.ts`,
  `supabase/functions/naver-local-search/`, 검색·지점·주소 모달

### 결정

- 네이버 지도 웹에서 정확한 건물명은 이름·주택 분류·주소·출발/도착이 중심인 상세로 열린다.
  모토맵도 기존 일반 장소 목록·상세로 이름·주소와 출발/도착을 제공한다. 부동산·광고·네이버
  리뷰를 복제하거나 지도 소비자용 ID/비공개 API를 이용하지 않는다. UI 참고가 API 동등성을 뜻하지 않는다.
- 카카오의 정상 결과가 있으면 네이버를 추가 호출하지 않는다. 카카오의 정상 0건 또는 실패만
  네이버를 조회한다. 입력·결과 지도·지점·제보 검색·POI 보완은 같은 검색 함수를 사용한다.
- 네이버는 최대 5건, 주변 파라미터 없음, 안정 외부 ID 없음이라는 제약을 유지한다. 결과 지도는
  좌표로 기존 20km를 적용한다. 입력/길찾기 지점은 먼 목적지도 선택 가능하다. 네이버 페이지의
  `isEnd`는 false이며, 한 건이어도 목록에서 선택한다. 네이버 지도 앱처럼 자동 상세로 열지 않는다.
- 내부 `KakaoLocalResult`, `kakaoOnly`, 최근 저장의 `type: kakao`는 구자료 호환 이름이다.
  새 optional `source`와 네이버 지도 검색 URL로 실제 출처를 구분하며, 목록 하단에 공급자를 표시한다.
  분석의 `kakao_count` 의미는 유지하고 `naver_count`/`external_count`와 선택 타입을 분리한다.
- 카카오 실패 후 네이버 결과가 있으면 결과는 표시하고 부분 실패를 전달한다. 실패를 정상 0건으로
  바꾸지 않는다. 네이버 upstream은 8초, 클라이언트·일반 장소 연결 조회 전체는 10초에 취소한다.
  검색어·키·주소·좌표·공급자 원문을 오류 로그나 추가 테스트 자료에 저장하지 않는다.
- Client Secret은 서버의 `NAVER_LOCAL_SEARCH_CLIENT_SECRET`, ID는
  `NAVER_LOCAL_SEARCH_CLIENT_ID`로만 주입한다. Maps·로그인 키와 분리한다. 프로젝트 apikey/
  사용자 JWT의 기존 gateway 호환을 유지하며 `verify_jwt=true`만으로 로그인 사용자라고 가정하지 않는다.
  서버 HMAC IP/검증 사용자 호출 제한은 5분 20회·하루 100회, 본문 2KB, no-store다.
  이 제한은 프로젝트 전체 예산 상한이 아니며 API HUB quota·유료 전환은 별도 운영 점검 대상이다.

### 기존 기록과 검토한 시행착오

- 네이버 ID를 임의 생성하거나 `providerId`에 URL/좌표 키를 넣지 않는다. 기존 schema의
  `coordinate` identity를 사용하므로 DB 마이그레이션이 필요 없다. 검색은 일반 장소를 생성하지 않는다.
- 이미 연결된 `generalPlaceId`는 조회·캐시·최근 검색·지도·기록 액션까지 우선한다. 해당 UUID가
  없어졌으면 새 행으로 자동 치환하지 않는다. coordinate 행의 기존 키도 Kakao ID로 오인하지 않는다.
- 네이버 좌표가 기존 행과 다르면 150m 이내에서 NFKC/공백·광역 주소 축약 후 **이름과 주소가
  모두 같은 유일한** 행만 읽어 재사용한다. 후보 상한 100건이면 유일성을 확정하지 않는다.
  주소가 도로명/지번으로 다르거나 후보가 여러 개라면 임의 병합하지 않는다. 모든 공급자·주소
  변경의 영구 동일성을 보장하는 정책은 아니며, 불확실한 별도 기록은 운영 검토 대상으로 남긴다.
- POI 원본 좌표에 저장된 기존 행이 있으면 그 UUID를 먼저 보존한다. 기존 연결 없는 신규 POI만
  정확한 이름의 네이버 좌표 스냅샷을 재사용한다. 같은 좌표의 다른 이름 등록 상호와 건물을 합치지 않는다.
- 제보 승인 연결에는 재사용한 canonical 행의 실제 provider/key를 넘긴다. 새 네이버 좌표 키로
  재계산해 기존 리뷰·즐겨찾기·방문 기록의 승격 연결을 끊지 않는다. 기존 승격 트리거는 변경하지 않는다.

### 검증과 배포 경계
