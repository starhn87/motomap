# 장소·코스 제보 심사

사용자 제보를 사람이 일관되게 심사하고, AI가 동일한 기준으로 근거를 정리하도록 하는 결정을
기록한다. 구체적인 현재 승인 기준은 [submission-approval-policy.md](../submission-approval-policy.md)를
따른다.

## 활성 원칙

1. AI는 승인·반려를 추천할 뿐 최종 결정을 내리지 않는다.
2. 승인·반려·판단 유보를 구분하며, 근거를 찾지 못한 사실만으로 반려하지 않는다.
3. 사람용 문서와 AI 프롬프트는 같은 버전과 규칙 ID를 사용한다.
4. Discord 심사 메시지는 적용한 기준 버전과 규칙 ID를 보여준다.
5. 캠핑 장소는 바이크가 사이트까지 진입해 바로 옆에 주차할 수 있는 오토캠핑만 승인한다.
6. 장소는 안전한 바이크 접근·주차를 공통으로 확인하고, 바이크 특화·라이딩 지원 기능·라이더가
   검증한 일반 목적지 중 하나의 가치 경로를 통과해야 한다. 모든 카테고리에 커뮤니티 언급 수를
   일률적으로 요구하지 않는다.
7. Claude 구조화 출력 스키마에는 공급자가 지원하는 JSON Schema 부분집합만 사용한다. 표시 개수처럼
   API가 지원하지 않는 제약은 프롬프트와 응답 후 처리에서 보장한다.

## MODERATION-001 — 버전이 있는 공통 승인 기준을 사람과 AI가 함께 사용한다

- 날짜: 2026-08-23
- 상태: 활성
- 관련 구현: `docs/submission-approval-policy.md`,
  `supabase/functions/_shared/submissionPolicy.ts`, `supabase/functions/judge-submission/index.ts`

### 배경

기존 AI 심사 프롬프트에는 장소의 대략적인 라이더 관련성과 일부 카테고리 예외만 있었다. 사람이
일관되게 참고할 문서, 근거 강도, 안전·중복 기준, 캠핑과 코스의 구체 경계가 없어 같은 제보가
심사 시점이나 조사 결과에 따라 다르게 추천될 수 있었다.

### 결정

- 사람용 기준 문서를 운영 기준의 원문으로 둔다.
- Edge Function은 같은 버전과 규칙 ID를 가진 요약을 직접 import해 AI 시스템 프롬프트에 넣는다.
- 구조화 판정에는 결론에 사용한 규칙 ID를 필수로 받고 Discord 메시지에 표시한다.
- `approve`는 필수 기준을 통과하고 충분한 근거가 있을 때, `reject`는 기준 미달의 적극적 근거가
  있을 때, `uncertain`은 근거 부족·출처 상충·접근성 미확인일 때 사용한다.
- Discord의 승인·반려 버튼과 기존 푸시 흐름은 유지한다. AI 추천에 따른 자동 변경은 추가하지
  않는다.

### 검토한 대안과 시행착오

- 프롬프트만 길게 수정하면 사람이 기준을 확인하기 어렵고 이후 변경이 조용히 일어나므로
  채택하지 않았다.
- 웹 검색 부재를 반려로 간주하면 작은 라이더 장소와 공급자 미등록 장소를 잘못 제거할 수 있어
  채택하지 않았다.
- AI 확신도가 높으면 자동 승인하는 방식은 출처 오인, 동명 장소, 도로 접근 제한을 사람이 확인할
  기회를 없애므로 채택하지 않았다.

### 영향과 재검토 조건

운영자는 Discord 메시지의 버전·규칙 ID를 기준 문서에서 바로 대조할 수 있다. 실제 심사에서
반복되는 예외가 쌓이면 규칙을 추가하되 문서와 AI 요약을 같은 커밋에서 함께 변경한다. AI 추천과
사람 결정의 불일치율을 계측할 수 있게 되면 기준별 정확도를 재검토한다.

## MODERATION-002 — 구조화 출력은 공급자가 지원하는 스키마 부분집합만 사용한다

- 날짜: 2026-08-24
- 상태: 활성
- 관련 구현: `supabase/functions/judge-submission/index.ts`,
  `supabase/functions/_shared/submissionPolicy.ts`

### 배경

판정에 직접 사용한 규칙 ID만 간결하게 표시하려고 `criteria` 배열을 최대 6개로 제한했다. 이를
Claude 구조화 출력의 JSON Schema에 `maxItems: 6`으로 표현했지만 Claude API는 배열 제약 중
`minItems` 0 또는 1만 지원하고 `maxItems`는 지원하지 않았다. Edge Function 타입 검사와 배포는
통과했지만 실제 판정 요청이 HTTP 400으로 거부됐고, 성공 표식이 남지 않아 5분 주기 누락 판정
작업이 같은 제보를 반복 호출했다.

### 결정

- 구조화 출력 스키마에는 Claude가 지원한다고 명시한 키워드만 사용한다.
- `criteria`는 지원되는 `minItems: 1`과 규칙 ID `enum`으로 유효성을 보장한다.
- 최대 6개라는 표시 품질 제약은 프롬프트에 중요도 순서와 함께 명시하고, 응답을 받은 뒤
  `slice(0, 6)`으로 방어적으로 보장한다.
- 백그라운드 판정 실패는 제보 원문이나 API 키를 로그에 남기지 않고 테이블·레코드 ID·정규화한
  오류 메시지만 Edge Function 로그에 기록해 Discord 알림만으로 원인을 추적하는 상황을 막는다.
- 승인 기준과 규칙 ID 자체는 바뀌지 않았으므로 이번 수정으로 기준 버전을 올리지 않는다.

### 검토한 대안과 시행착오

- 타입 검사만으로는 원격 API의 JSON Schema 부분집합 위반을 찾을 수 없었다.
- 최대 개수 제한을 완전히 없애면 Discord 메시지가 불필요하게 길어질 수 있어 기존 의도는
  프롬프트와 응답 후 처리로 유지한다.
- 지원하지 않는 제약을 설명 없이 스키마에 남기는 방식은 API 요청 전체를 실패시키므로 사용하지
  않는다.

### 영향과 재검토 조건

구조화 출력 스키마를 변경할 때는 공급자 공식 문서의 지원 목록을 먼저 확인한다. SDK가 지원하지
않는 제약을 자동 제거하고 응답 후 검증까지 제공하는 안정적인 도우미를 도입하면 수동 스키마와
후처리 경계를 다시 검토한다.
