# 외부 공급자 장애 대응

네이버 지도, 카카오 로컬·길안내, 기상청 날씨, 에어코리아 미세먼지, 오피넷 유가처럼
모토맵이 직접 통제할 수 없는 SDK·API가 실패해도 사용자가 빈 화면, 무한 로딩 또는 공급자의
기술 오류 문구를 마주하지 않게 하는 결정 기록이다.

관련 구현:

- `lib/api/`, `lib/queryClient.ts`, `lib/toast.ts`
- `hooks/useBikeRoutes.ts`, `hooks/useWeather.ts`, `hooks/useGasStations.ts`
- `components/map/MapHome.tsx`, `app/search-results.tsx`, `app/navi.tsx`
- `modules/kakao-navi/`, `docs/domain-decisions/service-suspension.md`

## 먼저 확인할 활성 원칙

1. 로딩, 정상적인 빈 결과, 일부 성공, 오래된 데이터, 재시도 가능한 실패, 운영상 비활성 상태를
   서로 다른 상태로 취급한다. 요청 실패를 빈 배열이나 계속 도는 스피너로 숨기지 않는다.
2. 공급자 SDK·HTTP 응답의 원문, 상태 코드와 내부 설정 이름은 사용자에게 직접 노출하지 않는다.
   사용자 문구는 무엇을 못 하는지와 다음 행동만 한국어로 알리고 원문은 진단 정보로만 남긴다.
3. 사용자가 직접 시작한 동작은 같은 화면에서 즉시 피드백한다. 백그라운드 갱신 실패는 전역
   토스트로 방해하지 않고 이전 데이터 유지, 섹션 내 상태 또는 조용한 폴백을 사용한다.
4. 일부 공급자만 실패해도 나머지 결과와 기능은 유지한다. 검색의 일부 실패를 0건으로 오인하거나
   날씨·유가 실패 때문에 장소·지도 전체를 닫지 않는다.
5. 네트워크·타임아웃·일시적인 서버 오류만 제한적으로 재시도한다. 인증·권한·키·상품 비활성화
   같은 운영 설정 오류는 자동 재시도하지 않고 같은 세션의 반복 호출을 차단한다.
6. 지도와 길안내처럼 진행을 막는 실패에는 무한 로딩 대신 명시적인 오류 상태, `다시 시도`와
   안전하게 돌아갈 경로를 함께 제공한다.
7. Sentry에는 공급자, 작업, 정규화한 오류 종류, 공급자 코드, 재시도 횟수와 릴리스 문맥만 남긴다.
   API 키·토큰·전체 응답·정확한 위치·검색어는 남기지 않는다.
8. 운영 중단·재개 상태는 일반적인 공급자 장애보다 우선한다. `suspended` 또는 `preparing`에서는
   오류 UI를 시험하려고 지도·위치·길안내 SDK를 초기화하지 않는다.

## PROVIDER-001 — 오류 종류와 사용자 상태를 공통 계약으로 정규화

- 날짜: 2026-08-31
- 상태: 활성(1.2.8 구현 필수)
- 예상 구현: `lib/providerErrors.ts`, 공급자별 API 모듈과 화면별 비동기 상태

### 배경

현재 오류 처리는 호출부마다 다르다. 검색 결과 화면은 실패와 0건을 구분하지만 일반 카카오 검색은
실패를 빈 배열로 돌려주기도 한다. 날씨·유가는 쿼리 실패 시 선택 기능이 조용히 사라질 수 있고,
카카오 KNSDK 초기화 실패는 공급자 원문을 토스트 설명으로 노출한다. 길안내 경로가 없는 상태를
로딩과 같은 조건으로 그려 초기화가 이미 실패했어도 스피너와 비활성 버튼이 계속 남는다.

공급자마다 별도의 거대한 요청 래퍼를 만들면 네이티브 SDK와 REST API의 차이를 감추고 불필요한
추상화가 된다. 대신 오류 분류, 사용자 문구, 재시도 가능 여부와 진단 필드만 공유하고 화면은
기능 중요도에 맞는 상태를 직접 표현한다.

### 결정

공통 오류 분류는 최소한 다음 계약을 가진다.

| 오류 종류 | 예 | 자동 재시도 | 사용자 대응 |
|---|---|---:|---|
| `cancelled` | 화면 이탈, 새 검색으로 이전 요청 취소 | 없음 | UI·Sentry 모두 생략 |
| `offline`·`timeout` | 연결 없음, 제한 시간 초과 | 최대 1회 | 이전 데이터 유지 또는 다시 시도 |
| `rate_limited` | HTTP 429 | `Retry-After`가 허용하는 경우만 | 잠시 후 다시 시도 안내 |
| `temporary` | HTTP 5xx, 공급자 일시 장애 | 지수 지연으로 최대 1회 | 기능 단위 오류·부분 성공 |
| `configuration` | 401·403, 앱 키·번들 ID·상품 비활성 | 없음 | 점검 중 안내, 세션 반복 호출 차단 |
| `invalid_request` | 잘못된 좌표·인자, 지원하지 않는 경로 | 없음 | 입력·범위에 맞는 구체적인 안내 |
| `invalid_response` | 필수 필드 누락, 해석 불가 응답 | 없음 | 일반 오류 안내, 진단 이벤트 기록 |

공통 오류 객체는 `provider`, `operation`, `kind`, `retryable`, 선택적인 HTTP 상태·공급자 코드와
원본 `cause`를 가진다. 화면에는 정규화한 사용자 문구만 전달하고 `cause`는 Sentry 직렬화 전에
민감 정보를 제거한다. 사용자 취소와 정상적인 오프라인은 오류 알림 집계에서 제외하고,
`provider + operation + kind + vendorCode`를 기준으로 같은 이슈를 묶는다.

재시도는 조회처럼 멱등인 동작에만 적용한다. 기본 React Query 재시도 횟수를 기계적으로 따르지
않고 오류 종류에 따라 결정하며, 쓰기·제보·리뷰·푸시 발송은 기존 멱등성 계약이 확인되지 않으면
자동 재시도하지 않는다. 설정 오류가 한 번 확인되면 같은 공급자·기능의 자동 요청을 앱 세션에서
중단한다. 사용자가 누르는 `다시 시도`도 설정 오류에는 즉시 재호출하지 않고 운영 상태가 바뀌거나
앱이 새로 시작된 뒤에만 허용한다.

기능별 표현은 다음 기준을 따른다.

| 기능 | 실패 시 유지할 것 | 오류 UI와 다음 행동 |
|---|---|---|
| 네이버 지도 | 지도 밖 검색·설정·지원 진입 | 초기화 제한 시간을 넘기면 지도 영역에 `지도를 불러오지 못했어요`, `다시 시도` 표시 |
| 카카오 길안내 | 목적지와 직전 지도 | 경로 로딩을 종료하고 오류 카드에 `다시 시도`, `지도로 돌아가기` 제공 |
| 통합 검색 | 성공한 등록 장소·라이딩 추천·일반 장소 | 실패한 공급자만 부분 오류로 표시하고 전체 0건 화면과 구분 |
| 날씨·미세먼지·유가 | 마지막 성공 데이터와 기준 시각 | 백그라운드 실패는 기존 값을 유지하고, 최초 실패는 해당 선택 섹션에서만 재시도 |
| 소셜 로그인 | 로그인 화면과 다른 로그인 수단 | 실패한 수단만 안내하고 이메일·다른 공급자 선택은 유지 |

네이버 지도 SDK가 JS에 명시적인 초기화 오류를 주지 않는 경우 `onInitialized`가 정해진 시간 안에
오지 않는 것을 실패 후보로 보고 오류 오버레이를 표시한다. 재시도는 지도 뷰를 안전하게 한 번
재마운트하되 무한 재마운트하지 않는다. 카카오 KNSDK는 `loading | ready | error`를 명시적으로
분리해 초기화·경로 요청 실패 뒤 스피너가 남지 않게 한다.

서비스 상태 엔드포인트에는 필요한 경우 공급자 기능별 `available | degraded | unavailable` 상태와
사용자용 문구를 추가한다. 원격 상태가 `unavailable`이면 SDK/API를 호출하기 전에 기능 단위 점검
UI를 표시한다. 이 상태는 공급자 콘솔 장애가 사용자 오류와 경고 메일로 확산되는 것을 줄이는
운영 차단 장치이며, 앱 전체의 `suspended | preparing | active` 상태를 대체하지 않는다.

### 1.2.8 필수 구현·검증 체크리스트

1. 공통 오류 분류와 공급자별 변환 함수를 구현하고 기술 원문이 UI에 직접 노출되는 호출부를
   제거한다.
2. 카카오 길안내 초기화·경로 요청 상태를 명시적으로 분리해 무한 스피너를 없애고 오류 카드,
   다시 시도와 지도 복귀를 제공한다.
3. 통합 검색에서 등록 장소, 카카오 일반 장소와 라이딩 추천의 일부 성공을 유지하고 공급자 실패를
   실제 0건과 구분한다.
4. 날씨·미세먼지·유가의 마지막 성공 데이터, 기준 시각, 최초 실패와 백그라운드 갱신 실패 UI를
   구분한다.
5. 네이버 지도 초기화 감시와 한 번의 재시도·오류 오버레이를 추가한다. 네이티브 오류 이벤트를
   추가해야 하면 1.2.8 빌드에 포함하고 브리지 계약 변경 여부를 함께 검토한다.
6. 원격 서비스 상태의 공급자 기능 플래그와 세션 단위 반복 호출 차단을 구현한다. 상태 확인 실패는
   `OPS-002`의 앱 전체 실패 폐쇄 원칙을 약화시키지 않는다.
7. Sentry fingerprint와 비민감 진단 필드를 적용하고 취소·일반 오프라인·예상된 미지원 경로가
   운영 장애 알림을 오염시키지 않는지 확인한다.
8. 격리된 내부 테스트 환경에서 오프라인, 타임아웃, 429, 5xx, 401·403·상품 비활성화,
   잘못된 응답, SDK 초기화 미완료를 각각 재현한다. 각 경우에 무한 로딩·빈 화면·원문 노출·
   반복 호출이 없는지 확인한다.
9. 위 검증이 끝나기 전에는 production 공급자를 복구하거나 공개 상태를 `active`로 바꾸지 않는다.

### 검토한 대안과 시행착오

- 모든 실패를 토스트로 표시하면 백그라운드 자동 갱신 때 사용자가 행동할 수 없는 알림만 반복된다.
- 모든 실패를 빈 배열·`null`로 바꾸면 정상적인 0건과 장애를 구분할 수 없고 잘못된 빈 화면을 만든다.
- 모든 API를 한 요청 래퍼로 묶으면 KNSDK 초기화, 네이티브 지도 생명주기와 REST 요청의 재시도
  의미가 서로 달라 오히려 분기가 숨는다.
- 설정 오류에도 자동 재시도하면 사용자 화면은 나아지지 않으면서 공급자 경고 메일, 제한 소모와
  Sentry 이벤트만 늘어난다.
- 공급자 기능을 다시 활성화해 구버전 오류를 피하는 방식은 운영 중단 안전 경계를 무력화하므로
  사용하지 않는다.

### 영향과 재검토 조건

새 외부 SDK·API를 추가할 때는 출시 전에 오류 종류, 빈 결과, 이전 데이터 폴백, 재시도와 원격
차단 방식을 이 문서에 연결한다. 공급자 오류 코드나 React Query의 기본 재시도 정책을 바꾸면
분류 매핑과 장애 주입 테스트를 함께 갱신한다. 오류율·재시도 성공률과 사용자 이탈을 관측한 뒤
자동 재시도 횟수를 늘릴 수 있지만, 설정 오류 반복 호출 차단과 사용자 원문 비노출 원칙은 유지한다.
