# 반복 성능 조사 — 숨은 지도 센서의 소유권부터 개선

성능 최적화 전체 완료 보고서가 아니다. 10월 10일 밤 시작해 11일로 이어진 내부 조사다.
현재는 시작·지도 대기의 반복 기준값 첫 블록과 검색 화면 대기 비교를 수집한다.
사진·길안내 10회 반복과 30분 사용, 20회/3블록의 최종 A/B 판정은 별도 후속이다.

## 실행 조건과 범위

- 같은 iPhone 16/iOS 27.0.1, 유선 연결, 로컬 Apple Development 서명 Release 1.2.8/build 1/runtime 1.2.8.
- Expo 57.0.27/RN 0.86.3/NMapsMap 3.24.0/KNSDK-UI 1.12.14 조합과 내부 채널을 유지한다.
- 사용자가 잠금 해제·동일 Wi-Fi·저전력 모드 해제 준비를 확인했다. 밝기·SDK 타일 캐시·온도는
  완전히 통제하지 못했다. 호스트의 로컬 빌드가 일부 기준값 수집과 겹쳐 관찰 부하 차이도 남는다.
- 앱·인증·즐겨찾기 데이터를 지우지 않는다. force launch는 프로세스 새 시작이며 디스크 캐시가 빈
  cold cache가 아니다. 이전 중단 화면 측정과 활성 지도 기록을 섞지 않는다.
- 공개 preparing/자동 작업 정지 유지. Git 푸시·EAS/TestFlight 업로드·production OTA·공개 재개 없음.
- 원본 trace/XML/서명·설치 결과는 저장소 밖 private 로컬에만 있다. 기기 ID·좌표·계정은 기록하지 않는다.

## 변경 전 — 예비 5회와 본 측정 첫 블록 7회

각 실행은 Activity Monitor의 모토맵 bundle ID launch 30초 기록이다. 시작·종료 준비 때문에
trace 전체는 약 31초다. 모든 표본에서 대상 process를 확인하고 export의 ID/ref를 해석했다.
예비 표본은 본 측정 집계에 합치지 않았다. 현재 도구·export 경로 실패는 0회다.

| 지표 | 예비 5회 중앙값 | 본 측정 7회 중앙값 | 본 측정 최소~최대 |
|---|---:|---:|---:|
| Footprint 표본 최고 | 324.85 MiB | 370.11 MiB | 333.89~386.41 MiB |
| 종료 직전 footprint | 232.99 MiB | 233.80 MiB | 232.44~236.46 MiB |
| 종료 직전 OS CPU Time | 1.897초 | 2.053초 | 2.008~2.139초 |
| 10~20초 CPU | 1.48% | 1.48% | 1.39~1.87% |
| 20~30초 CPU | 0.92% | 0.93% | 0.87~1.39% |

시작 피크는 흔들리지만 종료 직전 값은 이 작은 블록에서 비슷했다. 앱을 매번 다시 시작했으므로
이 결과로 동일 프로세스의 반복 사용 누수나 장기 안정성을 판정할 수 없다. 본 측정 목표 20회를
채우지 않았으며 7표본의 P90은 최대값과 같아 정밀한 상위 분포로 보고하지 않는다.

CPU는 Instruments % CPU 원값을 유효 구간 시간으로 가중한다. 10초/20초 경계와 겹친 표본도
겹친 구간만 포함한다. 10월 10일 예비 보고서의 start 기준 집계와 경계 처리 방식이 조금 다르므로
소수점 차이를 성능 변화로 보지 않는다. Time Profiler sample weight와 OS CPU Time을 혼동하지 않는다.

## 첫 개선 — 가려진 지도의 센서만 중지

코드에서 지도 홈과 place-preview가 각각 위치·방향 구독을 생성하며, 기존 훅의 중지 조건은
길안내 여부뿐임을 확인했다. 숨은 화면이 센서를 소유할 수 있는 결함과 CPU 감소율은 구별한다.

- 화면 포커스·홈의 실제 노출 완료·앱 active·길안내가 아님을 모두 만족할 때만 지도 구독을 유지한다.
- 지도 인스턴스·직전 카메라·마커 windowing은 그대로 보존한다. freeze/unmount하지 않는다.
- 경로 미리보기는 숨은 홈에 의존하지 않고 자기 화면에서 위치만 구독한다. 방향 watch는 만들지 않는다.
- High/10m 정확도·늦은 native watch cleanup·KNSDK GPS/백그라운드 동작은 그대로다.
- 소스: `0949971`과 Router import 보정 `2f20f37`. 후자는 Expo 57의 bundle 검사가 직접
  @react-navigation/native import를 거부한 뒤 기존 expo-router/react-navigation 경로로 수정한 것이다.
  검사 비활성화·추가 라이브러리 설치로 우회하지 않았다.

타입 검사·Node 전체 테스트 49개·release 정합성·diff 검사를 통과했다. Python 집계 검사는
5개이며 XML 참조/다른 process 제외·시간 경계·누락 값·분위수·저장소 밖 원본 경계와
수집기의 20초 후 고정 검색 화면 전환을 검증한다.
내부 로컬 Release 빌드와 서명·권한·채널 검사를 통과했고 기존 앱 위에 설치했다.
사용자가 개선본의 지도·내 위치·장소 마커가 정상 표시된다고 확인했다.
후속으로 사용자가 지도↔탐색, 검색 복귀, 경로 미리보기→안내→다른 앱→복귀→종료도 정상이라고
확인했다. 이 기본 회귀 확인은 10회 반복·위치 callback 계측·성능 개선율 확정과 구별한다.

## 검색 화면 대기 — 원인에 맞춘 비교

기존 앱을 90초 launch 기록하고 약 20초 뒤 ridemap://search를 전달했다. 사용자가 실제 검색
화면 표시를 확인했다. 입력·다른 버튼 조작 없이 대기했다. 변경 후도 90초 launch로 기록했지만
대화 처리 지연으로 route dispatch가 약 32초로 늦었다. 그러므로 30~60초 구간은 전후 비교에서
제외하고 충분히 뒤인 60~90초만 비교한다. 외부 route dispatch 성공은 픽셀 표시 시각을 자동
계측한 것이 아니며 변경 후 실제 화면 확인은 별도다. 다음 기록부터 수집기의 --search-idle이
20초 뒤 자동으로 같은 route를 연다. 이 시행착오 기록과 표본은 삭제하지 않는다.

| 지표 | 변경 전 1회 | 변경 후 | 해석 |
|---|---:|---:|---|
| 검색 대기 30~60초 CPU | 0.927% | 비교 제외 | route 진입 시각 차이 |
| 검색 대기 60~90초 CPU | 1.134% | 1.095% | 시간 가중값; 단일 쌍 |
| 종료 직전 footprint | 244.83 MiB | 243.55 MiB | 사진·지도 반복 누수 측정과 별개 |

차이가 작고 반복·진입 시각 통제가 충분하지 않아 실제 성능 개선 효과는 미확정이다.
소유권 결함을 수정했다는 사실과 수치상의 유의미한 개선은 구별한다. 개선본의 UI 복귀·길안내
검증은 후속 사용자 확인으로 통과했다. 자동 시점 전환의 반복 블록과 위치·방향 callback 수 관찰은 남는다.

## 사진 반복은 미수행 — 작업자 직접 자동화로 전환

사진 기록을 시작한 뒤 사용자가 반복 조작은 Codex가 수행하도록 요청했다. 실제 사진 조작은
한 회도 수행하지 않았으므로 해당 trace를 중단하고 앱을 일반 실행으로 복원했다. 이 기록은
사진 benchmark에서 제외하며 앱 크래시/실패 표본으로 세지 않는다.

- 기존 연결을 사용하는 Xcode 27 Device Hub에서 실제 모토맵 화면을 확인했다. USB 개발자 연결과
  앱 데이터는 바꾸지 않았으며 별도 iPhone Mirroring의 신규 연결·권한도 활성화하지 않았다.
- Device Hub의 기본/전용 창과 정확한 bundle 바인딩을 확인했지만 현재 Computer Use의 좌표
  입력이 실패했다. 화면을 볼 수 있다는 사실을 실제 사진 tap/swipe/pinch 성공으로 해석하지 않는다.
- 멀티터치까지 재현하는 XCTest UI 테스트 러너를 대안으로 검토한다. 새 개발용 테스트 러너
  서명·기기 설치·해당 자동화 방식 승인 전에는 등록/설치하지 않는다. 공개 앱/배포와 분리한다.
- 자동화 화면 전송·테스트 러너 부하가 있는 비교는 같은 도구 조건의 새 블록으로 분리한다.
  사용자에게 다시 수동 10회 반복을 부탁하거나 미수행을 성공으로 기록하지 않는다.

## 후속 후보와 완료 판정

이전 20초 활성 지도 Time Profiler를 ID/ref까지 다시 해석했을 때 2,169 Running 표본 중
PostHog 이름 프레임을 포함한 표본은 354개, screenshot renderer 프레임은 129개였다.
이름 기반의 겹치는 inclusive 분류이며 합산할 수 없다. 스크린샷 capture와 queue 작업이 원인
탐색 후보라는 근거이지 SDK의 전체 CPU 비중·사용률·제거 시 개선율은 아니다.

1. 탭·검색·장소 오버레이·길안내 복귀의 내 위치/카메라 회귀와 숨은 화면 CPU를 확인한다.
2. 같은 사진으로 열기→넘기기→확대→닫기를 10회 연속 수행한다. 각 회차의 피크/복귀 직후,
   블록 종료 후 30초·120초를 기록한다. 매 회차 120초를 기다리지 않는다.
3. 경로/길안내 시작·복귀·종료 10회와 SDK 해제를 같은 방식으로 확인한다. 실제 주행은 하지 않는다.
4. 반복 기준값이 의미 있게 남는 영역만 하나씩 개선한다. 리플레이 비교는 별도 내부 진단으로
   분리하고 마스킹·공개 계측 정책을 함부로 변경하지 않는다.
5. 같은 SDK·계측 설정의 전후 3블록으로 변동 폭·기능 회귀를 확인한 뒤 효과를 확정한다.

기본 복귀 대기는 PERF-004에 따라 30초·120초다. 5분 gcTime 이후나 SDK 캐시 안정화가
원인일 때만 더 긴 실험을 별도로 제안한다. 120초로 줄이려고 cache 정책을 바꾸지 않는다.

## 재현

도구는 `scripts/profile-ios.py`다. 원본 경로는 존재하지 않는 저장소 밖 디렉터리를 지정한다.
기기 ID는 로컬 인자로만 전달하며 보고서·명령 예시에는 실제 값을 넣지 않는다.

```sh
python3 scripts/profile-ios.py record --device "$MOTOMAP_DEVICE_ID" \
  --output /tmp/motomap-baseline-block-1 --label baseline-map-block-1 \
  --count 7 --seconds 30 --rest 10
PYTHONDONTWRITEBYTECODE=1 python3 tests/test_ios_profile.py

# 검색 대기는 수집기에서 같은 시점에 이동한다. --seconds 90이 필요하다.
python3 scripts/profile-ios.py record --device "$MOTOMAP_DEVICE_ID" \
  --output /tmp/motomap-search-block-1 --label search-idle-block-1 \
  --count 3 --seconds 90 --rest 10 --search-idle
```

전체 시작 반복 목표 20회는 7/7/6 세 블록으로 나눈다. launch/수집/대상 확인/export/집계를
자동화하지만 pan·pinch·길안내 UI 동작은 아직 자동화하지 않았다. 도구 실패는 그대로 남기고
첫 실패에서 batch를 멈춘다. 완료 후 앱을 일반 실행으로 복원한다.

## 후속 — 승인된 XCTest 자동화와 검색 대기 전후 3블록

사용자가 별도 테스트 러너 서명·설치·실행, 필요한 테스트 App ID/프로필과 자동 반복 조작을
승인했고 Git 푸시·공개 배포는 금지했다. Xcode 기본 XCTest를 사용하며 새 테스트 프레임워크는
설치하지 않았다. 기존 개발 서명/프로필로 별도 러너 설치에 성공했고 iPhone의 최초 자동화
암호 확인은 사용자가 직접 완료했다. 앱은 삭제하지 않고 비교본을 기존 앱 위에 설치했다.

### 준비 중 실패와 해결 — 성능 표본에서 제외

- 암호 확인 전 러너의 automation-mode timeout은 승인 후 해결했다.
- 외부에서 실행한 앱을 `activate`+URL로 제어하면 접근성 load가 실패했다. 프로세스만
  종료 후 XCTest로 새로 launch해 해결했다. 앱 데이터는 초기화하지 않았다.
- 검색 결과는 개별 `StaticText`가 아니라 여러 텍스트를 묶은 row였다. 실제 트리의 행을
  선택하도록 수정했다. 상세가 보이는데 내부 버튼이 숨은 것은 MAP-038로 보완했다.
- 첫 RSG fixture에는 필요한 사진이 없었다. DB에서 장소명과 사진 개수만 읽어 기존 리뷰
  사진 4장이 있는 공개 장소로 바꿨다. 사용자/리뷰 본문/이미지 URL을 보고서에 기록하지 않으며
  제보·리뷰·즐겨찾기·DB 데이터를 변경하지 않았다.
- 새 fixture에서 1→2장 이동, 핀치 확대 중 pan 후 2장 유지, 축소 후 3장 이동, X로 닫기를
  실기기 assert로 통과했다. 후속 동작은 미수행 사진 trace와 별개다.

### 검색 대기 — 동일 도구 전후 3블록씩

같은 Expo 57/RN 0.86 Release·내부 채널·기기에서 센서 소유권 수정 전후를 비교했다.
양쪽 모두 MAP-038 접근성 설정을 사용했고 Device Hub 화면 전송은 종료했다.
매 블록 앱을 새로 실행→실제 검색 바 탭→입력 화면 확인→20초 대기를 측정했다.
XCTest의 첫 준비 구간을 버려 블록당 유효 3개, 각 비교본 총 **9개**다. 대기 자체는
준비 포함 블록당 80초이며 시작 시간·키보드 표시 시간·실제 장소 검색 성능은 측정하지 않았다.

| 지표 | 수정 전 중앙값 (최소~최대) | 수정 후 중앙값 (최소~최대) |
|---|---:|---:|
| 20초 구간 앱 CPU time | 0.2440초 (0.1897~0.2857) | 0.2095초 (0.1840~0.2783) |
| 앱 physical memory peak | 263.36 MB (259.89~264.16) | 266.88 MB (262.00~286.21) |
| 구간 종료 앱 physical memory | 263.34 MB (259.59~263.80) | 266.85 MB (261.98~285.89) |

메모리는 XCTest가 내보낸 kB 값을 1,000으로 나눈 MB다. 이전 Instruments MiB 표와 직접
비교하지 않는다. CPU time은 앱에서 소비한 누적 시간이며 시스템 전체 CPU%·배터리 지표가 아니다.

- CPU time 중앙값은 약 **14.1% 낮게 관측**됐지만 전후 범위가 겹치고 블록당 CPU 변동도
  있다. 같은 기기의 순차 A→B 실행, 비고정 열/캐시/외부 데이터 조건 때문에 인과적·일반적
  14.1% 개선으로 확정하지 않는다. native 센서 callback 수나 배터리 사용은 직접 계측하지 않았다.
- **메모리 감소는 확인되지 않았다.** 수정 후 중앙값은 약 3.5 MB 높고 두 번째 블록은
  더 높았다. 검색 20초 대기는 중복 센서의 소유권을 확인하는 실험이지 사진/지도 반복 누수
  해소를 입증하는 실험이 아니다. 수치가 좋아 보이도록 cache/정확도를 줄이지 않는다.
- 가려진 위치·방향 구독 중지와 늦은 구독 cleanup은 코드/단위 검사와 기존 기본 기기 검증에
  근거해 유지한다. 이 비교는 소유권 수정의 큰 메모리 개선을 주장하는 근거가 아니다.

사진 반복 및 30초·120초 회복 기록은 같은 러너의 후속 블록으로 진행한다. 도구와 원본 경계는
`scripts/ios-ui-profile/README.md`와 PERF-005에 보존한다.
