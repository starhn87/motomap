# 모토맵 성능 측정·최적화 계획 초안

> 2026-10-10: 패키지·소스 전환과 명확한 자원 해제 결함 수정은 승인됐다(PERF-003).
> 아래 준비 전용 단계는 10월 4일 기록이며, 앱 실측·운영 복구·네이티브 빌드는 여전히 별도 승인 대상이다.
> 패키지 업데이트와 최적화를 별도 커밋으로 남기고 실기기 CPU·메모리 수치는 미측정으로 유지한다.
> 후속 승인: 1.2.8 측정용 로컬 빌드·기기 설치·프로파일 준비를 허용했다. 운영 복구·공개 배포는
> 포함하지 않는다. Xcode 호환성 때문에 실제 설치·실측은 아직 미완료다(아래 11절).
> 이후 안정판 Xcode 27 업데이트를 승인받아 설치했다. 첫 실행 약관 동의는 별도 확인 대기이며,
> 기기 설치·실측은 여전히 미완료다.
> 후속으로 사용자가 직접 약관 동의를 완료했다고 확인했다. Xcode·iOS SDK 27과 Instruments의
> 실기기 온라인 연결을 확인했고 Pods 설치를 재개했다. 설치·실측 완료와는 구분한다.

- 작성일: 2026-10-04
- 현재 상태: **Release 컴파일 통과, 개발자 계약·서명 갱신으로 기기 설치·실측 대기**
- 조사 기준: 앱 저장소 `db51616`, Expo 54 / React Native 0.81.5 / 앱 1.2.7
- 범위: 앱 시작·화면 로드, 지도·길안내, JS·네이티브 CPU, 메모리, 네트워크·캐시, 이미지·목록, 번들·배터리
- 원칙: [성능 의사결정](domain-decisions/performance.md), 기존 [성능 백로그](../PLAN.md#성능구조-후순위-백로그)
- 업그레이드 연결: [패키지 업그레이드 준비 계획](package-upgrade-plan.md). 구버전 최소 기준 → 버전업·안정화 → 신버전 전체 측정 순서로 실행한다.

## 1. 목적과 실행 경계

체감되는 지연을 측정 가능한 구간으로 나누고, 실제 병목이 확인된 순서로 개선한다.
단순히 평균 FPS나 번들 크기 하나를 낮추는 것이 아니라 **빠른 첫 반응, 부드러운 조작,
긴 사용 중 안정성, 정확한 지도·길안내 동작**을 함께 지킨다.

아래 표는 10월 4일 사업자·위치기반서비스 신고 보완 및 대기 시점의 준비 경계다.
10월 10일 소스 작업·로컬 측정 준비에 대한 후속 승인은 문서 상단과 11절을 따른다.

| 시점 | 가능한 작업 | 하지 않는 작업 |
|---|---|---|
| 지금 | 문서·기존 코드 검토, 외부 호출 없는 정적 검사, 측정 시나리오·보고서 설계 | 앱 활성화, Supabase 복구, 공급자 API 활성화·호출, 앱 실행·부하 시험, 계측 코드·라이브러리 추가, 빌드·OTA |
| 신고·보호조치 확인 후 내부 검증 | [OPS-003](domain-decisions/service-suspension.md)의 조건을 확인하고 공개 상태를 `preparing`으로 유지한 채 승인된 내부 테스트 | 성능 측정만을 이유로 중단 게이트 우회, 공개 `active` 전환, 운영 재개 알림 발송 |
| 공개 재개 이후 | 승인된 표본 관찰, 실제 사용 조건에서 회귀 확인 | 무단 대량 API 호출, 원본 위치·이동 경로를 성능 로그에 수집 |

계획 전체를 운영 재개의 필수 조건으로 만들지는 않는다. 재개 조건은
[운영 재개 준비 문서](relaunch-readiness.md)를 따른다. 재현되는 멈춤·크래시나 핵심 기능
실패는 우선 처리하되, 효과가 불확실한 후순위 최적화는 재개 이후에도 진행할 수 있다.
라이딩 지도 Visualizer 등 미출시 기능의 구현·측정은 이번 범위에서 제외한다.

## 2. 현재 구조와 이미 적용된 개선

아래는 **코드·결정 기록에서 확인한 사실**이며, 실제 속도·사용량이 검증됐다는 뜻은 아니다.
장소 수·기기별 사용량·현재 지연 시간은 아직 측정하지 않았다.

| 영역 | 현재 상태 | 이번에 검증할 것 |
|---|---|---|
| 앱 시작 | `app/_layout.tsx`에서 서비스 상태 확인 후 `ActiveRootLayout`을 로드한다. 폰트·인증·설정 복원 등이 이어진다. | 게이트 대기, 모듈 평가, 폰트·복원, 첫 지도 표시를 분리한다. lazy import를 네이티브 번들 분할로 간주하지 않는다. |
| 지도 장소 | 클러스터 제거, 카메라 idle 시 실제 영역 기반 windowing, 뷰포트 폭·높이의 1.5배 렌더 범위, 조회 중심 snap, 전국 폴백 | 이동 시 서버 요청·렌더 마커 수·메모리 변화와 누락 없는 표시. 이미 구현한 windowing을 재구현하지 않는다. |
| 위치·방향 | 고빈도 구독을 `TrackedUserLocationMarker`로 격리하고 등록 마커는 memo 경계로 분리 | 위치 이벤트가 전체 지도·상세 렌더로 전파되는지, 구독이 종료·복귀 시 정리되는지 |
| 검색 | 공유 검색 훅, 300ms debounce, 2자 이상 조회, AbortSignal | 빠른 타이핑의 요청 취소·오래된 응답 무시, 사용자 대기 중 debounce와 공급자 지연의 비중 |
| 사진 | 원본은 현재 페이지 ±1만 마운트, 썸네일은 FlatList, `expo-image`의 `memory-disk` 캐시 | 디코딩된 이미지·캐시·뷰어 반복 진입의 메모리. 언마운트를 즉시 메모리 반환으로 간주하지 않는다. |
| 서버 상태 | React Query 기본 staleTime 60초, gcTime 5분, retry 1회 | 지도 이동으로 늘어난 비활성 query, 캐시 적중·재요청, 복귀 시 refetch |
| 길안내 | 네이버 경로 미리보기와 KNSDK 전체 화면을 별도로 사용 | 두 SDK의 초기화·지도 다운로드·종료 비용, JS가 아닌 네이티브 병목 |
| 관찰 도구 | `ActiveRootLayout`에서 Sentry 초기화, 설정상 tracesSampleRate 0.2. PostHog 세션 리플레이 사용 | 실제 수집 구간·표본·부하. 현재 Sentry 초기화 전인 서비스 게이트를 자동 측정한다고 가정하지 않는다. |

## 3. 무엇을 측정할 것인가

### 3.1 화면 로드와 체감 반응

각 시간은 동일한 단조 증가 시계로 기록하고, 병렬 요청 시간을 합산해 전체 대기로 표시하지 않는다.
사용자가 처음 내용을 볼 수 있는 시점과 핵심 조작을 할 수 있는 시점을 분리한다.

| 구간 | 시작 → 종료 | 함께 남길 정보 |
|---|---|---|
| 프로세스 시작 | OS가 앱 실행 → 첫 실제 앱 콘텐츠 표시 | 프로세스 새 시작/재개, 최초 설치·권한·OTA 여부 |
| 사용 가능한 메인 | 실행 → 지도·핵심 컨트롤을 조작할 수 있음 | 서비스 게이트, 폰트·인증 복원, 지도 초기화 각각의 시간 |
| 서비스 게이트 | 상태 요청 시작 → 확인 결과·화면 반영 | 성공/중단/실패/재시도. 중단 화면은 정상 메인과 별도 시나리오 |
| 탭·화면 이동 | 입력 → 대상 화면의 기본 콘텐츠·조작 가능 | 이미 방문한 화면/처음 방문, 기존 데이터 캐시 여부 |
| 장소 상세 | 마커·결과 선택 → 타이틀·액션 사용 가능 | 등록/일반 장소, 기본 상세와 리뷰·날씨·유가 등 선택 정보 준비 시간 분리 |
| 검색 | 마지막 입력 또는 제출 → 결과·전용 empty·직접 장소 포커스 | debounce 포함 체감 시간과 실제 요청 시작 이후 시간을 모두 기록 |
| 지도 포커스 | 선택 → 최종 카메라·핀·시트가 함께 안정 | 직전 카메라 보존, 시트 제외 중앙 정렬, 빈 지도 프레임 여부 |
| 길안내 | 시작 입력 → 네이티브 안내가 사용 가능 | 경로 미리보기, KNSDK 초기화, 지도 준비를 각각 구분 |
| 사진 | 사진 선택·슬라이드 → 대상 이미지 표시 | 메모리/디스크/네트워크 캐시, 이미지 해상도, 실패·재시도 |

`onLayout`, 지도 `onInitialized`, 요청 완료는 **후보 계측 지점**이지 실제 화면에 픽셀이
보였다는 보장이 아니다. 내부 테스트 영상·프레임 기록과 대조해 의미를 확정한다. OS 시작은
네이티브 도구를 기준으로 삼고, Sentry span은 수집이 시작되는 이후 구간만 보조한다.

React Native에는 웹의 CLS 점수를 그대로 적용하지 않는다. skeleton → 실제 콘텐츠 전환,
조건부 섹션 등장 시 **화면 이동량·횟수와 빈 프레임**을 동일 화면 녹화로 비교한다.
속도 개선 때문에 스켈레톤과 실제 레이아웃의 불일치를 되살리지 않는다.

### 3.2 자원·안정성 지표

| 분야 | 지표 | 해석 시 주의 |
|---|---|---|
| 프레임 | JS·UI 작업 시간, 긴 프레임 분포, hitch·누락 프레임, 제스처 반응 | 평균 FPS만으로 판단하지 않는다. 60Hz 약 16.7ms / 120Hz 약 8.3ms는 프레임 예산의 참고값이며 실제 주사율을 기록한다. |
| CPU | 시나리오별 CPU 시간·벽시계 시간, JS/메인 스레드/SDK 작업, idle CPU | CPU 비율의 도구별 정의·코어 수를 남긴다. 낮은 CPU에서도 I/O 대기·잠금 때문에 메인 스레드가 멈출 수 있다. |
| 메모리 | 네이티브 메모리 footprint, JS heap, 피크·복귀 후 안정값, 반복 사용 추세 | JS heap과 전체 footprint를 더하지 않는다. 높은 캐시와 계속 증가하는 누수를 구별한다. |
| 네트워크 | 시나리오당 요청 수·응답 크기·지연·취소·오류·재시도 | 서버 처리, 전송, JS 파싱·정렬, 화면 반영을 가능한 범위에서 분리한다. |
| 캐시 | 활성/비활성 query 수, cache hit, 이미지·지도 캐시, 재방문 요청 수 | gcTime을 줄이면 메모리는 줄어도 재조회·CPU·데이터 사용량이 늘 수 있다. |
| 크기 | JS/Hermes 번들, OTA 전송량, 설치 크기, 이미지·폰트·카탈로그 비중 | 세 값은 서로 다르다. 압축 파일 크기로 디코딩 이미지 메모리를 추정하지 않는다. |
| 에너지 | 고정 시나리오의 전력·발열·위치/네트워크 활동 | 짧은 배터리 % 변화만으로 결론 내리지 않는다. 네트워크·온도·화면 조건을 맞춘다. |
| 안정성 | 크래시·hang·메모리 경고·복귀 실패, 기능 누락 | 빨라졌어도 마커·리뷰·검색 결과가 빠지면 개선이 아니다. |

JS·UI 스레드와 release 측정의 구분은
[React Native 0.81 성능 문서](https://reactnative.dev/docs/0.81/performance)를 기준으로 한다.
이 참조와 아래 도구 버전은 **업그레이드 전 조사 기준**이다. 목표 SDK·RN이 확정되면 해당 버전의
공식 도구·Hermes·Sentry 수집 범위를 다시 확인한다. 도구 변화와 앱 성능 변화를 혼동하지 않는다.

| 요청 계측·[DB 실행 계획](https://supabase.com/docs/guides/database/query-optimization) | 조회·응답·파싱 병목 분리 | DB 복구 및 승인 후 제한된 읽기 전용 요청으로 확인한다. 운영 부하·RLS·비용을 고려한다. |

### 4.1 비교 조건 고정

- iOS는 지원 범위 내 상대적으로 오래된 실기기 1대와 현재 주력 실기기 1대를 먼저 선정한다.
  정확한 기종·OS·빌드·OTA ID·SDK 버전·데이터 규모를 보고서에 남긴다. 시뮬레이터는 원인 탐색 보조로만 사용한다.
- 같은 기기의 전후 결과를 비교한다. 화면 밝기·주사율·저전력 모드·발열·충전 여부·네트워크를 맞추고,
  열 상태가 달라진 실행은 따로 표시한다. 다른 기기 CPU %를 직접 비교하지 않는다.
- 프로세스 새 시작, 살아 있는 프로세스로 복귀, 첫 설치·권한 승인, OTA 다운로드·재시작을 구분한다.
  강제 종료만으로 OS·지도·디스크 캐시까지 모두 초기화됐다고 부르지 않는다.
- 비어 있는 앱 데이터 캐시와 데워진 캐시를 별도 측정한다. SDK 타일 캐시를 통제할 수 없으면 그 한계를 기록한다.
  운영 계정의 즐겨찾기·인증 저장소를 측정을 위해 지우지 않는다.
- 개발/계측 빌드는 원인을 찾는 용도, release/TestFlight는 체감·최종 수치 확인 용도로 분리한다.
  무거운 프로파일러를 동시에 여러 개 붙이지 않고 계측 on/off 비교로 관찰 부하를 확인한다.

### 4.2 반복·집계 방법

1. 시나리오당 5회 예비 실행으로 계측 지점·캐시 상태·실패 조건을 확인한다.
2. 시작 시간은 조건별 20회, 짧은 화면·제스처 동작은 조건별 30회를 기본으로 측정한다.
   긴 길안내·에너지 시험은 횟수보다 동일 시간·동작 구간을 맞추고 실제 표본 수를 공개한다.
3. 소규모 표본은 중앙값(P50)·P90·최소/최대·실패 수를 함께 낸다. P95 판정이 필요한 조회는
   최소 100표본을 확보하되, 이 수만으로 통계적 정밀도가 보장되지는 않음을 명시한다.
4. 전후 비교는 동일 조건으로 3개 블록에서 반복한다. 가능한 시나리오는 A/B 실행 순서를 번갈아
   배치해 캐시·발열·네트워크 변화 영향을 줄인다. 최초 권한 등 반복 불가능한 조건은 별도 표기한다.
5. 느린 값·timeout·크래시를 임의로 제외하지 않는다. 사용자 취소는 실패와 분리하고,
   중도 종료 결과도 남긴다. 긴 작업이 끝나지 않으면 성공 표본의 평균으로 덮지 않는다.

메모리는 진입 → 동작 → 닫기/복귀를 10회 반복해 회차별 피크와 복귀 후 값을 기록한다.
복귀 30초·120초 시점 및 React Query 기본 gcTime 5분을 지난 6분 시점의 값도 비교한다.
강제 GC 결과는 보조로만 사용하고, SDK·이미지 캐시가 일정 수준에서 멈추는지와 객체·구독이
계속 남는지를 함께 본다. 사용량 증가만 보고 즉시 누수로 판정하지 않는다.

대규모 fixture를 운영 DB에 넣거나 전국 공급자 API를 반복 호출하지 않는다. 외부 API가 필요한
정합성 확인과 로컬 fixture 부하 시험을 나눈다.

재현 환경을 사용한다. 위치 좌표나 주행 경로를 성능 보고서에 보관하지 않는다.

## 6. 병목별 개선 후보와 착수 조건

**후보는 원인 확정이나 구현 지시가 아니다.** 기준값 수집 후 사용자 영향·재현성·비용·회귀 위험으로
정렬하고 한 번에 하나의 원인을 바꾼다. P0는 우선 조사이고, 효과 확인 전 무조건 SDK를 교체하지 않는다.

| 순서 | 후보 | 착수 증거·방향 | 예상 변경 범위 |
|---|---|---|---|
| 1 · P0 | 길안내 SDK의 main-thread hang | 기존 `KNMapLoaderRLM.loadMapInfo`·`initializeFullmapDownloader`의 2초 이상 멈춤 보고를 재현하고 CPU 작업/동기 I/O 대기를 구분. 공식 SDK 수정·공급자 제보·안전한 초기화 경계 검토 | 네이티브/SDK 변경은 새 빌드. JS 비동기 wrapper만으로 SDK 내부 blocking이 해결됐다고 하지 않음 |
| 2 · P1 | 앱 시작의 불필요한 직렬 대기 | gate·폰트·인증·모듈 평가별 critical path가 길 때. 필수 의존성을 유지하며 비필수 초기화 지연·병렬화 검토 | JS 중심이면 OTA 후보. 인증·개인정보·초기화 계약 변경은 별도 승인 |
| 3 · P1 | 지도 렌더·구독·조회 낭비 | idle에도 CPU가 높거나 이동당 전체 렌더/중복 요청이 많을 때. 기존 windowing 효과·selector 경계·취소·구독 cleanup 확인 | OTA 후보. 마커 표시 규칙·위치 정확도는 유지 |
| 4 · P1 | 이미지·목록 메모리 | 반복 진입 후 안정값이 계속 늘거나 실제로 원본을 불필요하게 디코딩할 때. thumbnail/original 분리·이미지 크기·list window·해제 경계 검토 | JS/이미지 처리 중심. 라이브러리·업로드 모델 변경 시 별도 계획 |
| 5 · P1 | query 캐시·검색·응답 변환 | 지도 이동마다 query·응답 크기가 누적되거나 파싱·정렬 CPU가 클 때. 요청 수·cache hit·gc 이후 값 확인 후 조정 | OTA 후보. 서버/RPC/RLS 변경은 승인·마이그레이션 검증 |
| 6 · P2 | AI 애니메이션·리플레이 비용 | 긴 답변의 프레임 저하, 계측 on/off 자원 차이, 기존 PostHog 예산 조건 확인 | 단어 애니메이션 상한·리플레이 표본화. 마스킹·오류 관찰 유지 |
| 7 · P2 | 카탈로그·폰트·번들 | Atlas 비중과 실제 시작 CPU/전송량이 함께 의미 있을 때 | 단순 파일 분할·맹목적 압축 금지. 네이티브 포함 자산 감소는 다음 빌드에서 확인 |
| 8 · P3 | 서버 범위 조회·SDK 전환 | 기존 백로그의 승인 장소 >500개 또는 미리보기 조회 P95 >300ms 조건. Expo 업그레이드는 공식 호환성·보안 근거 확인 후 | DB/의존성/패치·runtime 동기화 필요. 업그레이드를 자동 성능 개선으로 가정하지 않음 |

기존 시행착오를 다시 만들지 않는다.

- 마커를 고빈도로 확대·축소하거나 children 캡처 방식으로 바꾸지 않는다. 텍스처 폭주·잔상 문제가 있었다.
- windowing 개선을 이유로 선택 장소·내 위치를 빼거나 클러스터를 되살리지 않는다.
- 검색 복귀 지도를 unmount/freeze해서 검은 화면·잘못된 시작 카메라를 만들지 않는다.
- 바텀시트의 `animateOnMount={false}`와 등록/일반 장소의 동작·레이아웃 일관성을 지킨다.
- `useMemo`/`useCallback`을 일괄 추가하지 않는다. profiler로 긴 작업·불필요한 렌더 경계를 찾은 뒤 적용한다.
- 위치 센서·길안내 정확도를 낮춰 수치만 좋게 만들거나 네이티브 위치 표시를 중복 활성화하지 않는다.
- 요청을 다 기다리게 하거나 과도한 고정 높이를 넣어 로딩·레이아웃 지표를 숨기지 않는다.

## 7. 목표·완료 판정 초안

기준값이 없으므로 절대 목표는 **협의용 후보**다. 1차 측정 후 기기·시나리오별 예산을 정하고,
정상 네트워크와 장애 시 목표를 분리한다. 아래 숫자를 현재 달성한 결과나 공개 SLA로 사용하지 않는다.

| 항목 | 초기 목표 후보 | 판정 방법 |
|---|---|---|
| 터치 | 사용자 입력의 시각적 첫 반응 100ms 이내 | 서버 완료 시간이 아니라 pressed/optimistic 등 첫 반응을 측정 |
| 장소 상세 | 이미 캐시된 기본 콘텐츠 300ms 이내 | 리뷰·날씨 등 선택 정보 준비와 구분. uncached/느린 네트워크는 기준값 후 설정 |
| 앱 시작 | 기준값 수집 후 첫 화면·핵심 조작 각각 예산 설정 | 단일 ‘로딩 완료’로 필수 게이트와 지도 준비를 감추지 않음 |
| 프레임·hang | 같은 제스처의 긴 프레임·hitch 감소, 기존 2초 이상 SDK hang 재현 해결 | 평균 FPS 개선만으로 통과하지 않음. 처리 중 실제 blocking이 사라졌는지 확인 |
| 메모리 | 캐시 안정화 후 반복 루프에서 지속 상승·이탈 객체 없음 | 기기별 peak 예산은 실측 후 설정. 무조건 동일 MB 목표를 강제하지 않음 |
| 요청·에너지 | 불필요 요청·idle 작업 감소, 기능·정확도·발열 악화 없음 | 더 자주 요청하는 메모리 절감 등 트레이드오프를 함께 공개 |
| 회귀 | 핵심 지표가 전후 3블록에서 10% 이상 악화되면 원인 검토 | 자연 변동 폭·계측 부하와 대조. 크래시·빈 화면·결과 누락은 비율과 무관하게 실패 |

최적화 완료는 **원인 증거 + 전후 반복 측정 + 기능 회귀 통과 + 부작용 확인**이 모두 있어야 한다.
차이가 측정 잡음 수준이면 효과 미확인으로 기록하고 불필요한 복잡도를 남기지 않는다.

| 2 | 패키지 업그레이드 U2~U3, 기능·호환성 안정화 | Expo 지원 조합·native patch·로그인·OTA·지도·길안내·사용자 상태 검증, 최적화 코드는 섞지 않음 |

| 4 | 같은 패키지 조합에서 병목 하나씩 수정·재측정 | 원인별 최소 논리 커밋, 전후 수치·트레이드오프·롤백 방법 |
| 5 | 동일 시나리오·긴 세션·지원 runtime 회귀 | 순서·빈 화면·마커·사진·검색·길안내 정확성 확인, 개인정보·릴리스 정책 동기화 |
| 6 · 승인된 공개 재개/배포 후 | 정상 계측 설정에서 버전별 관찰 | 충분한 표본의 trace·hang·오류 확인. 표본 부족은 별도 표기, 개선 근거 갱신 |

이전 초안의 ‘현재 조합에서 전체 측정 후 최적화’ 순서는 패키지 전환이 예정된 이번 재개에 대해서
[PERF-002](domain-decisions/performance.md)의 순서로 보완했다. 구버전 최소 기준과 신버전 기준의
차이는 **버전업 영향**, 신버전 기준과 같은 패키지 조합의 최적화본 차이는 **최적화 효과**로 기록한다.
구버전이 중단 게이트로 실행 불가능하면 비교용 활성 OTA를 만들지 않고 미측정으로 남긴다.
서로 다른 네이티브 SDK 비교본을 같은 appVersion/runtime/channel로 배포하지 않는다.

문서 단계에서 빌드·푸시·OTA는 하지 않는다. 이후 계측·다영역 최적화·DB·의존성·네이티브 작업은
검증·커밋 후 푸시/배포 승인을 받는다. 변경별 OTA 가능 여부는
[릴리스·호환성 정책](domain-decisions/release-compatibility.md)으로 판단하고 `check:release`를 통과시킨다.
UI 성능 문제를 해결하는 작은 JS 수정도 이번 계획 실행 범위에서는 사전 합의한 배포 경계를 따른다.

각 수정은 `npx tsc --noEmit`와 관련 순수 테스트를 실행한다. 지도·gesture·SDK의 체감 성능은
타입 검사로 검증됐다고 하지 않는다. 기존 테스트가 없는 동작은 내부 실기기 시나리오로 확인한다.

## 10. 개인정보·측정 비용·기록 관리

- 허용 필드는 scenario ID, 화면의 **경로 패턴**(실제 장소·사용자 ID 제외), 익명화된 기기 등급,
  앱/빌드/runtime/OTA, 소요 시간·횟수·크기·성공 여부·캐시 상태 등 최소값으로 제한한다.
- GPS 좌표·주행 경로·검색어·목적지·집/회사·이메일·토큰·사진 내용은 성능 span·이벤트에 넣지 않는다.
  좌표가 들어간 queryKey·요청 URL도 그대로 로그로 남기지 않는다.
- heap dump, Instruments trace, 화면 녹화에는 사용자 문자열·위치가 포함될 수 있다.
  원본은 접근 제한된 로컬 보관, 공유 전 점검·삭제하고 저장소에는 요약만 넣는다. 외부 SDK 제보도 동일하다.
- Expo Atlas 산출물에는 번들 소스와 인라인된 `EXPO_PUBLIC_*` 값이 포함될 수 있다.
  원본을 커밋하거나 공개 업로드하지 않는다.
- 성능 관찰은 Sentry를 기본으로 하고 PostHog에 동일 trace를 중복 수집하지 않는다.
  서비스 게이트보다 먼저 telemetry를 활성화해 중단 정책을 우회하지 않는다.
- 최소 계측이 실패해도 사용자 동작을 막지 않게 한다. 샘플링과 전송량·리플레이 비용을 확인하고
  개인정보 마스킹을 해제하는 방식으로 측정 비용을 줄이지 않는다.
- DB 실행 계획은 승인된 읽기 전용 조회만 대상으로 한다. `EXPLAIN ANALYZE`도 실제 쿼리를
  실행하므로 부작용 함수·쓰기 쿼리·운영 부하를 사전 확인하고 RLS를 우회하지 않는다.
- 결정이 바뀌면 [PERF 기록](domain-decisions/performance.md), 이 계획, 해당 도메인·백로그를
  같은 논리 단위에서 동기화한다. 이전 측정·실패 기록은 삭제하지 않고 후속 결과와 연결한다.

[Apple의 지원 표](https://developer.apple.com/xcode/system-requirements)는 Xcode 26.6의 macOS
지원 범위를 26.x로, 안정판 Xcode 27은 macOS 26.6 이상으로 표시한다. 호스트와 호환되는
안정판 도구 갱신은 다른 프로젝트에 영향을 주는 공용 환경 변경이므로 별도로 승인받는다.
단순히 기기가 iOS 27이라는 이유만으로 Xcode 26.6의 모든 device support가 불가능하다고 하지는 않는다.

### 재개 순서

1. 승인된 안정판 Xcode 설치·선택 후 GUI 실행, `xcodebuild`·SDK·`xctrace` 기기 연결을 다시 확인한다.
   Apple 로그인·약관 동의가 필요하면 사용자에게 넘긴다. beta/RC를 임의로 선택하지 않는다.
2. [Expo SDK 57 안내](https://expo.dev/changelog/sdk-57)에 따라 iOS 27 SDK의 scene 설정,
   카카오 소셜 callback, KNSDK 수명주기를 검토한다. 기존 non-scene 생성 성공을 새 SDK 검증으로 대체하지 않는다.
3. Pods·codegen·native compile을 다시 진행한다. CLI의 Node 22.23.0과 Pods 하위 프로세스에서
   관측된 Node 25.8.1 경로 차이도 확인하고 실제 사용 도구를 고정·기록한다.
4. Release 설정 + 개발용 서명으로 빌드하고 설치 전 app/runtime·bundle ID·서명·
   `get-task-allow`를 확인한다. Sentry 자동 업로드·Expo CLI telemetry는 끄며 앱 데이터를 지우지 않는다.
5. 설치·프로파일 연결 후 중단 화면 시나리오와 실제 지도 시나리오를 분리한다. `suspended`에서는
   지도·센서 비교가 불가능하다. 운영 복구 승인 전에는 우회하지 않으며 중단 화면 수치를 지도 개선 효과로 보고하지 않는다.
6. 승인된 실제 지도 실행 환경에서 같은 SDK의 최적화 전/후를 비교한다. 기존 1.2.7 기준값을
   얻지 못하면 버전업 개선율은 미확인으로 남기고 신버전 기준부터 측정한다.

### 후속 실행 — Xcode 27 설치, 약관 동의 대기

- 사용자가 공용 Xcode 업데이트를 승인해 App Store에서 **Xcode 27.0 안정판**을 설치했다.
  설치 정보의 버전과 첫 GUI 실행을 확인했고 기존 OS 비호환 실행 거부는 사라졌다.
- 첫 실행에서 `Xcode and Apple SDKs Agreement`가 표시됐다. 법적 동의는 업데이트 승인과
  구분해 사용자 확인을 요청했으며 `Agree`를 누르거나 CLI로 대신 수락하지 않았다.
  약관 동의·첫 실행 구성 후 SDK·Instruments 연결을 다시 확인한다.
- iOS 27 SDK용 Expo scene 설정을 추가해 재생성과 plist 검사를 통과했다. 카카오 URL 처리,
  universal link와 기존 AppDelegate 수명주기 전달은 생성물·상류 소스에서 보존됨을 확인했다.
- 별도 Naver codegen과 Pods 과정의 전체 RN iOS codegen이 통과했다. RN dependencies release와
  RN core debug 아카이브의 공급자 SHA1 확인도 통과했다. 이는 전체 Pods 설치나 컴파일 성공을 의미하지 않는다.
- 느린 artifact 연결은 받은 임시 파일을 유지해 이어받았다. 완성된 RN core debug 파일만 검증 후
  다운로드 산출물로 옮겼다. 임의의 SDK 바이너리·검증 우회·구성 대체는 사용하지 않았다.
- 로컬 빌드의 `.xcode.env.local`은 Node 22.23.0을 명시했다. 기기의 기존 1.2.7 앱·데이터는
  변경하지 않았으며 모든 CPU·메모리·프레임 결과와 개선율은 미측정이다.
- 소스 설정·전달 경로 회귀 테스트 포함 **44개**, 타입 검사, 기본·origin/main 비교
  `check:release`는 통과했다. 변경 커밋은 `675b7ca`이며 푸시·공개 배포는 하지 않았다.

### 후속 실행 — 사용자 약관 동의 완료·기기 연결 복구

- 사용자가 Xcode 이용약관 동의를 직접 완료했다고 알려주었다. 별도 CLI 수락은 실행하지 않았다.
- `xcodebuild -version`: Xcode **27.0 / 27A266a**. `-checkFirstLaunchStatus` 성공과 iOS SDK **27.0**을 확인했다.
- CoreDevice에서 유선 connected·usable DDI를 확인했고 `xctrace list devices`에서도 iOS 27.0.1
  실기기가 Offline이 아닌 온라인으로 표시된다. 이전 연결 실패가 현재는 재현되지 않는다.
- 기존 앱·데이터는 아직 교체하지 않았다. Pods·개발용 Release 서명 빌드·설치·프로파일을
  이어가되 운영 복구·게이트 우회·공개 배포는 하지 않는다. 지도·길안내 성능은 환경 복구 승인 뒤에 측정한다.

### 후속 실행 — Pods·Release 컴파일 통과, Apple 개발자 계약에서 서명 차단

- CocoaPods 목록 갱신으로 NMapsMap 3.24.0 조회 실패를 해결했다. 최종 설치는 **128 dependencies /
  141 pods**, 전체 iOS codegen을 통과했다. Expo post-install이 KakaoNavi의 iOS target도 16.4로
  맞췄으므로 모듈 podspec을 선제 변경하지 않았다.
- RN core·dependencies·Hermes의 동일 공급자 URL 아카이브를 재사용했다. 중복 다운로드가 느려
  임시 실행에만 URL allowlist·공급자 SHA1 재확인 후 복사하는 다운로드 캐시를 사용했다.
  원래 추출·prepare·Pod 검사와 Release 전환 스크립트는 유지했다. SDK 버전·podspec·전역 도구는 변경하지 않았다.
- 별도 snapshot의 Xcode 27 / iOS 27 SDK / Release **서명 없는 컴파일(exit 0)**과 번들 생성을
  확인했다. 소스는 `26cc80e`에 `675b7ca`의 scene 설정을 적용한 후보 1.2.8이며 원래 `ios/`는 보존했다.
  `-quiet` 실행은 Swift 경고와 함께 ‘exit code 0 but produced no further output’ 진단을
  출력했지만 최종 종료 코드는 0이었다. 진단 문구만으로 컴파일 실패/해결을 단정하지 않는다.
  이어서 `-quiet` 없이 재확인한 Release 빌드도 **BUILD SUCCEEDED / exit 0**을 확인했다.
  생성된 앱의 version·runtime은 모두 1.2.8이다. 이것은 서명 없는 산출물이라 기기에 설치하지 않는다.
- 기존 개발 프로필에는 Apple 로그인·Associated Domains 권한이 없었다. 사용자가 모토맵의
  개발용 서명 갱신을 승인해 `-allowProvisioningUpdates`를 실행했으나 Apple 서버가
  **PLA Update available**로 거부했다. 최신 **Apple Developer Program License Agreement**는
  Xcode·SDK 약관과 별개이며 사용자 검토·동의가 필요하다. 권한을 빼거나 대신 수락하지 않았다.
- 개발자 계약 동의 후 프로필 갱신·서명 빌드를 재시도하고 entitlements·bundle/runtime을
  확인한 뒤 기존 앱 위에 설치한다. 앱 삭제·데이터 초기화, EAS 제출·공개 배포는 하지 않는다.
- 앱 설치·실행·CPU·메모리·프레임·에너지는 **아직 미측정**이다. 현재 설치 앱은 여전히 1.2.7이며
  운영 DB·공급자·게이트도 유지한다. 실제 지도 비교는 운영 환경 복구의 별도 승인 이후에 가능하다.
