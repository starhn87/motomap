## 신고 내용과 제품·고지의 대조

신고 서류 원본은 저장소에 보관하지 않는다. 운영자가 제공한 신고 완료 정보와 공개 사업자
표기를 반영하되, 아래 내용을 실제 신고 범위와 하나씩 대조한다. 불일치가 있으면 코드를
먼저 공개하거나 신고 내용을 추정해서 약관에 반영하지 않고 담당기관에 보완·변경 필요 여부를
확인한다.

- [ ] 사업자등록과 신고확인증의 상호·대표자·주소가 서로 일치한다.
- [ ] 신고한 서비스 설명이 주변 검색, 날씨·유가, AI 추천, 이륜차 길안내, 도착·경유 기록의 실제
  위치 처리와 일치한다. 향후 라이딩 경로 Visualizer는 현재 서비스와 구별해 별도로 검토한다.
- [x] [공통 법률 문서](../constants/legal.ts)의 상호·대표자·문의 이메일을 운영자가 확인한
  정보로 맞춘다. 개인정보·위치정보 보호책임자는 대표 이승우로 표기한다.
- [x] 사업장 주소·전화번호는 2026-10-10 운영자가 공개 기재를 허용한 정확한 표기로 공통
  법률 문서에 반영한다. 개인식별번호·등록증 원본은 저장소에 보관하지 않는다.
- [ ] 위치기반서비스 이용약관의 나머지 필수 고지와 실제 처리·보호조치를 대조한다.
  위치정보 이용·제공사실 확인자료의 보유근거·기간과 실제 보관 절차도 확인한다.
  [위치정보법 제19조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029559611)
- [ ] 개정 약관·방침의 시행일과 고지 절차를 재개 일정에 맞춰 확정한다. 신고 수리일을
  서비스 재개일이나 약관 시행일로 자동 사용하지 않는다.
- [ ] 개인정보 처리방침의 수집 항목, 외부 제공·위탁·국외 이전, 보관·파기 문구를 앱 코드와
  공급자 계약·실제 설정에 대조한다. Supabase 리전, PostHog 화면 기록, Sentry 진단 항목과
  카카오 길안내 좌표 전송 범위를 포함한다.
- [ ] 위치기반 서비스 이용약관의 동의·철회·열람 경로가 실제 앱에서 작동하는지 확인한다.
- [ ] App Store 개인정보 공개, 위치 권한 문구, 리뷰어 안내와 위 두 문서를 맞춘다.
- [ ] 신고 시 제출한 보호조치의 증빙과 실제 접근 권한·로그·보존·삭제 절차를 대조하고
  공식 상담 또는 전문 검토의 결론을 민감 정보 없이 기록한다.

## 1.2.8 기술 준비

2026-10-04 추가 준비: [패키지 업그레이드 계획](package-upgrade-plan.md)과
[성능 계획](performance-optimization-plan.md)을 연결했다. 구버전 최소 기준 → 업그레이드·
기능 안정화 → 신버전 전체 측정·최적화 순서다. 후보 조사·문서화만 했으며 설치·버전 변경·
빌드·실측은 미착수다. 이 준비 기록이 아래 실기기·신고·공개 재개 게이트를 통과했다는 뜻은 아니다.

- [x] 홈과 무관한 웹 상태 조회 계약을 만들고, 기본값을 `suspended`로 고정한다.
- [x] 앱은 상태 응답이 없거나 잘못되면 서비스 모듈을 초기화하지 않는 재개 게이트를 둔다.
  별도 `internal-testflight` 채널만 준비 상태에서 내부 검증할 수 있도록 코드를 준비했다.
- [ ] 외부 공급자 오류를 실패·빈 결과·설정 비활성화로 구분하고
  [1.2.8 장애 대응 목록](domain-decisions/external-provider-resilience.md)을 완료한다.
- [ ] 운영 백엔드 재활성화 정비 창에 [주행 기록 결정 문서](domain-decisions/ride-history.md)의
  RIDE-004(과거 전체 GPS 경로 파기)를 적용하고 원문 좌표 없는 파기 증빙을 남긴다.
  재활성화 전에는 운영 DB를 건드리지 않는다.
- [ ] `config/release-policy.json`, 릴리즈 노트, App Store 문서, 네이티브 계약을 1.2.8로
  동기화하고 릴리스 검사와 TestFlight 실기기 검증을 통과한다.
- [ ] 재개 공지·푸시는 한 번만 발송되게 만들고 Expo ticket·receipt 및 무효 토큰을 확인한다.

## 실제 재개 게이트

1. 신고 수리·신고확인증과 사업자·법률 문서·보호조치의 일치를 확인한다.
2. 앱 공개 상태를 닫아둔 채 백엔드·외부 공급자를 복구하고 상태를 `preparing`으로 둔다.
   `internal-testflight` 빌드를 내부 그룹에만 배포하여 성공·실패 경로를 모두 검증한다.
3. 1.2.8 App Store 배포와 구버전 업데이트 경로를 확인한다.
4. 웹 상태를 `active`로 바꾸고 새 설치·구버전 앱·딥링크를 다시 확인한다.
5. **맨 마지막에** 운영 재개 공지·푸시를 발송하고 도달·실패와 Sentry 오류를 관찰한다.

신고 접수만으로 재개하지 않는 원칙은 유지한다. 2026-10-10 운영자가 신고 수리 완료와 아래
준비 작업을 승인했지만, 실제 복구·배포·공개 상태 전환·전체 푸시는 별도 승인을 받는다.
2026년 10월 중 재개 약속의 변경 가능성이 생기면 월말 전에 앱·웹·README·고객지원 안내를
함께 갱신한다.

## 2026년 10월 재개 작업과 승인 경계

- 코드 작성·의존성 설치·정적 검사·순수 테스트·최소 논리 단위 커밋은 승인 범위에 포함된다.
- Git 푸시, 로컬/클라우드 네이티브 빌드, TestFlight/App Store 제출, OTA·웹 배포와 푸시
  알림 발송은 실행 전에 사용자 허락을 받는다. Expo prebuild·Pods·codegen 등 네이티브
  생성 작업도 빌드 검증 창에서 함께 승인받고 기존 ignored/untracked 파일을 보호한다.
- Supabase 복구·운영 마이그레이션·카카오/네이버 설정 복구·스케줄러 재개·`preparing` 또는
  `active` 상태 배포는 별도 운영 변경으로 승인받는다.
- 별도 Supabase 환경은 만들지 않는다. 준비 코드가 있어도 실기기·데이터 보존 검증을
  완료했다고 표시하지 않는다. Visualizer와 Android 공개 출시는 재개 필수 범위에서 제외한다.

다음 항목은 공개 재개 전에 반드시 해결한다.

1. 구버전 재개 연결 OTA는 이전 네이티브 조합으로 따로 준비한다. 업그레이드한 전체 앱을
   구 runtime 이름만 바꿔 배포하지 않는다. 구버전 경로는 App Store 업데이트까지만 제공한다.
2. `internal-testflight` 바이너리는 preparing 진입 예외가 있으므로 App Store에 그대로
   공개하지 않는다. 검증된 동일 코드·네이티브 조합을 production 채널로 따로 빌드한다.
3. production 앱을 preparing에서 막은 채 제출하면 심사팀도 기능을 검증할 수 없다.
   실제 서비스와 같은 기능에 접근할 승인된 심사 경로·계정을 설계·검증하고 심사 메모에
   설명한다. 내부 채널 문자열만으로 서버 권한을 부여하거나 일반 서비스와 다른 숨은 기능을
   심사팀에 보여주지 않는다. [Apple 심사 지침](https://developer.apple.com/app-store/review/guidelines/#before-you-submit)
4. 게이트를 받지 않은 구버전은 공급자 복구 직후 접근할 수 있다. 복구 정비 창의 서버 접근
   통제·기존 설치본 영향과 자동 계정 정리·외부 호출 스케줄러를 점검하고 승인받는다.
   앱의 준비 화면이나 EAS 채널을 백엔드 전체의 접근 통제로 오인하지 않는다.
5. 웹은 상태 JSON만 active로 바꾸면 복구되지 않는다. 소개·공유 라우팅과 상태를 함께
   검증하고, suspended/preparing·법률 문서·정적 자산·AASA 경계를 유지한다.
6. 재개 공지는 캠페인 식별자로 한 번만 등록·발송하고 ticket/receipt를 구분한다.
   APNs 전달 성공을 실제 열람 성공으로 표시하지 않는다. 본인 기기 검증 뒤 전체 발송한다.

## 2026-10-10 복구 전 점검 후속

사용자가 로컬 1.2.8의 중단 안내 표시를 확인하고 내부 검증용 DB·네이버·카카오 복구와
진입 준비를 승인했다. 공개 재개·Git 푸시·공개 배포·알림은 별도다.

| 점검 대상 | 확인 결과 | 다음 실행 조건 |
|---|---|---|
| production Supabase | `INACTIVE` | 기존 API 접근과 자동 작업 재개 영향을 포함한 정비 창 범위 확정 |
| 공개 상태·웹 | `suspended` / 홈 503 | 공개 서비스는 닫고 내부 진입만 허용할 승인된 preparing 변경 |
| 네이버 `ridemap` | 사용자 재로그인 뒤 Static Map만 확인 | 기존 자격 증명 복구가 구 설치본에도 적용됨을 반영 |
| 설치한 로컬 Release | Expo update channel 헤더 없음 | 정식 내부 채널 설정을 포함한 재빌드·설치. JS에서 채널을 위조하지 않음 |
| DB 자동 작업 | 저장소에 계정 정리·장소 검토 cron 존재 | 실제 cron·Vault·Edge Function 설정 확인 전 자동 작업 비활성 보장 불가 |
| 카카오·App Store | 이번 점검에서 콘솔 재확인하지 않음 | 과거 기록만으로 현재 상태를 확정하지 않음 |

내부 채널은 UI 분기이며 서버 보안 통제가 아니다. Supabase Network Restrictions도 HTTPS
Auth·Data API·Storage에는 적용되지 않는다. 구버전까지 완전히 닫는 격리를 새로 구성할지,
기존 키를 복구하는 정비 창에서 일부 구버전 호출 가능성을 받아들일지 먼저 확정한다.
이 선택 전에는 원격 복구를 실행하지 않았다. 상세 근거는 OPS-006 후속 기록을 따른다.

복구 시 Supabase가 보존된 데이터·설정을 되살리거나 서비스 버전을 갱신할 수 있으므로 실제
Postgres·확장·마이그레이션·cron·데이터 보존을 대조한다. 최신 Postgres 17.11 변경의
ltree·pgcrypto·btree_gist·사용자 정의 operator 해당 여부도 실제 카탈로그에서 확인한다.
[공식 변경 안내](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes)
