# 모토맵 운영 재개 준비 점검

2026-09-30 기준의 **준비 목록**이다. 이 문서 자체는 법률 적합성 확인이나 운영 재개 승인이
아니다. 실제 상태 전환 순서는 [서비스 중단·재개 결정](domain-decisions/service-suspension.md)의
OPS-003을 따른다.

## 현재 확인된 상태

| 항목 | 상태 | 확인 근거·다음 작업 |
|---|---|---|
| 사업자등록 | 운영자가 완료했다고 알림 | 등록증의 상호·대표자·사업장·업종을 비공개로 대조한다. 번호·주소 원문은 저장소에 기록하지 않는다. |
| 위치기반서비스사업 신고 | 운영자가 접수했다고 알림 | **접수와 수리는 다르다.** 처리 결과와 신고확인증의 사업자 정보·서비스 범위를 확인한다. |
| 앱 공개 상태 | 중단 유지 | `app/_layout.tsx`는 공개 상태·설치 버전·호환 OTA가 검증되기 전 서비스 모듈을 마운트하지 않는다. |
| 웹 공개 상태 | 중단 유지 | 홈·공유는 503, 법률 문서와 AASA는 접근 가능. `/service-status`도 `suspended`로만 준비한다. |
| 운영 백엔드·지도 공급자 | 중단 유지 | Supabase, 네이버 지도, 카카오맵과 iOS 번들 ID 복구는 신고·보호조치 확인 후에만 한다. |

공식 신고 절차는 `민원 신청 → 접수 → 서류 심사 → 신고 수리 → 신고확인증 교부`다.
[방송미디어통신위원회 안내](https://www.kmcc.go.kr/user.do?page=A04100213)

## 신고 내용과 제품·고지의 대조

신고 서류 원본은 아직 이 저장소에서 확인할 수 없다. 운영자가 민감 정보를 가린 사업계획서와
처리 결과를 제공하면 아래 내용을 실제 신고 범위와 하나씩 대조한다. 불일치가 있으면 코드를
먼저 공개하거나 신고 내용을 추정해서 약관에 반영하지 않고 담당기관에 보완·변경 필요 여부를
확인한다.

- [ ] 사업자등록과 신고확인증의 상호·대표자·주소가 서로 일치한다.
- [ ] 신고한 서비스 설명이 주변 검색, 날씨·유가, AI 추천, 이륜차 길안내, 도착·경유 기록의 실제
  위치 처리와 일치한다. 향후 라이딩 경로 Visualizer는 현재 서비스와 구별해 별도로 검토한다.
- [ ] [공통 법률 문서](../constants/legal.ts)의 운영 주체 표기와 연락 수단을 등록 정보에 맞춘다.
  현재 이 파일은 `회사`라는 템플릿 표현과 배포 전 검토 필요 주석을 사용한다. 이것만으로
  법률상 오류라고 단정하지 않고 운영 주체가 개인사업자인 점과 맞춰 검토한다.
- [ ] 개인정보 처리방침의 수집 항목, 외부 제공·위탁·국외 이전, 보관·파기 문구를 앱 코드와
  공급자 계약·실제 설정에 대조한다. Supabase 리전, PostHog 화면 기록, Sentry 진단 항목과
  카카오 길안내 좌표 전송 범위를 포함한다.
- [ ] 위치기반 서비스 이용약관의 동의·철회·열람 경로가 실제 앱에서 작동하는지 확인한다.
- [ ] App Store 개인정보 공개, 위치 권한 문구, 리뷰어 안내와 위 두 문서를 맞춘다.
- [ ] 신고 시 제출한 보호조치의 증빙과 실제 접근 권한·로그·보존·삭제 절차를 대조하고
  공식 상담 또는 전문 검토의 결론을 민감 정보 없이 기록한다.

## 1.2.8 기술 준비

- [x] 홈과 무관한 웹 상태 조회 계약을 만들고, 기본값을 `suspended`로 고정한다.
- [x] 앱은 상태 응답이 없거나 잘못되면 서비스 모듈을 초기화하지 않는 재개 게이트를 둔다.
  별도 `internal-testflight` 채널만 준비 상태에서 내부 검증할 수 있도록 코드를 준비했다.
- [ ] 외부 공급자 오류를 실패·빈 결과·설정 비활성화로 구분하고
  [1.2.8 장애 대응 목록](domain-decisions/external-provider-resilience.md)을 완료한다.
- [ ] 운영 백엔드 재활성화 정비 창에 [주행 기록 결정 문서](domain-decisions/ride-history.md)의
  RIDE-004(과거 전체 GPS 경로 파기)를 적용하고 원문 좌표 없는 파기 증빙을 남긴다.
  재활성화 전에는 운영 DB를 건드리지 않는다.
- [ ] `config/release-policy.json`, 릴리즈 노트, App Store 문서, 네이티브 계약을 1.2.8로
  동기화하고 릴리스 검사와 TestFlight 실기기 검증을 통과한다.
- [ ] 재개 공지·푸시는 한 번만 발송되게 만들고 Expo ticket·receipt 및 무효 토큰을 확인한다.

## 실제 재개 게이트

1. 신고 수리·신고확인증과 사업자·법률 문서·보호조치의 일치를 확인한다.
2. 앱 공개 상태를 닫아둔 채 백엔드·외부 공급자를 복구하고 상태를 `preparing`으로 둔다.
   `internal-testflight` 빌드를 내부 그룹에만 배포하여 성공·실패 경로를 모두 검증한다.
3. 1.2.8 App Store 배포와 구버전 업데이트 경로를 확인한다.
4. 웹 상태를 `active`로 바꾸고 새 설치·구버전 앱·딥링크를 다시 확인한다.
5. **맨 마지막에** 운영 재개 공지·푸시를 발송하고 도달·실패와 Sentry 오류를 관찰한다.

신고 접수만으로 1~5단계를 앞당기지 않는다. 2026년 10월 중 재개 약속의 변경 가능성이 생기면
월말 전에 앱·웹·README·고객지원 안내를 함께 갱신한다.
